# ADR-0094: Close the recovery-path character-count gap (packages silently re-promoted to completed while missing whole characters)

- **Status:** Accepted
- **Date:** 2026-08-19
- **Related:** ADR-0093 (Ciaran Fox incident that surfaced this gap and deliberately deferred fixing it), ADR-0049 (`package_completion_blocking_defects()` — the existing shared-defect-check pattern this ADR extends), ADR-0064 (roster-count-mismatch detector — the async safety net this ADR complements, not replaces), ADR-0043 (`list_completed_but_empty_packages` — the zero-character detector this ADR's historical sweep leaned on to rule out other live cases)

## Context

ADR-0093 fixed three bugs in Ciaran Fox's package and, in its Consequences section, flagged a fourth, un-fixed gap: `mystery_packages.generation_status` can report `completed` even when `mystery_characters` has fewer rows than the roster the customer approved. Root cause of *why* characters go missing (the Make.com parent scenario fires one webhook per character to the Child scenario and gets an immediate 200 ack regardless of whether the Child actually succeeds — no per-character failure visibility) was already traced in that ADR and is not re-litigated here. This ADR is about the separate question: given that some characters WILL occasionally fail to generate, why does the *package* end up marked `completed` anyway, silently, with no alert?

Traced the actual mechanism by reading the live DB functions (`pg_get_functiondef`, not the migration files, per the drift discipline ADR-0089's Discussion established):

- `validate_package_characters()` — the trigger that fires once, on `mystery_packages.generation_completed_at` transitioning `NULL -> NOT NULL` — already does the right thing. It compares `mystery_characters` row count against the roster size parsed from `extracted_characters`, and downgrades `generation_status` to `needs_review` if the actual count is short. This is almost certainly what caught Ciaran's package the first time Make.com's parent scenario finished (16 of 24 succeeded, 8 silently failed) and correctly held it at `needs_review`.
- But two **recovery paths**, both running every 2 minutes via `pg_cron` (`heal_completed_packages_2min`, `sweep_incomplete_packages_2min` — the latter calls `promote_complete_packages()`), promote `needs_review -> completed` again once nothing looks wrong with the characters that exist. Both were extended in ADR-0049 to also call `package_completion_blocking_defects()` (guards against invalid `character_role` / raw error bodies), but **neither was ever given a row-count check**. Their promotion condition is only "no existing row has NULL/empty content" — a package with 16 non-empty, well-formed character rows and 8 rows that were never inserted at all satisfies that condition perfectly.
- Net effect: a package correctly held at `needs_review` for a missing-characters reason gets silently re-promoted to `completed` by the very next cron tick (worst case ~2 minutes later), with no email, no log line a human would see, nothing — `heal_completed_packages()`/`promote_complete_packages()` don't call `notify-generation-issue` on promotion, only on the sweeps that *find* problems. This matches Ciaran's incident exactly and is a structural gap, not a one-off.

**Historical sweep** (requested as part of this task, run directly against production via `mcp__supabase__execute_sql`): compared `mystery_characters` row count against `conversations.player_count` for every `completed` package. 21 packages came back short. Investigated each:
- 1 is "Whispers From The Void" — already known-owned (memory `project_whispers_from_the_void_owned`): an intentional guest-dropout removal, not a bug.
- The remaining 20 all trace to `generation_completed_at` / `created_at` values from July 2025 through April 2026 — before ADR-0043 (the "completed but empty" completion-gate work, 2026-07-26) existed. This exact cohort was already investigated and closed in the 2026-08-13 CHANGELOG entry ("Investigation: host_guide/timeline 'null on 56%' was a false alarm — real gap is 13 old pre-ADR-0043 records, zero live impact"). Their `updated_at` all cluster on one of two exact timestamps (`2026-07-02 14:53:54.75796+00` or `2026-08-01 08:28:46.984237+00`) matching the JSON-normalization migrations run those days (`20260801_normalize_generation_status_*`), which bulk-`UPDATE`d `generation_status` on every row and so bumped `updated_at` without the packages having done anything — confirmed by checking `created_at`/`generation_completed_at` on a sample, all predating the timestamp by months.
- **Conclusion: no other live instance of this specific bug exists today.** Also confirmed zero packages are currently sitting in `needs_review` at all (a clean slate to ship this fix against — nothing this migration touches will change behavior for any package that exists today).

Also worth recording precisely because the codebase has already been burned by it once (ADR-0064's Discussion): `conversations.player_count` is **guest headcount**, not intended character count — the product deliberately allows extra guests to co-investigate rather than getting their own character. Using `player_count` as "expected characters" in a blocking check would reopen exactly that false-positive class. The sweep above used `player_count` deliberately (broadest possible net, human-reviewed each hit), but the **fix** in this ADR uses `mystery_packages.extracted_characters` — the roster size parsed from the customer's approved concept, the same source `validate_package_characters()` has always used — not `player_count`.

## Decision

Close the gap at the same layer ADR-0049 already established for structural defects: extend the two recovery functions with a row-count check, sourced from one new shared function so the parsing logic exists in exactly one place.

1. **New function `package_expected_character_count(_pkg mystery_packages) RETURNS int`** — the roster-size parser that was inline inside `validate_package_characters()` (handles `extracted_characters` stored as a JSON array or, per an existing known Make.com quirk, as a bare string), extracted verbatim so it has one definition instead of a candidate for a second, driftable copy. Returns `0` (never blocks) when unparseable or absent — same fail-open posture the original inline logic already had.
2. **`validate_package_characters()` refactored** to call the shared function instead of its own inline copy. Pure extraction, byte-identical behavior for every existing caller.
3. **`heal_completed_packages()` and `promote_complete_packages()` extended**: both gained an additional `AND` clause requiring `mystery_characters` row count `>=` `package_expected_character_count(mp)` (or the expected count is `0`/unknown, in which case the check doesn't apply — matching the existing `_expected_count > 0` guard). Neither function was touched anywhere else; the existing `package_completion_blocking_defects()` guard from ADR-0049 stays exactly as it was.

## Rationale

- **One parsing function, three call sites** — not three copies. This codebase has a documented, named failure class for exactly this shape of mistake (memory `project_gate_detector_deadlock`: "Paired-predicate drift is the signature bug... 3 prod bugs same day, all 'one concept two predicates'", ADR-0055/56/57). `validate_package_characters()` already had the correct logic; the fix is to make the two recovery paths consume the *same* logic, not re-derive their own.
- **Reuses `extracted_characters`, not `player_count`.** `extracted_characters` is already the authoritative "what roster did we agree to generate" signal everywhere else in this codebase (`validate_package_characters()`, and — via a from-scratch re-parse of the chat transcript rather than this stored value — the ADR-0064 `roster_mismatch` detector). `player_count` is guest headcount and can legitimately exceed it. Using the wrong one would either miss real gaps (player_count too high, never blocks) or false-positive on every co-investigator package (player_count used as a hard floor).
- **Fixed at the same layer as the existing structural-defect guard (ADR-0049), not by changing the trigger's firing condition.** The trigger only re-validates on the `generation_completed_at` NULL→NOT NULL transition; broadening that would be a much larger change (every `UPDATE` touching `generation_status` would need re-validation logic, including from paths that have nothing to do with character generation) for the same outcome ADR-0049 already achieved narrowly: make the two specific recovery paths that CAN silently resurrect a blocked package structurally incapable of ignoring the reason it was blocked.
- **No auto-recovery added for entirely-missing character rows.** This ADR only stops the false "completed" signal — it does not make missing characters regenerate themselves. That's a deliberately separate, larger piece of work (see Consequences).

## Alternatives Considered

- **Use `conversations.player_count` as the expected-count source**, since that's the plainest "how many characters should exist" signal and was the initial framing of the task. Rejected once ADR-0064's Discussion was re-read: player_count is guest headcount, not roster size, and the product's own co-investigator design means the two numbers are allowed to diverge legitimately. Confirmed the risk isn't theoretical — several of the 21 sweep hits were `player_count` far exceeding `extracted_characters`-implied roster size in ways that look like the guest/character split, not a generation bug.
- **Real-time visibility fix on the Make.com side** (module 300/301/302 self-heal branch, or restructuring the child webhook call to wait for a real response instead of an immediate 200 ack) — this is the actual root cause of characters failing to generate in the first place, and is worth doing, but is a Make.com-side change requiring manual import/publish (this session has no Make.com API access, same constraint noted in ADR-0089/ADR-0093) and doesn't by itself explain why the *package* ships anyway once some characters fail. Deliberately out of scope for this ADR: closing the "ships despite failures" hole is valuable on its own regardless of whether the underlying failure rate ever improves, and doesn't require Jonathan to do a manual Make.com import to take effect (this fix is pure SQL, live the moment the migration runs).
- **A new async detector** (RPC + `health-check.yml` wiring), mirroring ADR-0064's `roster_mismatch` pattern. Considered but rejected as the *primary* fix: an async detector on a rolling schedule would have caught Ciaran's package eventually, but only after the customer already saw and complained about a "finished" package — the whole point of ADR-0093's Consequences flagging this was to stop the false-positive completion from happening at all, not to detect it faster after the fact. The existing `roster_mismatch` detector (ADR-0064) still runs and still adds value as an independent, differently-sourced safety net (it re-parses the approved chat transcript rather than trusting `extracted_characters`) — nothing here removes or duplicates it.

## Consequences

- **Positive:** the specific mechanism that let Ciaran's package (and, structurally, any future short package) get silently re-promoted to `completed` is closed. Verified against the live DB: zero packages currently in `needs_review`, so this ships against a clean slate with no existing package's status changing as a side effect.
- **Not addressed — deliberately, see Alternatives:** why characters fail to generate in the first place (Make.com parent/child ack-blindness). This ADR only stops the false "completed" signal once a shortfall has already happened.
- **Not addressed — a real remaining gap, flagged for follow-up, not built here:** once a package is correctly held at `needs_review` for missing (not just empty) characters, nothing regenerates the missing rows automatically. `notify-generation-issue`'s existing auto-recovery (fires a re-generation webhook per character) only covers characters that have a `mystery_characters` row with empty/invalid content — it has no code path for a roster slot that never got a row inserted at all, same limitation ADR-0093 already named. The existing alerting loop (`sweep_stuck_needs_review_packages`, every 10 minutes, re-invokes `notify-generation-issue`, subject to its 6-hour cooldown) will still page a human for these — this ADR's fix guarantees that page actually happens instead of being silently pre-empted by an incorrect promotion, but the recovery itself (as with Ciaran's package) remains a manual child-webhook re-fire.
- **`extracted_characters` can itself be wrong or absent** (parses to 0, or the extraction under/over-counted) — in that case `package_expected_character_count()` returns 0 and the new check doesn't apply, same fail-open behavior the original inline logic in `validate_package_characters()` already had. This is a pre-existing, accepted limitation (see ADR-0064's Discussion on the extractor's own scope limits), not something this ADR changes or worsens.

## Discussion

The task framing (and ADR-0093's own Consequences note) both pointed at `conversations.player_count` as the natural "expected character count" signal, and it's a reasonable first instinct — it's the plainest number in the schema that means "how many people are playing." Re-reading ADR-0064's Discussion before writing any SQL is what caught that this product deliberately breaks the assumption that guest count equals character count (co-investigators). Worth recording as a reminder for the next person who reaches for `player_count` in this codebase: check whether the thing being compared is "how many people bought a ticket" or "how many characters the approved concept promised," because those are two different, not-always-equal numbers and this codebase has a specific, deliberate feature (not a bug) that makes them diverge.

The other real decision point was whether to fix this by broadening `validate_package_characters()`'s trigger condition (so it re-validates on any `generation_status` write, not just the `generation_completed_at` transition) versus extending the two specific recovery functions. Broadening the trigger is more thorough in the abstract — it would catch a hypothetical future third path that also promotes to `completed` without going through either recovery function — but ADR-0049 already made this exact call for structural defects (extend the two known recovery paths, not the trigger's firing condition) and it has held up cleanly since. Consistency with that precedent, plus the narrower blast radius of touching two known functions instead of changing when a trigger fires at all, won out over the marginal extra coverage of a hypothetical unknown third path.
