# ADR-0054: Child-content regenerator — ADR-0051 layer 3

- **Status:** Accepted — built and deployed 2026-08-01; two eval findings fixed and redeployed 2026-08-02 (still a standalone primitive; not yet wired into the gate or the worker)
- **Date:** 2026-08-01 (updated 2026-08-02)

## Context

ADR-0051 named four layers to shift generation integrity left: (1) structural DB constraints, (2) a pre-completion gate over all detector classes (shipped same day as ADR-0053), (3) a child-content regenerator — the keystone that turns the gate's "hold" into "self-heal" — and (4) Make-pipeline reliability work (deferred).

Layer 2 shipped with a deliberate, named gap: `meta_text_leak`, `victim_mismatch`, `slip_culprit_leak`, and `identity_conflict` packages land in `needs_review` and **HOLD** — no auto-repair exists for most of these classes at the gate's point of action (ADR-0053, "Interim behaviour until layer 3"). Separately, the ADR-0047 auto-remediation worker has always escalated `identity_contamination` and `slip_culprit_leak` untouched, explicitly noting in its own source: "child-generated, judgment-heavy, no safe deterministic fix and no child-content regenerator yet."

Both gaps have the same shape: they are child-generated defects (they live in `mystery_characters` fields, not the host-facing `mystery_packages` fields `regenerate-parent-content` already handles), and character fields carry a coherence risk `regenerate-parent-content` doesn't: every character field is originally generated with knowledge of every *other* character via `master_context.relationshipMatrix`. Regenerating a character field blind — without that same cross-character context and the G-rule guardrails the live Child Make scenario uses — risks reintroducing the very defect being repaired (e.g. rewriting an `introduction` without re-checking it against the character's own `background`/`relationships` can just produce a *different* false kinship claim).

This ADR builds that regenerator: `regenerate-child-content`.

## Decision

Deploy a new edge function, `regenerate-child-content`, that regenerates a bounded set of whitelisted `mystery_characters` fields for one or more characters in a package, by calling Claude directly with a prompt mirrored from the live Child Make blueprint (`temp-files/MM Live - Child (Unified)19-SlipGuilt-OutputHygiene-VictimQuestions.blueprint.json`), gated by a mandatory re-detect check before any write is kept.

**Contract:**

```
POST { package_id, character_id, character_ids?, fields[], defect_class_hint?, dry_run? }
```

- `fields` must be drawn from the same whitelist `remediation_read_field`/`remediation_write_field` (ADR-0047) already enforce — this function adds no new writable surface. `secrets` (plural, jsonb) is in that DB whitelist but rejected here with an explicit error: the Child prompt only ever generates `secret` (singular, text); `secrets` has no generation equivalent to mirror.
- `defect_class_hint` (`identity_contamination` | `slip_culprit_leak` | `meta_text_leak`) is optional but does two things when given: (a) it **widens** `fields` — for `identity_contamination` specifically — to the full claims-bearing field set the `identity_conflict` detector's own text search scans (`introduction` + all round scripts/innocent-variants + final statement/final-innocent), unioned with whatever the caller asked for, never narrowed, so a single call doesn't leave the contamination sitting in a field nobody thought to name; and (b) it drives **auto-expansion** of the target-character set (below).

**Context assembly** (mirroring the Child scenario's own inputs): full `master_context` text, the target character's established role (read from the DB, not re-derived), the original per-character seed description (recovered from `mystery_packages.extracted_characters`, matched fuzzily since seed names are sometimes slash-separated e.g. `"Raven/Rave Sinclair"`), the full cast roster (names + roles, for rumor/question/accusation targeting), and `mystery_packages.user_conversation` as a brainstorming fallback. One gap, named honestly: the *per-character chat excerpts* the original generator used (`{{63.characterChatExcerpts}}` in the Make blueprint) are not persisted anywhere and are **not recoverable post-hoc** — the prompt says so explicitly and asks the model to rely on `master_context` and established fields instead.

**Anchor context (repair-specific, not present in the original generation prompt):** for every field in the current call's group that is *not* being regenerated, plus `background`/`relationships`/`secret`/`description` unconditionally when they aren't the target, the character's **current** value is included as "established truth, do not contradict." This is the mechanism that keeps a narrow repair (e.g. just `introduction`) from drifting away from fields that are staying put — without it, a field-scoped rewrite is exactly as likely to introduce a new inconsistency as the one it's fixing.

**Call-boundary mirroring:** fields are grouped into the same boundaries the live blueprint uses per mystery style — identity (`description`/`background`/`relationships`/`secret`/`introduction`), social (`rumors`/`accusations`, worded differently per style), and the round-script bundle (detective: `round2_script`.../`final_statement`; character-style: innocent bundle + guilty bundle + accomplice bundle, each a separate Claude call per the blueprint's own module split). **Correction (2026-08-02, eval finding):** a request touching a field in a group does NOT regenerate the whole group. The `output_schema` sent to Claude is filtered down to only the requested/effective subset within that group (`fieldsToGenerate = group.fields.filter(f => effectiveFields.includes(f))`), and every field that gets generated also gets written — nothing extra is generated, and nothing generated is withheld. Within-call coherence (e.g. round 3 questions must target different suspects than round 2) is preserved only when the relevant fields were requested together in the same call; naming a single field in a group does not pull its groupmates in for that benefit. The call-boundary grouping determines *which Claude call a field routes through*, not *how much gets regenerated*.

**Multi-character auto-discovery:** when `defect_class_hint` is given, the function calls the same ADR-0042/0041 detector RPCs `auto-remediate-packages` already uses (`list_packages_with_identity_conflicts`, `list_packages_with_slip_culprit_leak`, `list_packages_with_meta_text_leak`) *before* mutating, and unions every character named alongside the primary target into the repair set — bounded by `MAX_TARGET_CHARACTERS` (8). A 3+-claimant identity conflict, or a slip-culprit-leak package with several leaking characters, is fixed in one call rather than requiring the caller to loop and hope each partial fix doesn't get reverted by the others still being broken.

**The re-detect gate (mandatory, mirrors `auto-remediate-packages`'s `runGatedAttempt`):** before mutating, the function snapshots all four detector states for the package (not just the hinted one) — `identity_conflicts`, `meta_text_leak`, `slip_culprit_leak`, and `self_directed_questions`. **Correction (2026-08-02, eval finding):** the fourth class, `self_directed_questions`, was missing from the original ship — the gate checked only three. That was a real gap: this function is whitelisted to write `round2/3/4_questions`, and ADR-0053's completion gate blocks on `self_directed_question` exactly as it does the other three, so a repair that reintroduced a self-directed question would previously have been reported `outcome: "fixed"` instead of rejected. Now fixed — `list_packages_with_self_directed_questions` is in both the before/after snapshot and the acceptance logic (`stillImplicatesTouched` / `regressions`). After writing, the function re-snapshots and accepts the change only if (a) no defect instance naming a touched character survives, for the hinted class, and (b) **no new defect instance appeared in any of the four classes**, even for a character nobody touched this call. Failing either check reverts every write byte-for-byte and returns `outcome: "escalated"`. A content-loss guard (refuse a rewrite that guts a ≥40-char field by more than half) is a handler-independent backstop, same shape as ADR-0047's.

**Guarded per-field writes (2026-08-02, eval finding):** the per-field write loop (`readField` → content-loss guard → `writeField`) is wrapped in its own try/catch, not just the upstream Claude-call/parse step. As shipped, a `remediation_read_field` / `remediation_write_field` throw mid-loop — reproduced for `relationships` when the character's existing value is `null` or a jsonb object, roughly 7% of prod characters, though the gap applied to a throw on ANY field — escaped both for-loops uncaught, was caught only by the function's outermost handler, and returned a bare `500` *without* calling `revertAll()` or `logRow()`. Any fields already written earlier in that same call stayed committed, unreverted, and unlogged — a direct violation of the "degrade to escalate, never ship worse" invariant the rest of this function is built around. Now any write-loop throw sets the same `hadError` flag the generation-step catch already used, so it flows through the existing `revertAll()` + `logRow(outcome: "failed")` + response path instead of crashing past it. **Named, deliberately out of scope:** this makes a `relationships` throw on a null/object-valued character a *clean escalate* rather than an unlogged partial write — it does not make `remediation_write_field` able to actually repair `relationships` in that state. That's a separate follow-up (see Consequences).

**Spend + audit:** every attempt logs to the same `auto_remediation_log` table ADR-0047 built (`before_value`, `cost_usd`, `outcome`), and reads the same table's daily total against a **shared** `DAILY_SPEND_CAP_USD` ($5) — this function and the periodic worker draw from one ceiling, not two independent ones. Cost is a flat per-Claude-call estimate ($0.03), consistent with the flat-rate accounting `auto-remediate-packages` already uses for its own Claude call.

## Rationale

- **Reuses everything ADR-0047 already built and proved**, rather than inventing a parallel write path: the same whitelisted field accessors (so this function structurally cannot write a non-whitelisted column, independent of anything in its own logic), the same audit table, the same spend-cap pattern, and the same detector RPCs.
- **Mirrors the live generator's own prompt rather than writing a new one from scratch.** A repair prompt with different G-rules than the generator risks *reintroducing* a defect the generator no longer produces, or missing a guardrail the live blueprint has that a from-scratch rewrite wouldn't think to include. Verbatim mirroring is the only way to guarantee the repair prompt is at least as safe as the thing it's repairing.
- **Widening fields for `identity_contamination` (rather than trusting the caller's exact field list) is the safer default.** The detector's own definition of "still contaminated" scans a fixed field set; a narrower repair that doesn't cover it can look successful to a naive check while leaving the package flagged. Since the widening only ever unions (never narrows), a caller asking for more never gets less.
- **The regression guard (checking all three detector classes, not just the hinted one) is the single most important safety property added beyond a literal port of `runGatedAttempt`.** ADR-0047's worker never needed this because its deterministic edits (regex strips, retargeting) can't plausibly introduce an unrelated defect class. An LLM rewrite of five paragraphs of character narrative can. Without this guard, a "successful" identity-contamination fix could silently introduce a meta-text leak and still report `outcome: "fixed"`.

## Alternatives Considered

1. **Regenerate the entire character record from scratch on every repair call.** Rejected: throws away everything correct about the character (paid content the host has already seen, in the `needs_review` case) to fix one field, and multiplies cost and defect-reintroduction surface for no benefit — the whole point of a *field-scoped* repair is that most of the character is fine.
2. **Write a purpose-built, minimal repair prompt instead of mirroring the Child blueprint.** Rejected — see Rationale. A shorter, hand-rolled prompt is exactly the kind of change that could silently drop a guardrail (e.g. the SLIP-STYLE GUILT rule, or the accomplice-coherence rule) the live generator relies on, with no detector currently covering that specific omission.
3. **Skip the auto-expansion and require the caller to loop over every contributing character itself.** Rejected per the task brief's own framing: a naive loop reverts each character's fix in turn because the *others* are still broken, and can never converge without either widening the unit of repair (this ADR's approach) or the caller reimplementing the same detector-based discovery this function now does once, centrally.
4. **Skip the cross-class regression guard and only re-check the hinted class**, matching `auto-remediate-packages`'s literal `stillFlagged` more closely. Rejected: `auto-remediate-packages`'s edits are deterministic and structurally incapable of crossing defect classes; an LLM rewrite is not, and the task explicitly requires the fix to "never reintroduce the very defect it's fixing" — read broadly, that has to include defects of a *different* class than the one being targeted.
5. **Charge actual metered Anthropic token cost instead of a flat per-call estimate.** Deferred, not rejected: `auto-remediate-packages` already uses a flat estimate for its own Claude call, and matching that convention keeps the shared spend cap's accounting internally consistent. Precise metering is a reasonable follow-up if the flat estimate proves too far off in practice.

## Consequences

- The ADR-0053 gate's `meta_text_leak`, `slip_culprit_leak`, and `identity_conflict` HOLD classes now have a real, gated repair path available — they no longer strictly require a human. `victim_mismatch` was already handled by `regenerate-parent-content` (it's a parent-content field); this function's specific unlock is the *child*-content classes ADR-0053 named as unresolved.
- The ADR-0047 worker's two permanently-escalated classes (`identity_contamination`, `slip_culprit_leak`) now have a mechanical fix available to call — **wiring is deliberately deferred to a follow-on pass** (see Discussion). Until wired, the worker's behavior is unchanged: it still escalates both classes exactly as before.
- **Mirror-drift risk, carried forward from `regenerate-parent-content` and now doubled in surface.** This function's ~8 prompt fragments must be kept in sync with the live Child Make blueprint by hand. If the blueprint's G-rules change (a new guardrail, a reworded rule) and this file isn't updated to match, a repair could reintroduce a defect the live generator no longer produces, or fail a guardrail the generator has gained. No automated sync exists. The file header and this ADR are the only tripwires; a future pass should consider extracting the shared prompt fragments into one canonical source both the (eventual) live-generation path and this repair path read from, if and when the two need to change in lockstep often enough to justify it.
- **The per-character chat excerpts gap is permanent unless a future generation-time change persists them.** Repairs made via this function rely on `master_context` + established fields + the brainstorming conversation fallback instead. In practice this is very likely sufficient (the excerpts exist to seed *first* generation, and by repair time the character's established fields already encode whatever the excerpts contributed) but it is an honest, named gap rather than a silent one.
- New spend surface, but bounded by the *same* shared daily cap `auto-remediate-packages` already respects — the two functions cannot together exceed $5/day between them.
- `MAX_TARGET_CHARACTERS` (8) means a pathological package with more than 8 characters all implicated in the same defect instance will only partially repair in one call and report `truncated_targets: true` — call again to continue. This has not been observed in practice (typical casts are far smaller) and is a deliberate bound against a single call's blast radius, not a known gap.
- **Follow-up, not built here:** `remediation_write_field` cannot currently repair `relationships` when a character's existing value is `null` or a jsonb object (~7% of prod characters) — the 2026-08-02 write-loop fix makes that failure mode a clean, logged escalate instead of an unlogged partial write, but the underlying accessor still can't write that field in that state. Extending `remediation_write_field` (or this function's write path) to actually handle it is separate, deliberately out-of-scope follow-up work.
- Live end-to-end invocation of the deployed function could not be exercised from this session — the sandbox's network egress policy blocks direct calls to `*.supabase.co`. Verification here is: (a) `esbuild --bundle` (externals marked) parses cleanly, (b) `tsc --noEmit` reports zero type errors, (c) the Supabase deploy API accepted the function and reports `status: "ACTIVE"`. **A live smoke test (real `dry_run: true` call, then a real repair against a known-flagged package) is recommended before this function is wired into anything automated**, per the task's own "owner evals in a fresh tab" closing instruction.

## Discussion

The task explicitly scoped this pass to build-and-validate the primitive, *not* to wire it into the ADR-0053 gate's repair-in-loop or the ADR-0047 worker's escalate paths — "document the exact call contract... wiring is the next pass." That contract, concretely, for whoever does the wiring:

- **For the ADR-0047 worker**, replace `handleEscalateOnly` for `identity_contamination` and `slip_culprit_leak` with a `runGatedAttempt`-style plan whose `apply` calls `regenerate-child-content` with `{ package_id, character_id: <first claimant/leaker>, fields: <a reasonable default like the identity group + round scripts>, defect_class_hint: <the class> }` — note this function already does its *own* internal re-detect gate and auto-expansion, so the worker's wrapping call mainly needs to translate its `FixPlan.apply()`/`.revert()` shape around a function that already reverts internally on failure; the worker's outer gate becomes close to a no-op confirmation rather than a second independent check, which is fine (belt-and-suspenders, not redundant risk).
- **For the ADR-0053 gate's future repair-in-loop**, the natural call site is wherever a package would otherwise be left in `needs_review` for one of the four HOLD classes: call `regenerate-child-content` with the `structuredDefects` entry's character name(s) resolved to IDs and an appropriate `fields` list, then re-run `package_completion_blocking_defects` (or just trust this function's own `outcome`) before deciding whether to promote the package to `completed` or leave it in `needs_review`.
- **Why not wire it now:** the task brief was explicit, and independently this function's blast radius (mutates paid character content, spends money, and its correctness depends on ~8 hand-mirrored prompt fragments staying in sync with a live Make blueprint) is exactly the kind of surface ADR-0047's own build notes flagged as warranting an independent eval before running unattended. Building the primitive and its contract first, then wiring and eval'ing the integration as its own pass, follows the same discipline that ADR-0047's "deployed but not scheduled until eval'd" build did.

A secondary judgment call: whether `fields` widening for `identity_contamination` should have been left to the caller entirely (simpler contract) versus baked into the function (safer default, more surprising for a caller passing an exact field list expecting it to be honored exactly). Chose the safer default because the alternative — a caller reasonably assuming `fields: ["introduction"]` regenerates *only* `introduction` and being surprised when `round2_script` also changed — was judged less costly than the alternative failure mode (a caller under-specifying `fields`, the gate legitimately reporting `escalated` every time because the real contamination is sitting in a field never touched, and no error message pointing at why). The widening is unioned, not replaced, and is fully visible in the response's `fields_effective` versus `fields_requested`, so the surprise is at least inspectable.
