# ADR-0069: `approved_concept_message_id` never re-captures after a later substantive roster revision

- **Status:** Accepted
- **Date:** 2026-08-07 (proposed), 2026-08-11 (accepted + implemented)
- **Related:** ADR-0057 (select concept snapshot by parse, not header), ADR-0059 (send snapshot + everything after it as context), ADR-0068 (roster-annotation regex fix — this issue surfaced while sweeping for other packages hit by that bug)

## Context

Found while sweeping paid packages for other instances of ADR-0068's annotation-regex bug. "Death At The Blackthorn Wedding" (conversation `cd4ca44d-d3ac-46ea-8663-6811c98fe1fc`) showed a 12-vs-10 roster mismatch and initially looked like a second case of ADR-0068's bug — its roster lines use a `(Female)`/`(Male)` tag between name and dash (e.g. `**Lady Vivienne Blackthorn** (Female) — ...`), the same shape as Heather's `*(OPTIONAL PLAYER)*`. Confirmed: running the actual **deployed** (pre-ADR-0068) regex against this content produces 4 garbled entries with markdown fragments bleeding into the "names," and the ADR-0068-fixed regex correctly parses all 12 — so the fix generalizes as intended, beyond the literal wording it was written for.

But that's not what actually happened to this package. The full message history shows:

- **2026-07-22, 21:59** — customer approves a 12-player roster. `approved_concept_message_id` gets captured (once) pointing at this message.
- **2026-08-07, 17:30** — 16 days later, same conversation, customer explicitly says *"Change it to be ten players"* and receives a revised 10-player roster in the next (and final) message.
- **2026-08-07, 17:39–17:49** — package generates. `conversations.player_count` is 10 (correctly synced to the customer's final intent). But `approved_concept_message_id` still points at the **July 22** message — it never moved.

`extractCharactersFromMessages` extracts *only* from `approved_concept_message_id` when one is set (per ADR-0057's design — this is deliberate, not an oversight in itself). Against the stale July 22 content, the header-path regex garbled (per the ADR-0068 root cause, live in production), triggering the cross-validation Claude-fallback (`extractedCharacters.length(4) < playerCount(10) - 2`). That fallback concatenates **all** assistant messages containing `**` — every draft in the conversation, not just the approved one — and truncates to 8000 characters before sending to Claude. With ~38,000+ characters of draft history preceding the actual final revision, the true 10-player message likely never reached the model's context at all; the 10 characters that ended up in `mystery_characters` are the first 10 names of the **stale 12-player draft**, not the customer's actual final roster. The descriptions/talents she asked for in her final revision were not necessarily used.

Root cause, in `supabase/functions/mystery-webhook-trigger/index.ts`:

```ts
if (!conversation.approved_concept_message_id && conversation.messages) {
  const candidate = findLatestConceptMessage(conversation.messages as any[]);
  ...
}
```

The guard is `if (!conversation.approved_concept_message_id ...)` — capture happens **once**, the first time generation runs (or the chat-creation path runs) without a snapshot already set. Nothing re-evaluates whether a *later* message supersedes it. `player_count` has its own independent auto-sync (added separately, keyed off the extracted character count each generation run) which is why it correctly reflects "10" even though the snapshot content doesn't.

This is a different failure from anything ADR-0057/ADR-0059 addressed. ADR-0057 fixed *which* message gets chosen as the snapshot (parse-based, not header-based) — this is about *whether* the chosen snapshot ever gets replaced once a customer meaningfully changes their mind afterward. ADR-0059 widened context by sending the snapshot **plus everything after it** to Make.com's prose-generation prompts specifically *because* later refinements matter — but `extractCharactersFromMessages`'s roster extraction was deliberately scoped to the snapshot alone (again, correctly, per ADR-0057's own reasoning about not resurrecting superseded drafts) — the two mechanisms now disagree about which content is authoritative for structure (characters) versus content (prose), and a customer revision that changes the roster itself falls into the gap between them.

## Decision

**Accepted: implement candidate 1 (re-capture on roster-shape drift) as the primary fix, plus candidate 3 (fix the Claude-fallback's truncation order) as cheap complementary hardening. Candidate 2 (explicit client-side re-approval flow) is deferred — not implemented.**

Before deciding, ran the sweep the original write-up flagged as missing: for all 46 paid conversations with `approved_concept_message_id` set (as of 2026-08-11), used the SHIPPED `extractRosterFromMessage`/`findLatestConceptMessage` (esbuild-transpiled from the real source, same discipline as `scripts/__tests__/conceptSnapshot.test.mjs`) to check whether any later message independently parses into a roster with a different character count or <50% name overlap versus the current snapshot.

**Result: zero live cases.** Blackthorn Wedding (already manually repointed) was the only conversation in the dataset matching this exact shape. The other two known incidents this ADR's own investigation surfaced — Black Swan Society and Adelaide Crane, both already cited by name in the `ADR-0059` code comment as the motivating incidents for that fix — do **not** match this shape either: their later revisions changed setting, tone, and backstory prose, but never restated a formatted character list at all (`extractRosterFromMessage` returns 0 on their later messages). 15 of the 46 conversations have *some* assistant activity after their snapshot, but none of it independently re-parses into a differently-shaped roster.

This changed the decision from "which of these three roughly-equal options" to "these three options solve two different problems, and only one of them still has an open gap":

- **Candidate 1** (roster-shape re-capture) is exactly and only the Blackthorn Wedding shape. The sweep shows it's rare (1 confirmed instance to date) but real, cheap, deterministic, mirrors the already-trusted `player_count` auto-sync pattern, and — critically — is a **pure win with no plausible downside**: it only ever promotes the pointer to a message that itself passes the same clean-roster-parse bar the *original* snapshot capture used, so it can never regress a case that was already correct. Implemented.
- **Candidate 2** (explicit re-approval UX) is the only option that would have caught Black Swan Society / Adelaide Crane's prose-only drift, since it doesn't depend on a re-stated roster. But that class is already substantially covered going forward by `ADR-0059`'s `conversationContent` widening (snapshot + everything after, sent to Make.com's prose-generation prompts) — which shipped *because of* those two incidents. Building a full "re-confirm your cast" client flow is a materially larger project (new UI, new interaction, `MysteryChatCreator` changes) than the sweep's findings justify right now, and it's out of scope for a fix scoped to the edge function. Deferred as future work if a genuine roster-renaming-without-restated-list case is ever found in a future sweep.
- **Candidate 3** (fix Claude-fallback truncation order) is orthogonal to the snapshot-pointer problem but directly addresses a concrete failure mechanism from the Blackthorn Wedding writeup: `relevantContent.substring(0, 8000)` truncated by raw concatenation order, so ~38,000+ chars of earlier draft history could crowd out the actual final revision before it ever reached the fallback's context window. Cheap, deterministic (no LLM calls used to build the fix itself — only the fallback's own already-existing, already-authorized Claude call is affected), and strictly safer than the previous behavior. Implemented alongside candidate 1 as defense-in-depth: if the roster-shape re-capture (or a case it doesn't catch) ever routes through the Claude fallback, the fallback now can't silently amplify the same class of staleness bug.

## Implementation

- `supabase/functions/mystery-webhook-trigger/index.ts`:
  - New pure helper `rosterDiffersMeaningfully(snapshotRoster, latestRoster)` — count differs, or <50% name overlap. Placed in the same "pure prelude" region as `extractRosterFromMessage`/`findLatestConceptMessage` so it's covered by the esbuild-transpile test technique.
  - New block in the request handler, immediately after the existing capture-once block: if `approved_concept_message_id` is already set, re-derive `findLatestConceptMessage` against the full message list; if it points at a *different*, *later* message whose roster `rosterDiffersMeaningfully` from the current snapshot's, update `approved_concept_message_id` to the later message before generation reads it.
  - `extractCharactersWithClaude`: `relevantContent` is now built by walking eligible messages **newest-first** and accumulating into the 8000-char budget, dropping the oldest drafts first when the budget is exceeded, instead of head-truncating a naive oldest-first concatenation.
- `scripts/__tests__/conceptSnapshot.test.mjs`: 4 new checks — roster-shape drift is flagged (Blackthorn Wedding shape), cosmetic rewording of the same cast is not flagged, an end-to-end `findLatestConceptMessage` + `rosterDiffersMeaningfully` walkthrough of the actual Blackthorn Wedding timeline, and a Black-Swan-shape prose-only revision (no restated roster) correctly does NOT trigger a re-capture.

## Discussion

Found this by accident while trying to confirm ADR-0068's fix generalizes to a second real customer package — and it very nearly got misattributed as "another instance of the same bug" because the surface symptom (roster count mismatch, annotation pattern in the roster lines) looked identical. Re-running the *actual deployed* source against the content (rather than trusting a hand-reconstruction of "the old regex") is what surfaced the contradiction: the regex output was garbage, but the database held clean data that garbage couldn't have produced — meaning some other path was responsible, which led to finding the stale snapshot.

## Addendum 1 (2026-09-05): customer complaint on a paid order — a same-day regression in `isPlausibleRosterCount` (ADR-0118/3d6b694) reopened this exact gap via a different mechanism

Customer (Raegen Schott, "Murder At The Golden Feather Awards," conversation `97115032-8948-4810-a8ca-3a09c9a30ea1`) emailed: she'd confirmed removing "Monty/Mona Magpie" from her roster twice in chat before purchasing (24→22 characters over several days, then 22→21 the same evening she paid), but her delivered package still had 22 characters including Mona Magpie. This is the exact ADR-0069 shape this ADR already fixed — so first question was whether the `rosterDiffersMeaningfully` re-capture logic itself had regressed.

**It hadn't — a standalone node harness (real message content, zero Anthropic spend, same technique as ADR-0118) proved the re-capture logic works perfectly against this exact conversation.** `findLatestConceptMessage` correctly identifies the customer's final 21-person message as the latest roster-bearing message, correctly detects it differs from the stale 22-person snapshot, and would correctly re-capture — **when tested with `conversation.player_count = 22`.**

**The actual bug: `player_count` was very likely still 24 (the customer's original selection) at the moment generation ran, not 22.** `player_count` is a "form-captured" value (per this file's own `[PlayerCount] Drift detected: form=...` log message) — it is never updated by natural-language chat edits like "get rid of the magpie," only by an explicit form control or the post-generation auto-sync that keys off the *extracted* count. The customer's 24→22→21 reductions all happened purely in chat text; nothing in this flow updates `player_count` until after a generation runs. Re-running the same harness with `player_count = 24` reproduces the exact failure: `isPlausibleRosterCount(21, 24)` evaluates `21 >= 24-2` as false, so both of the customer's final 21-person messages get rejected as "implausible," `findLatestConceptMessage` falls back to the last *plausible* match — which is the stale 22-person snapshot itself — the re-capture condition (`latestConceptMsg.id !== currentSnapshotMsg.id`) never fires, and generation proceeds against the stale snapshot. Confirmed the closing link in the chain: the post-generation auto-sync then set `player_count` to 22 (matching what was actually extracted), which is why the DB showed 22 going into this investigation and made "player_count was already 22" look like the natural default assumption — it wasn't, at the moment that mattered.

**This is a same-day regression, not a recurrence of the original gap.** `isPlausibleRosterCount` was added *today* (commit `3d6b694`, deployed as `mystery-webhook-trigger` v134, ~17:43 UTC) specifically to stop a *different* failure — a later reply that merely *looks* like a roster (e.g. "4 murder-method direction options") false-matching and overwriting a real snapshot (see ADR-0118 Addendum 1). That fix is doing its job for the case it targeted. But it introduced a new failure mode for a case ADR-0069 had already solved: a customer who legitimately shrinks their roster by more than the tolerance window (`playerCount - 2`) via chat, while `player_count` itself hasn't caught up. The two fixes are now in tension — `rosterDiffersMeaningfully`'s count-and-overlap check would correctly distinguish a real 22→21 edit from a fake "4 direction options" match on its own, but it never gets the chance because `isPlausibleRosterCount` filters the real candidate out first.

**Fixed this customer's package directly, not via the buggy pipeline.** Removing a character post-generation while preserving everything else (murderer identity included, per the customer's explicit request) is exactly what the paid "Remove a Character" adaptation pipeline (`adapt-mystery-apply`, ADR-0088) already does safely — used it as a $0, pre-`paid` single-row batch (same pattern as this project's established free-hand-fix convention), since this was our bug, not a billable customer request. Outcome: `verified`, zero `touched_characters` needing review (Mona Magpie wasn't cross-referenced by name elsewhere), one field polished by the pipeline's own LLM pass (the "22 distinguished birds" framing → 21). Verified after: 21 `mystery_characters` rows, `conversations.player_count` auto-corrected to 21, no residual "Mona"/"Magpie"/"22" references anywhere in `game_overview` or `detective_script`, all 3 standard detectors and `package_completion_blocking_defects()` clean.

**Exposure checked, not exhaustively swept.** Only 3 packages have generated since the 3d6b694 deploy (~17:43 UTC 2026-09-04) as of this writing: Golden Feather Awards (confirmed exposed, fixed above), "Lethal Mutations: Death At The Helix Institute" (checked — no late roster-count-changing chat message exists in its transcript, so this specific failure mode never had an opportunity to trigger), and "Dirty Martini, Deadly Party: Faith's Last Birthday Bash" (checked — same, roster was finalized at 4 before the approved snapshot and never revised afterward; incidentally this package generated *after* ADR-0103 Addendum 20's `v37` blueprint import and shows a clean, in-voice "no enemies" section for one of its 4 characters, an early positive data point for that separate fix). No corpus-wide backward sweep was run for older paid packages, since this specific regression can only have existed since today's 3d6b694 deploy — there's no older backlog to check.

**Not fixed — a real design trade-off, not something to decide solo.** `isPlausibleRosterCount`'s tolerance window is the only thing standing between two failure modes this project has now hit on the same day: too narrow, and a legitimate large roster reduction gets rejected (this incident); too wide, and a fake structural match (ADR-0118's original bug) gets accepted. Candidate directions, not yet chosen between:
1. **Widen the tolerance window** (e.g. a larger floor than `playerCount - 2`) — simplest, but purely numeric and doesn't address the actual root cause (a stale reference value), just shrinks the window where it bites.
2. **Scope `isPlausibleRosterCount` out of the re-capture path specifically**, relying on `rosterDiffersMeaningfully`'s own count-and-overlap heuristic there — risks reintroducing ADR-0118's original bug for the re-capture path specifically (a fake structural match after the real snapshot would also "differ meaningfully" and could get re-captured), needs careful thought about whether the two failure shapes are actually distinguishable some other way (e.g. requiring the re-capture candidate to *also* look like real character content, not just the right shape).
3. **Keep `player_count` itself live during the conversation** — apply something like `rosterDiffersMeaningfully` to `player_count` too, updating it whenever a later roster-bearing message parses to a meaningfully different count, *before* generation, not just after. Addresses the actual root cause (the reference value being stale at decision time) rather than working around a stale reference. Bigger change, touches a value multiple systems key off, needs more validation before shipping.

## Addendum 2 (2026-09-05, same day): fixed — a fourth option none of the above three, deployed and verified

Jonathan asked to tackle the regression head-on rather than leave it open. Re-reading ADR-0118's own incident write-up (the exact false-positive `isPlausibleRosterCount` was built to stop) surfaced a discriminating signal none of Addendum 1's three candidates used: **the fake "roster" that caused ADR-0118's original bug embeds real character surnames inside unrelated phrases** ("Holloway's Compound," "Ashgrave's Old Craft" — a murder-method-options list, not a cast) but shares **zero exact character names** with the real roster. A legitimate revision like Mona Magpie's removal shares **95% of its names** (21 of 22) with the snapshot it's revising. Name overlap against the *current snapshot* — not count plausibility against a possibly-stale `player_count` — is what actually distinguishes "customer revised their existing cast" from "AI wrote something else that happens to parse the same way."

**The fix: `isPlausibleRosterCandidate(candidateRoster, playerCount, referenceRoster?)`.** A candidate is trusted if *either* `isPlausibleRosterCount` passes (unchanged, still the sole signal wherever no reference roster exists — first-capture, the Claude-fallback budget guarantee) *or* it shares ≥50% of its names (normalized, exact match — not substring, so "Holloway's Compound" does not credit-match "Dr. Victor Holloway") with a supplied reference roster. `findLatestConceptMessage` now takes an optional `referenceRoster` parameter; the re-capture block (the only site that has a trustworthy prior roster to compare against — the current snapshot itself) passes it. The extraction-acceptance check (`extractCharactersFromMessages`, reading whatever `approved_concept_message_id` already points to) had its `isPlausibleRosterCount` gate **removed entirely**, reverting to its pre-3d6b694 behavior: once the capture/re-capture logic has chosen a pointer — now hardened with the overlap signal — re-litigating that choice downstream with a blunter, staler signal only reintroduces the same failure one step later (confirmed this would otherwise still reject Golden Feather's correctly-re-pointed message, since `player_count` is fixed by the snapshot pointer being right, not by this second check).

**Verified against both real incidents before deploying**, via a standalone node harness (real message content reconstructed from each incident's own ADR write-up, zero Anthropic spend, same technique used throughout ADR-0118/ADR-0103):
- Golden Feather Awards, `player_count` still 24 (the regression's exact trigger): `findLatestConceptMessage` now correctly returns the customer's true 21-person message (overlap with snapshot: 0.955).
- Hollingsworth Estate's original false positive, reconstructed from ADR-0118's own transcript excerpts: the 5-item murder-method-options fake match is still correctly rejected (overlap: 0.0) — the fix everyone already relied on keeps working.

**Added 3 new permanent regression tests** to `scripts/__tests__/conceptSnapshot.test.mjs` (both incident shapes, plus a direct `isPlausibleRosterCandidate` unit check) — full suite now 20/20 passing, up from 17.

**Deployed `mystery-webhook-trigger` v135** via the Supabase CLI directly from the local file (`supabase functions deploy mystery-webhook-trigger --no-verify-jwt`) rather than retyping ~1,500 lines into a tool call — pulled the deployed source back afterward and diffed byte-for-byte against local: identical. `verify_jwt: false` confirmed preserved (this function's payment-gate logic depends on it staying disabled — see the function's own header comment).

**Not yet validated against a real purchase carrying this exact shape** (a large chat-only roster reduction after `player_count` has gone stale) — the 20-test suite and the two incident reconstructions are the confidence this ships on. Worth an explicit check on the next `sweep` that hits a large late roster edit, same spirit as the Addendum 20 (ADR-0103) `v37` validation note.

## Addendum 3 (2026-10-01): the `has_accomplice` auto-sync this ADR's own fix added was silently dropped by a later migration — live broken for 3 weeks, found while closing out an unrelated package

While confirming "Emma's Honky Tonk: A Meow-der Mystery" (package `1b44560c-5e95-4d8a-93d8-6fa682e074d7`, ADR-0103 Addendum 65/66) was fully clean, its `conversations.has_accomplice` still read `true` after its 4 wrongly-tagged `accomplice` characters had already been corrected to 0 and the package had gone through a real `needs_review` → `completed` transition — exactly the transition `validate_package_characters()`'s has_accomplice sync (migration `20260905183501_sync_has_accomplice_from_actual_characters.sql`) is supposed to catch.

**Checked the live database directly rather than trusting the repo file** — `pg_get_functiondef()` on the deployed `validate_package_characters()` showed no `_has_accomplice_actual` variable and no `UPDATE conversations` block at all. Migration `20260908074900_stamp_generation_completed_at_on_validated_completion.sql` (2026-09-08, three days after the sync was added, ADR-0103 Addendum 30's follow-up) redefined the function with `CREATE OR REPLACE` from a base that predated the sync block, and the function it deployed simply never had it — classic paired-predicate-drift via silent base-version loss, not a merge conflict or a reverted commit anyone would have seen flagged.

**Confirmed live-broken 2026-09-08 through 2026-10-01 (~3 weeks):** every package that completed in that window never had `has_accomplice` auto-corrected at completion, regardless of what the customer actually decided via chat.

**Fixed:**
1. Restored the sync block into the current (correct) version of the function — preserving the `generation_completed_at` stamping logic `20260908074900` added, not reverting that migration, just re-adding what it accidentally dropped. Migration `20261001000000_restore_has_accomplice_sync_dropped_by_completed_at_stamp.sql`.
2. Confirmed restored: `pg_get_functiondef()` now shows the sync block present.
3. Fixed Emma's Honky Tonk directly (`has_accomplice → false`) — an already-completed package won't retroactively benefit from the trigger fix.
4. **Corpus-checked the actual blast radius** rather than assuming it was limited to the one package found by chance: every `mystery_style='detective'` package completed since 2026-09-08 with a genuine `has_accomplice`/`character_role` mismatch in either direction (the original shape this sync exists to catch). Zero other live instances — Emma's Honky Tonk was the only real-world case the 3-week outage actually affected, even though the theoretical exposure was every detective-style completion in that window.

**Lesson, consistent with this codebase's established "migration list isn't reliable, verify live state" practice** (see `supabase migration list` section of `CLAUDE.md`): a `CREATE OR REPLACE FUNCTION` migration that doesn't diff against the *currently live* function body before writing its new version can silently drop logic a completely unrelated, intervening migration added — even when that intervening migration is itself correctly applied and well-documented. The fix for *this* instance is applied; the general risk (another future `CREATE OR REPLACE` on this same function dropping this same block again) isn't structurally closed by this addendum — flagged for awareness, not solved.

## Addendum 4 (2026-10-04): the Addendum 3 restore made slip-style packages lose `has_accomplice` — the Host Guide told hosts to draw only a MURDERER slip

**Trigger:** a customer email from the Hedberg Hollow purchase (slip style, 16 characters, conversation `07864eb8-06b5-4538-a4a5-10814df22563`): "I see in the instructions that after round one we will determine the murderer by picking slips but it doesn't say to do the same with the accomplice. And wouldn't the accomplice have to be an ally of the murderer?"

**Root cause:** the `has_accomplice` sync that Addendum 3 restored sets the flag to "does any `mystery_characters` row have `character_role = 'accomplice'`". That is right for detective style (Make pre-assigns roles) and always false for `mystery_style = 'character'`, where the murderer and accomplice are drawn at the table and no role is ever written. So every slip-style completion since the restore on 2026-10-01 had the customer's real request overwritten with false. `HostGuideTemplate.tsx` (and the character-packet guide copy via `get_packet_metadata_by_token`) pick their slip-draw wording from that flag: with false, the guide prepares and explains a MURDERER slip only, while all 16 characters still carry full accomplice branches and `detective_script` still calls the accomplice up at the reveal. The customer asked for "an accomplice mechanism" in the first chat message. Addendum 3's corpus check covered only `mystery_style = 'detective'` and so could not see this; the sync was also briefly live 2026-09-05 to 2026-09-08 before `20260908074900` dropped it.

**Blast radius (checked, not assumed):** slip-style paid packages with `has_accomplice = false` where the customer's messages ask for an accomplice (and no "do not include") or the characters carry accomplice branches: Hedberg Hollow (10-03), Boogie Nights, Bloody Nights (10-03), El Último Brindis De Laia (10-02, Spanish, "Incluir un mecanismo de cómplice"), The Gods Must Be Gossiping / Aphrodite's Birthday Bash (09-08). Last slip-style `has_accomplice = true` package before the restore: 2026-09-27. "Do not include an accomplice" packages (Feast For The Dying etc.) are correctly false and untouched.

**Fixed:**
1. Migration `20261004000000_has_accomplice_sync_skip_slip_style.sql`: the sync block in `validate_package_characters()` only runs when `NEW.mystery_style IS DISTINCT FROM 'character'`. Applied via the Supabase MCP and confirmed live with `pg_get_functiondef` (the function was diffed against the repo file first; identical apart from this guard).
2. The four affected conversations set back to `has_accomplice = true` (the guide is rendered live from the flag, so the Host Guide and character packets now show the accomplice slip text with no regeneration).

**Customer's second question (is the accomplice an ally of the murderer?):** by design the slip-style accomplice scripts are ally-agnostic. They are written around "someone I love / someone I've known for years" and protect whichever player drew MURDERER, because who that is cannot be known when the package is generated. No content change.

**Not done / deliberately left:** no new detector. The signal (what the customer asked for in free-text chat) is not cleanly checkable in SQL; the failure is closed at its source instead. The general risk that a later `CREATE OR REPLACE` drops this block again is still not structurally closed, same as Addendum 3.
