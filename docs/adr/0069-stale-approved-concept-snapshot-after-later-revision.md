# ADR-0069: `approved_concept_message_id` never re-captures after a later substantive roster revision

- **Status:** Accepted
- **Date:** 2026-08-07 (proposed), 2026-08-11 (accepted + implemented)
- **Related:** ADR-0057 (select concept snapshot by parse, not header), ADR-0059 (send snapshot + everything after it as context), ADR-0068 (roster-annotation regex fix — this issue surfaced while sweeping for other packages hit by that bug)

## Context

Found while sweeping paid packages for other instances of ADR-0068's annotation-regex bug. "Death At The Blackthorn Wedding" (conversation `cd4ca44d-d3ac-46ea-8663-6811c98fe1fc`) showed a 12-vs-10 roster mismatch and initially looked like a second case of ADR-0068's bug — its roster lines use a `(Female)`/`(Male)` tag between name and dash (e.g. `**Lady Vivienne Blackthorn** (Female) — ...`), the same shape as Heather's `*(OPTIONAL PLAYER)*`. Confirmed: running the actual **deployed** (pre-ADR-0068) regex against this content produces 4 garbled entries with markdown fragments bleeding into the "names," and the ADR-0068-fixed regex correctly parses all 12 — so the fix generalizes as intended, beyond the literal wording it was written for.

But that's not what actually happened to this package. The full message history shows:

- **2026-07-22, 21:59** — customer approves a 12-player roster. `approved_concept_message_id` gets captured (once) pointing at this message.
- **2026-08-07, 17:30** — 16 days later, same conversation, customer explicitly says *"Change it to be ten players"* and receives a revised 10-player roster in the next (and final) message.
- **2026-08-07, 17:39–17:49** — package generates. `conversations.player_count` is 10 (correctly synced to the customer's final intent). But `approved_concept_message_id` still points at the **July 22** message — it never moved.

`extractCharactersFromMessages` extracts *only* from `approved_concept_message_id` when one is set (per ADR-0057's design — this is deliberate, not an oversight in itself). Against the stale July 22 content, the header-path regex garbled (per the ADR-0068 root cause, live in production), triggering the cross-validation Claude-fallback (`extractedCharacters.length(4) < playerCount(10) - 2`). That fallback concatenates **all** assistant messages containing `**` — every draft in the conversation, not just the approved one — and truncates to 8000 characters before sending to Claude. With ~38,000+ characters of draft history preceding the actual final revision, the true 10-player message likely never reached the model's context at all; the 10 characters that ended up in `mystery_characters` are the first 10 names of the **stale 12-player draft**, not the customer's actual final roster. The descriptions/talents she asked for in her final revision were not necessarily used.

Root cause, in `supabase/functions/mystery-webhook-trigger/index.ts`:

```ts
if (!conversation.approved_concept_message_id && conversation.messages) {
  const candidate = findLatestConceptMessage(conversation.messages as any[]);
  ...
}
```

The guard is `if (!conversation.approved_concept_message_id ...)` — capture happens **once**, the first time generation runs (or the chat-creation path runs) without a snapshot already set. Nothing re-evaluates whether a *later* message supersedes it. `player_count` has its own independent auto-sync (added separately, keyed off the extracted character count each generation run) which is why it correctly reflects "10" even though the snapshot content doesn't.

This is a different failure from anything ADR-0057/ADR-0059 addressed. ADR-0057 fixed *which* message gets chosen as the snapshot (parse-based, not header-based) — this is about *whether* the chosen snapshot ever gets replaced once a customer meaningfully changes their mind afterward. ADR-0059 widened context by sending the snapshot **plus everything after it** to Make.com's prose-generation prompts specifically *because* later refinements matter — but `extractCharactersFromMessages`'s roster extraction was deliberately scoped to the snapshot alone (again, correctly, per ADR-0057's own reasoning about not resurrecting superseded drafts) — the two mechanisms now disagree about which content is authoritative for structure (characters) versus content (prose), and a customer revision that changes the roster itself falls into the gap between them.

## Decision

**Accepted: implement candidate 1 (re-capture on roster-shape drift) as the primary fix, plus candidate 3 (fix the Claude-fallback's truncation order) as cheap complementary hardening. Candidate 2 (explicit client-side re-approval flow) is deferred — not implemented.**

Before deciding, ran the sweep the original write-up flagged as missing: for all 46 paid conversations with `approved_concept_message_id` set (as of 2026-08-11), used the SHIPPED `extractRosterFromMessage`/`findLatestConceptMessage` (esbuild-transpiled from the real source, same discipline as `scripts/__tests__/conceptSnapshot.test.mjs`) to check whether any later message independently parses into a roster with a different character count or <50% name overlap versus the current snapshot.

**Result: zero live cases.** Blackthorn Wedding (already manually repointed) was the only conversation in the dataset matching this exact shape. The other two known incidents this ADR's own investigation surfaced — Black Swan Society and Adelaide Crane, both already cited by name in the `ADR-0059` code comment as the motivating incidents for that fix — do **not** match this shape either: their later revisions changed setting, tone, and backstory prose, but never restated a formatted character list at all (`extractRosterFromMessage` returns 0 on their later messages). 15 of the 46 conversations have *some* assistant activity after their snapshot, but none of it independently re-parses into a differently-shaped roster.

This changed the decision from "which of these three roughly-equal options" to "these three options solve two different problems, and only one of them still has an open gap":

- **Candidate 1** (roster-shape re-capture) is exactly and only the Blackthorn Wedding shape. The sweep shows it's rare (1 confirmed instance to date) but real, cheap, deterministic, mirrors the already-trusted `player_count` auto-sync pattern, and — critically — is a **pure win with no plausible downside**: it only ever promotes the pointer to a message that itself passes the same clean-roster-parse bar the *original* snapshot capture used, so it can never regress a case that was already correct. Implemented.
- **Candidate 2** (explicit re-approval UX) is the only option that would have caught Black Swan Society / Adelaide Crane's prose-only drift, since it doesn't depend on a re-stated roster. But that class is already substantially covered going forward by `ADR-0059`'s `conversationContent` widening (snapshot + everything after, sent to Make.com's prose-generation prompts) — which shipped *because of* those two incidents. Building a full "re-confirm your cast" client flow is a materially larger project (new UI, new interaction, `MysteryChatCreator` changes) than the sweep's findings justify right now, and it's out of scope for a fix scoped to the edge function. Deferred as future work if a genuine roster-renaming-without-restated-list case is ever found in a future sweep.
- **Candidate 3** (fix Claude-fallback truncation order) is orthogonal to the snapshot-pointer problem but directly addresses a concrete failure mechanism from the Blackthorn Wedding writeup: `relevantContent.substring(0, 8000)` truncated by raw concatenation order, so ~38,000+ chars of earlier draft history could crowd out the actual final revision before it ever reached the fallback's context window. Cheap, deterministic (no LLM calls used to build the fix itself — only the fallback's own already-existing, already-authorized Claude call is affected), and strictly safer than the previous behavior. Implemented alongside candidate 1 as defense-in-depth: if the roster-shape re-capture (or a case it doesn't catch) ever routes through the Claude fallback, the fallback now can't silently amplify the same class of staleness bug.

## Implementation

- `supabase/functions/mystery-webhook-trigger/index.ts`:
  - New pure helper `rosterDiffersMeaningfully(snapshotRoster, latestRoster)` — count differs, or <50% name overlap. Placed in the same "pure prelude" region as `extractRosterFromMessage`/`findLatestConceptMessage` so it's covered by the esbuild-transpile test technique.
  - New block in the request handler, immediately after the existing capture-once block: if `approved_concept_message_id` is already set, re-derive `findLatestConceptMessage` against the full message list; if it points at a *different*, *later* message whose roster `rosterDiffersMeaningfully` from the current snapshot's, update `approved_concept_message_id` to the later message before generation reads it.
  - `extractCharactersWithClaude`: `relevantContent` is now built by walking eligible messages **newest-first** and accumulating into the 8000-char budget, dropping the oldest drafts first when the budget is exceeded, instead of head-truncating a naive oldest-first concatenation.
- `scripts/__tests__/conceptSnapshot.test.mjs`: 4 new checks — roster-shape drift is flagged (Blackthorn Wedding shape), cosmetic rewording of the same cast is not flagged, an end-to-end `findLatestConceptMessage` + `rosterDiffersMeaningfully` walkthrough of the actual Blackthorn Wedding timeline, and a Black-Swan-shape prose-only revision (no restated roster) correctly does NOT trigger a re-capture.

## Consequences

- **CORRECTION (same day, after deeper verification): this specific customer's delivered content is actually correct.** The initial write-up above assumed the wrong-snapshot theory meant her delivered package reflected the stale July 22 draft. Directly reading her actual `mystery_characters` rows disproved that: all 10 names match her true final revision, talents are naturally woven into descriptions (not the old explicit "TALENT:" labels from the stale draft, which she'd explicitly asked to be removed), Cedric's "bitter grudge" detail (present only in her final message) is in his background, Rosalind's specific legal-knowledge framing is there, and the murder method (Bell Tower railing sabotage, Marlowe as killer, Sinclair as accomplice) matches her final approved version exactly. Even `mystery_packages.extracted_characters` — nominally the edge function's regex-derived seed — holds the clean, correct 10-name set, not the garbled 4-entry result a hand-test of the deployed regex against the stale snapshot produces in isolation.
- **The exact mechanism reconciling this is not fully understood.** Best working theory: Make.com's prose-generation steps (master_context, detective_script, and evidently whatever writes `extracted_characters` back) draw on the wider `conversationContent` (snapshot + everything after, per ADR-0059) rather than trusting the edge function's narrow regex-seeded `extractedCharacters` array in isolation, so the correct final content won out despite the stale pointer. Not verified against the actual Make.com blueprint logic (only partially mirrored in this repo's `temp-files/*.blueprint.json` exports) — worth confirming if this pattern is relied on again.
- **Remediation for this customer: pointer only.** `conversations.approved_concept_message_id` for `cd4ca44d-...` has been corrected to point at her actual final message (`8e30ddb2-...`) so the DB record is honest — no content was rewritten, none was needed.
- **RESOLVED (2026-08-11): the architectural gap is now fixed for the roster-shape drift class.** See Decision/Implementation above — `rosterDiffersMeaningfully` + the re-capture block close the gap this instance exposed. The gap for *prose-only* drift (Black Swan Society / Adelaide Crane shape, no restated roster) is not closed by this change; see Decision for why that's an accepted, reasoned deferral rather than an oversight.
- **Scope swept (2026-08-11): zero other live instances of this exact shape.** Ran the deterministic sweep against all 46 paid conversations with a snapshot set, using the shipped `extractRosterFromMessage`/`findLatestConceptMessage` (esbuild-transpiled from real source). Blackthorn Wedding (already manually repointed) was the only match. 15 of the 46 have later assistant activity after their snapshot, but none of it independently re-parses into a differently-shaped roster — so this was not a symptom of a widespread bug at the time of the sweep, though the fix now prevents it going forward regardless of frequency. A separate, untracked local audit (`2026-08-02-stale-concept-audit.md`, from a parallel session, semantic/manual rather than parser-based) flagged Black Swan Society and Adelaide Crane as "MISMATCH" using a broader read-the-full-conversation method — those are real, but per the Decision above they're the prose-drift class ADR-0059 already targets, not this ADR's roster-shape class; **their delivered content has not been re-verified in this pass** and remains a candidate for a follow-up if Jonathan wants those two customer packages specifically checked.
- **Independent of ADR-0068.** Deploying the ADR-0068 regex fix does not resolve the pointer-staleness gap itself, though it may reduce how often the regex-garble → Claude-fallback detour triggers in the first place.

- `scripts/__tests__/conceptSnapshot.test.mjs` — 4 new ADR-0069 regression checks
- Pointer corrected, content verified already-correct, no rewrite needed: `conversations`/`mystery_characters` for conversation `cd4ca44d-d3ac-46ea-8663-6811c98fe1fc`

## Discussion

Found this by accident while trying to confirm ADR-0068's fix generalizes to a second real customer package — and it very nearly got misattributed as "another instance of the same bug" because the surface symptom (roster count mismatch, annotation pattern in the roster lines) looked identical. Re-running the *actual deployed* source against the content (rather than trusting a hand-reconstruction of "the old regex") is what surfaced the contradiction: the regex output was garbage, but the database held clean data that garbage couldn't have produced — meaning some other path was responsible, which led to finding the stale snapshot.

Then the write-up made the same category of mistake again, one level up: it assumed "wrong snapshot pointer" necessarily meant "wrong delivered content" without actually reading the delivered content to check. It didn't — the prose-generation pipeline's wider context window apparently compensated. The lesson compounds: verify the *actual output* a customer received, not just the mechanism that theoretically produced it, at every layer of an investigation like this — a plausible causal chain is not the same as a confirmed one.
