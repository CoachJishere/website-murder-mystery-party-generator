# ADR-0052: Make an invalid character_role impossible to persist as delivered content

- **Status:** Accepted
- **Date:** 2026-08-01

## Context

ADR-0051 (shift-left generation integrity) named `character_role` as layer 1: "Structural DB constraints — make the worst classes impossible to persist. `character_role` as an enum/CHECK (a 502 body can't be stored as a role — the write rejects and the pipeline retries); the ADR-0050 double-encoding trigger is the template." This ADR is that layer, executed.

The gap it closes: ADR-0049 added `package_completion_blocking_defects()` and wired it into `validate_package_characters()`, `heal_completed_packages()`, and `promote_complete_packages()` — a **pre-completion gate** that catches an invalid `character_role` and downgrades the package to `needs_review` before it can reach `completed`. That gate works and is verified (ADR-0049's own Verification section). But it only fires at the completion boundary. Between a bad write landing and that boundary being crossed — which can be minutes, for a multi-character package generating in parallel routes — the raw garbage sits in the `character_role` column itself, as delivered content, readable by anything that queries the row directly (the character-access page, the two recovery crons' own intermediate reads, any future consumer). The gate prevents a *bad package* from being marked `completed`; it does not prevent a *bad value* from being stored at all. This ADR is the latter.

`character_role`, per `src/interfaces/mystery.ts` and the four values `package_completion_blocking_defects()` already treats as the closed vocabulary, must only ever be one of `murderer`, `accomplice`, `suspect`, `redHerring` — or `NULL` (legitimate for character-style/random-slip games that leave it unset per that function's own comment).

### The write path, traced live

Generation writes `mystery_characters` exclusively through Make.com scenario `9061052` ("MM Live - Child (Unified) v19"), via `supabase:upsertARecord` modules — ids `404, 408, 412, 504, 508, 512, 516, 520`, one per character slot across the scenario's two routes (confirmed by walking the live blueprint backup, `temp-files/MM Live - Child (Unified)19-SlipGuilt-OutputHygiene-VictimQuestions.blueprint.json`, the same file ADR-0049 traced for the root-cause chain). Every one of those eight modules has **no `onerror` key at all** in the blueprint — not even the empty array the upstream `createAMessage` modules have (`"onerror": []`). The scenario's own metadata block sets `"dlq": true` and `"maxErrors": 5`, with no auto-resume directive attached to these modules.

Make's documented behavior for a module error with no error handler attached is to stop the entire scenario execution at that bundle and file it as an incomplete execution in the Dead Letter Queue for manual review/resume — not to skip forward and continue the run, and not to retry automatically.

## Decision

**COERCE, not REJECT.** A `BEFORE INSERT OR UPDATE` trigger on `mystery_characters`, extending the table's *existing* normalize trigger (`normalize_character_data_trigger` / `normalize_character_data()`, which already shape-fixes `relationships`/`secrets` on write) rather than adding a second trigger. Any non-`NULL` `character_role` outside the four-value enum is coerced to the sentinel string `'invalid_role'` before storage. `NULL` passes through unchanged (still legitimate).

The sentinel — not `NULL` — is the second half of the decision: coercing to `NULL` would make a scrubbed 502 body indistinguishable from the "role intentionally left unset" case that `package_completion_blocking_defects()` explicitly carves out as legitimate. `'invalid_role'` is deliberately non-`NULL` and outside the enum, so it trips that function's *existing* `invalid_role` branch on its own terms — no changes needed to ADR-0049's gate at all. That function is already called, unconditionally, from all three completion-setting paths: `validate_package_characters()` (folds it into the same `needs_review` downgrade + notify machinery), and both `heal_completed_packages()` / `promote_complete_packages()` (`AND public.package_completion_blocking_defects(mp) IS NULL` in their `WHERE` clauses). The sentinel routes into exactly the retry/hold flow ADR-0049 already built and verified for this failure mode.

Migration: `supabase/migrations/20260801_normalize_character_role_on_write.sql`.

## Rationale

- **REJECT was the natural first instinct — and ADR-0051 named it as the example — but tracing the live write path rules it out.** No error handler exists anywhere in the eight character-write modules of the revenue-critical child scenario. A hard `CHECK` constraint on `character_role` would turn a future 502-body write into a Postgres error on `upsertARecord`, which Make has no handler for, which stops the whole scenario execution and DLQ-parks it. That is a strictly worse outcome for that generation run than today's bug (which at least completes, just wrong): a customer's mystery would go from "quietly ships one bad field, caught before `completed` by ADR-0049's gate" to "generation run dies mid-flight, requires manual DLQ resume, likely leaves *other* characters in that route unwritten too." A prevention mechanism that makes the failure mode worse for the exact incident it's meant to prevent is not the safer choice, appearances (the word "constraint" sounding stricter than "trigger") notwithstanding.
- **This directly mirrors ADR-0050's precedent on the same table family, one migration earlier the same day.** ADR-0050 rejected a hard `CHECK` on `generation_status` for the identical reason — Make.com would keep sending the bad pattern, and a hard reject "would break every live generation until the scenario is redesigned." The same logic applies here with, if anything, more force: `generation_status` writes happen for every package on every progress tick; `character_role` writes happen once per character but are the exact site of two real production incidents (Velvet Viper, Coronation) that already cost paying customers correct delivery once each.
- **Coerce to a sentinel, not `NULL`, specifically because the codebase already documents `NULL` as legitimate for this column.** `package_completion_blocking_defects()`'s own comment reads: "NULL is legitimate (character-style/random-slip games leave it unset) — only flag a non-NULL value that isn't one of the four known roles." Reusing `NULL` as the coercion target would have been building this migration's safety net directly on top of a documented carve-out in the very function meant to catch it — fragile today, actively wrong if that carve-out is ever tightened or removed independently of this change. The two recovery crons' own ad-hoc `character_role IS NULL` checks happen to also catch a `NULL` coercion today, but relying on that coincidence rather than the purpose-built `invalid_role` mechanism is exactly the kind of "two things that are semantically the same event, encoded differently, silently invisible to each other's tooling" drift ADR-0048/0049 already flagged as a recurring failure pattern in this codebase.
- **Extending the existing normalize trigger, not adding a new one.** `mystery_characters` already has `normalize_character_data_trigger` doing exactly this class of job (clean up a Make.com write's shape before it lands) for `relationships` and `secrets`. There is no other same-table `BEFORE` trigger that reads `character_role`, so there's no ordering hazard to manage the way ADR-0050 had to solve with its `trg_00_` naming convention — one trigger, minimal surface area, matching ADR-0050's own stated preference for reuse over addition.
- **Historical data reconciled, not left broken.** 21 existing rows (2 packages, both paid and `completed` 2026-04-22) held the legacy uppercase vocabulary (`MURDERER`/`GUILTY`/`ACCOMPLICE`/`INNOCENT`) — already known from ADR-0049's own verification pass, and re-confirmed live immediately before writing this migration (zero rows held an HTML/502 body; both known incidents were already hand-repaired, per ADR-0049). Because this is a trigger, not a table-wide `CHECK` (which validates every existing row at `ADD CONSTRAINT` time and would have required this cleanup as a hard precondition), reconciling old data wasn't strictly required for the fix to apply. It was done anyway because it's a real, low-risk, customer-facing bug fix in its own right: `src/pages/CharacterAccess.tsx`'s role banner only renders on an exact lowercase match against `murderer`/`accomplice`, so all 21 rows currently show no banner at all for characters whose role was already known unambiguously (each of the two packages has exactly one `MURDERER`/`GUILTY` row — the culprit, by construction of a single-murderer mystery). Mapped `MURDERER`/`GUILTY` → `murderer`, `ACCOMPLICE` → `accomplice`, `INNOCENT` → `suspect` (the column's own default, and the only safe generic mapping — no `redHerring` signal exists in the legacy vocabulary to recover).

## Alternatives Considered

1. **A hard `CHECK` constraint (`character_role IS NULL OR character_role IN (...)`).** Rejected — see Rationale and Discussion. The exact ADR-0051 example, and the one that would be reached for by default; ruled out only after tracing the live write path and confirming no error handler exists to absorb the resulting Make.com abort. Worth revisiting once the deferred Make-side reliability work (ADR-0051 layer 4 / ADR-0049's recorded Make-UI follow-up: error handlers on the `parse-claude-json` and `upsertARecord` modules) ships — same "revisit once the coercion branch is provably dead code" logic ADR-0050 recorded for its own CHECK alternative.
2. **Coerce to `NULL` instead of a sentinel.** Rejected — see Rationale. Works today (the two recovery crons' own NULL checks catch it incidentally), but rides on a coincidence rather than the purpose-built `invalid_role` mechanism, and directly collides with `package_completion_blocking_defects()`'s own documented "NULL is legitimate" carve-out.
3. **A new standalone trigger dedicated to this check, independent of `normalize_character_data()`.** Rejected — `mystery_characters` already has exactly one normalize-on-write trigger, and this is squarely inside its existing job description. Two overlapping BEFORE triggers on the same table for a table that doesn't need one is the ADR-0049 lesson about `validate_package_characters()` applied to a different table: reuse the one that already owns the moment, rather than adding a second thing to reason about.
4. **Skip reconciling the 21 historical rows; let the trigger guard only new writes.** Rejected — see Rationale. Not required for correctness (the trigger doesn't validate existing rows), but leaving a live, known, easily-fixed customer-facing bug (missing role banner) unaddressed when the fix is a five-line, fully-idempotent data migration is not a defensible trade, especially inside the same migration that's already touching this exact column for this exact reason.
5. **Do nothing beyond the ADR-0049 completion gate; rely on it alone.** Rejected — that gate is real and already verified, but it leaves the raw garbage sitting in the column as delivered content for the entire window between write and completion-attempt, which is precisely the gap ADR-0051 layer 1 calls out as separate from (and cheaper/more-permanent than) the gate itself.

## Verification

Run live against the production DB (`mhfikaomkmqcndqfohbp`), using disposable packages/characters created and deleted within the same session — nothing left behind:

1. **Historical data reconciled.** Pre-migration: 21 rows across 2 packages (`546eec7e…` "Death At The Velvet Rose", `79ab2ac3…` "Death At The Deadwood Saloon") held uppercase legacy vocabulary. Post-migration: `SELECT count(*) FROM mystery_characters WHERE character_role IS NOT NULL AND character_role NOT IN (...)` → `0`. Spot-checked both packages by name: every `MURDERER`/`GUILTY` row → `murderer`, every `ACCOMPLICE` → `accomplice`, every `INNOCENT` → `suspect`.
2. **Reproduced the exact incident shape on INSERT.** `INSERT INTO mystery_characters (..., character_role, ...) VALUES (..., '<html><head><title>502 Bad Gateway</title>...cloudflare...</html>', ...)` → stored `character_role = 'invalid_role'`. The raw HTML body never landed.
3. **Reproduced on UPDATE** (mirrors a Make.com retry overwriting an existing row). `UPDATE ... SET character_role = '502 Bad Gateway nginx/1.18.0'` on the same disposable row → `character_role = 'invalid_role'`. Confirms coercion fires on both `INSERT` and `UPDATE`, matching the ADR-0050 template.
4. **All four legitimate roles pass through unchanged.** `INSERT`ed one character each with `murderer`, `accomplice`, `suspect`, `redHerring` → all four stored verbatim, untouched by the trigger.
5. **`NULL` still passes through unchanged.** Confirms the legitimate "unset" case (character-style/random-slip games) is unaffected.
6. **ADR-0049 gate still holds a coerced package.** Drove a disposable package (one coerced `invalid_role` character among five clean ones) through the completing `UPDATE ... SET generation_status = completed, generation_completed_at = now()`. Result: `generation_status.status` came back `needs_review`, `structuralDefects: ["invalid_role.Bob Marchetti"]`. Never touched `completed`.
7. **Recovery crons cannot resurrect it.** With the package still `needs_review` from step 6, `heal_completed_packages()` returned `healed_count: 0`; `promote_complete_packages()` left the package at `needs_review`. Confirms both recovery paths correctly refuse to re-promote while the sentinel is present, via the same `package_completion_blocking_defects()` call ADR-0049 wired in.
8. **Retry flow still works once genuinely fixed.** Updated the coerced character's role to a real value (simulating a regeneration/retry), re-ran `promote_complete_packages()` → package correctly flipped to `completed`. The gate blocks broken content without breaking legitimate recovery.
9. **Clean package completes normally — no false gating.** A second disposable package with two clean characters (one `murderer`, one `suspect` — the suspect's description deliberately including the phrase "an old iron gateway to the estate," the same false-positive probe ADR-0049 used) driven through the same completing `UPDATE` → `completed` on the first attempt. The gate did not fire.
10. **Migration is idempotent.** Re-ran the reconciliation `UPDATE` statement standalone after the migration had already applied and the data was already clean → `0` rows affected. `CREATE OR REPLACE FUNCTION` is idempotent by construction; re-running the full migration file is a safe no-op.
11. **No new security findings.** `get_advisors(type: security)` run immediately after applying the migration shows no findings attributable to `normalize_character_data()` or its trigger (the function retains `search_path = ''` per this project's established convention).
12. **Cleanup verified.** All disposable packages/characters (ids under the `00000000-0000-4000-a000-…` synthetic namespace) deleted at the end of the session; post-cleanup count against that namespace confirmed `0`.

## Consequences

- `character_role` can no longer hold anything other than the four known values or `NULL` — regardless of which writer (Make.com today, any future path) sends it, and regardless of whether the Make-side root cause (no error handler on the child scenario's write modules) is ever fixed.
- The 21 historical rows are corrected; the `murderer`/`accomplice` role banner on `CharacterAccess.tsx` now renders correctly for both affected packages, a genuine (if minor, since both are old paid+completed orders) customer-facing fix bundled with the data-integrity work.
- **The Make.com root cause is not fixed** — no error handler exists on the `upsertARecord` character-write modules today, same as ADR-0049 left the `parse-claude-json` modules unpatched. This migration blocks the *symptom* (garbage landing in the column) at the DB layer; it does not make the underlying transient-5xx class rarer. Consistent with ADR-0051's own framing: reliability at each hop (layer 4) is sequenced last, backstopped by layers 1–2, precisely so it doesn't have to be rushed.
- **Recommended follow-up (Make UI, not applied here):** add error handlers (a **Break**-with-retry directive is the natural fit, matching ADR-0049's recommendation for the sibling `parse-claude-json` modules) to the eight `supabase:upsertARecord` character-write modules in scenario `9061052`, so a transient 5xx retries instead of DLQ-parking the whole run. Same blueprint-versioning discipline as ADR-0049/0050: duplicate the current head (Child v20) as a rollback point before editing, edit on the canvas, don't round-trip the blueprint via the API.
- **Revisit the hard `CHECK` once that follow-up ships and is stable** (mirrors ADR-0050's own note): if Make.com's write path gets a working retry-on-error handler, the coercion branch becomes a pure safety net rather than the primary defense, and a `CHECK` becomes viable without the "aborts a live paying-customer run" risk this ADR just traced and ruled out.
- ADR-0051's layer 1 is now complete for `character_role`. Layers 2–3 (extend the pre-completion gate to the full content-detector suite; build the child-content regenerator) remain as sequenced future work.

## Discussion

The sharpest judgment call was resisting the pull of "constraint" as inherently the stronger, more-correct-sounding fix. ADR-0051 itself names `character_role` "as an enum/CHECK" as the layer-1 example, and a `CHECK` genuinely is the more standard SQL tool for "this column must be one of N values." But the task was never "pick the textbook-correct primitive" — it was "make the bad value impossible to persist without breaking the live pipeline that's the actual source of the bad value." Those pull in different directions here specifically because the write path has zero error-handling: a rejected write isn't a clean "try again with a fixed value," it's an aborted scenario execution sitting in a DLQ until someone notices and manually resumes it. Tracing that — walking the actual blueprint, confirming the `onerror` key is entirely absent rather than assuming it based on ADR-0049's finding about the *different* `parse-claude-json` modules one hop upstream — was the part of this task that mattered most, because guessing wrong here (choosing REJECT without checking) would have shipped a "fix" that turns a data-quality bug into an availability bug for the exact customers it was meant to protect.

The second real decision, coerce-to-what, only became visible by reading `package_completion_blocking_defects()`'s own inline comment closely rather than assuming NULL is a neutral, safe default. It isn't neutral here — it's a value this specific codebase has already assigned a documented meaning to ("intentionally unset"), and reusing it for "scrubbed because it was garbage" would have quietly merged two different real-world states into one representation, which is exactly the "double-encoding" class of bug this whole ADR chain (0048 → 0049 → 0050) keeps surfacing in different forms. A non-NULL sentinel costs nothing extra to implement and keeps those two states distinguishable for as long as anyone might want to know the difference — including, eventually, ADR-0051's layer 3 regenerator, which will presumably want to tell "never generated" apart from "generated garbage, needs a redo" when deciding what to do with a `needs_review` package.

Worth naming plainly, matching ADR-0049's and ADR-0050's own closing honesty: this migration does not fix the bug. It fixes what the bug is allowed to produce. The Make.com scenario will keep having zero error handling on these eight modules until that's addressed on the Make canvas, and every 5xx that lands on a character write will still cost a `needs_review` cycle and a wasted Claude API call — just never, now, a raw error page delivered to a paying customer as their character's role, and never, now, a scenario run that dies silently in a DLQ over a value the DB could have just as easily normalized and moved on from.
