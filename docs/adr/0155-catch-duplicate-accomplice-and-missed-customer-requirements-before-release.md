# ADR-0155: Catch a duplicate accomplice and a missed customer requirement before release

**Status:** Accepted. Built and deployed 2026-10-13 (see Update 1). Jonathan approved the recurring extraction cost in Decision 2 ("recurring cost sounds fine") and the test runs.
**Date:** 2026-10-13
**Related:** ADR-0103 Addendum 92 (the trigger), ADR-0150 (requirements coverage), ADR-0154 (customer email on a hold), ADR-0138 (review-before-release), ADR-0153 (prompt consolidation, why the fix is not another prompt sentence)

## Context

"Blackthorn Manor" reached the customer with two problems the machinery should have handled before she saw them:

1. **A duplicate accomplice.** An innocent journalist was stored as a second `accomplice`. The gate detected it (`accomplice_role_mismatch`) and held the package, but the detector is deliberately detection-only ("nothing is coming to fix them", comment in `notify-generation-issue`), so the package sat until a human looked. A role relabel alone would not have been safe: the sheet had been written as an accomplice's and its secret named the real accomplice, so a relabel would have passed the gate and shipped the leak.
2. **A missing customer-requested role.** The approved concept promised a "substantial, fully developed co-investigator role" for Shannon with her own briefing. The package has no Shannon page (she is five silent mentions in the detective script). The ADR-0150 requirements check should report this. A `requirements_probe` on 2026-10-13 (about 0.15 USD) returned **"skipped: no customer requirements in master_context"**. `customerRequirements()` (`review-package-quality/review-core.ts`) only reads `userRequirements` or `characterDetails` string arrays from the Master Doc. Measured on the 26 paid packages created since 2026-10-01 **only 3 carry `userRequirements`** (S'more, the Dutch Tijdcapsule, Champagnens Skygge). So the requirements check, which ADR-0150 proved on the Dutch package, is silently skipped on about 88 percent of orders, and has been since it shipped on 2026-10-12.

## Decision

1. **Duplicate accomplice: heal, not just detect.** New auto-remediation class `accomplice_role_mismatch`, only for the unambiguous shape: `master_context.accompliceSelection.character` names one character, exactly one other character carries the role `accomplice`, and that other character's `master_context` entry says `isRedHerring` or is not the accomplice. Steps: (a) correct the role to the one `master_context` gives that character; (b) regenerate that one sheet through `regenerate-child-content` with the corrected role (about 0.15 USD per occurrence, same gated, reverting path as `narration_person_mismatch`), because the sheet text was written for the wrong role; (c) the gate and the reviewer then run as normal. Anything else (zero accomplices where one was asked, a name that matches nobody, two names in `master_context`) stays detection-only and escalates. Add the prefix to `WORKER_RECOGNIZED_PREFIXES` in `notify-generation-issue` so the page waits for the worker first (the KEEP-IN-SYNC rule).
2. **Requirements: do not depend on the Master Doc emitting the list.** When `customerRequirements()` finds no list, build one from the customer's own words in `user_conversation` (the brief plus the approved concept; where they conflict the approved concept wins, as the package already says) with one extra reviewer call that returns one requirement per line. Then the existing coverage call runs unchanged. Estimated cost 0.03 to 0.05 USD per order on top of the existing 0.14 to 0.15 USD coverage call (my estimate; the first run will give the real figure). Findings stay `open` for requirements (never auto-applied, as ADR-0150 says), so a missing Shannon briefing reaches Jonathan before the customer.
3. **Prove both before relying on them.** (a) Decision 2 is tested on Blackthorn Manor itself (the pre-fix package had no Shannon page; the extraction plus coverage must report it) and on the Dutch package as a negative control. (b) Decision 1 is tested on a synthetic clone of this package with a second `accomplice` role, as the ADR-0138 fixtures were (no user attached, no email).

## Rationale

Prevent, detect, heal, escalate (the North Star in ADR-0131): the gate already detects; Decision 1 adds the heal for the one shape that is safe to repair, and Decision 2 repairs a detector that was never running on most orders. Both are code and data fixes, not another sentence at the end of a Make prompt (ADR-0153).

## Alternatives considered

- **Relabel the role in SQL only (free).** Rejected: would have shipped the leak in this package (the demoted sheet's secret named Pam).
- **Ask the Master Doc prompt to always emit `userRequirements` (Parent85).** Rejected as the only fix: it already emits it on 3 of 26 and a prompt cannot be proven to hold (ADR-0142, ADR-0153). Could be added later as a second source.
- **Block release when no requirements list exists.** Rejected: would hold 88 percent of orders.
- **Make Shannon-like roles a deterministic gate (a named co-investigator must have a sheet).** Not deterministic: the concept's wording varies. Left to the coverage call.

## Consequences

- A recurring reviewer cost of roughly 0.03 to 0.05 USD per order for the extraction (Jonathan's yes needed; global rule on paid calls).
- More `REQUIREMENTS` findings will now appear on orders that were previously skipped, including ones that are not defects (the brief asks for name cards and ballots the product does not generate). They stay open and are verdict-recorded like other findings, so precision is measured before anything auto-applies.
- A duplicate accomplice becomes a 15-minute self-heal instead of a four-day hold, in the case where the shape is unambiguous.

## Discussion

Jonathan asked for something that catches this class up front instead of fixing each package by hand after the customer has seen it. Scoping showed two different gaps: the accomplice one is a missing repair, the Shannon one is a check that was not running. The second was the larger finding: the probe returned "skipped", which led to the 3-of-26 measurement. Jonathan approved the probe and the build direction on 2026-10-13; the recurring extraction cost is the one open question.

### Decision 2: requirements list from the conversation

- **Built:** when `customerRequirements()` finds no Master Doc list, `extractRequirements()` makes one extra call (effort medium, JSON schema `{requirements: string[]}`) over `user_conversation` (long chats keep their first 40 and last 60 percent), then the unchanged coverage call runs. The prompt says the approved concept wins over the brief and skips printables, formats, timing, optional items and headcount. Capped at 40 lines. Honours `review_requirements` (off skips both), is skipped in the second pass and in `dry_run`, checks the 10 USD daily cap before calling, and any failure returns null (the check is skipped exactly as before). Its cost is logged on its own `auto_remediation_log` row (`requirements_extract:N_lines`) and counts toward the per-package cap; the later `review:` row logs the remainder so nothing is counted twice. Findings keep `item_name` REQUIREMENTS and stay `open`: nothing in the auto-apply path touches them. `requirements_probe` now reports source, list, extraction cost, and accepts `force_extract:true` (probe only) to exercise the fallback on a package that has a Master Doc list.
- **Blackthorn Manor (`0bc4a72a`):** list built from the conversation: 19 lines; extraction 0.0246 USD, 7 s (20k-character chat); coverage 0.1956 USD. One finding, validated against the list: "Shannon is a substantial, fully developed co-investigator partnered with Stephanie, with her own backstory, personality and private briefing" has no character sheet (medium; the ADR-0150 rule gives high only for climax, reveal and central clue lines). The probe is read-only, so no row exists in `package_review_findings` for this package; Shannon's hand-written briefing still lives outside the database.
- **Dutch Tijdcapsule (`01c497a2`), negative control, two runs.** (a) Plain: the Master Doc has a list (20 lines), source `master_context`, 0.2021 USD, one finding (Tom's catchphrase, which the real run would discard as a non-unique quote), no climax finding. (b) Forced extraction: 32 lines from the conversation, extraction 0.0822 USD, 17 s (57k-character chat, the longest of the 26), coverage 0.1357 USD, 4 findings, none about the climax. I checked all four against the stored text with SQL: Bas' opening line, the `jawuhl meine Führer` catchphrase, Bas' old agenda and Thijssen's excursion, and the group photo Thijssen took are each absent from every sheet and shared document, so 4 of 4 are real customer details nothing carries (the one "agenda" hit in Dina's sheet is the unrelated phrase "geheime agenda"). The negative control holds: the climax lines, which are present, were not reported.
- **Cost, measured against the 0.03 to 0.05 USD estimate:** 0.0246 and 0.0822 USD on the shortest and longest chats of the two probes. Over the 26 paid orders since 2026-10-01 the stored conversation has a median of 7.3k, mean 13.9k and maximum 57.5k characters, so a typical order should cost about 0.01 to 0.03 USD; the figure is still unmeasured on a real order. Probe spend this decision: 0.2202 + 0.2021 + 0.2179 = 0.6402 USD.

### Decision 1: duplicate accomplice heal

- **Built:** class `accomplice_role_mismatch`, plan rules in `accomplice-heal.ts` (pure, 15 unit tests in `npm run test:roster`). It acts only when ALL hold: detective style; `ready_email_sent_at` is null (a delivered sheet is never rewritten under the customer; this guard is an addition to the ADR); exactly two characters carry `accomplice`; `master_context` names exactly one accomplice (dual-gender spellings match) and it is one of the two; the other has a per-character entry that says it is not the murderer. The other character's role becomes `redHerring` when `isRedHerring` is true, otherwise `suspect` (the two innocent labels in the corpus). Then: write the role, regenerate the whole role-dependent sheet through `regenerate-child-content` (14 fields, its three groups: identity, social, rounds), sync the `secrets` list, rebuild the bullet versions with `generate-pointform-summaries` (or clear them if that cannot run, so stale accomplice bullets cannot ship). The role is put back if the regeneration does not come back `fixed` or throws (`runWithRoleSwap`), so the gate keeps holding the package. Every other shape (slip, delivered, zero, one or three accomplices, no or several names in `master_context`, no entry for the other character) is logged once as `escalate:ambiguous:<reason>` with outcome escalated, which ends the notify grace period and pages immediately. The class is in the 5-minute held-only cron (migration `20261013120000`) and in `WORKER_RECOGNIZED_PREFIXES`.
- **Test on a synthetic clone** of Blackthorn (package `9224b650-3374-4c11-a9fb-6ff1a170ac48`, `is_test`, no user, review hold pre-released): Jackie set back to `accomplice` with her original leaky secret ("protect the person behind the note ... Pam") and marker bullets.
  - Dry run: one planned action, exactly as intended, and no real package in the candidate list.
  - Run 1 (direct call): fixed in 95 s. Database afterwards: Jackie `redHerring`, Pam the only accomplice, only Jackie's row touched, new secret about her own failed exposé with no mention of Pam, `secrets` equal to `secret`, marker bullets replaced, `accusations` back to the 189-character innocent stub, gate returns no defects. The existing pipeline released the package about 15 seconds later (status completed, ready-email slot claimed; no user, so no email).
  - Run 2 (after the migration, through the real 5-minute cron, fixture reset to held): healed at 11:21:21 and bullets at 11:21:34, same verified result. This exercised the deployed refactor of the shared delegate path.
  - Negative: three accomplice-role characters. Two worker runs wrote exactly one escalation row, spent 0, changed no role.
- **Cost:** logged 0.30 USD for the regeneration (three calls at the flat 0.10 estimate; the metered figure is not available) plus 0.05 for the bullets, 0.35 per occurrence, twice = 0.70 USD. That is about double the 0.15 in Decision 1, because the whole role-dependent sheet is regenerated: the accomplice text sits in the secret, the accusation sheet, the round scripts and the final statement, and a partial regeneration cannot be proven clean from the outside.
- **Not exercised live:** the revert-on-failure path (a live failure would cost about 0.3 USD); it is covered by five unit tests with a fake writer (success keeps the role, failure and a thrown error put it back, an unwritable role never runs the body, no swap writes nothing).
- **Fixture cleanup did not complete.** Deleting the fixture (package above, conversation `41b330d1-9904-48bf-bcf1-c1a1a99f36cf`, 11 characters) was declined by the session's permission layer on three attempts, including after Jonathan answered "Delete it". It remains in the database in `needs_review` with three accomplice-role characters and `is_test` true, no user, `ready_email_sent_at` null. Deleting the package also cascades its `auto_remediation_log` rows (the 0.70 USD above).
