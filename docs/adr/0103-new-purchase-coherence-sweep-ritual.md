

**Update 5 (2026-10-07, same day: still failing after Update 4; held run narrowed, one retry on timeout).** A third alert email arrived at 10:50 CEST (08:50 UTC): the same `list_packages_with_meta_text_leak` statement timeout, **four minutes after Update 4's migration was applied (08:46:09 UTC)**. So Update 4 did not by itself end it. Failures so far, all on the same detector: 01:45, 07:05, 07:13 (before any fix), 07:30 (old code, fatal), 08:00 and 08:13 (after Update 3, guard worked), 08:50 (after Update 4, guard worked). Runs between them were clean.
- **What the evidence says, and what it does not.** Alone, the 30-day call is a steady 2.2 s (Update 4); the timeout needs 8 s, so something makes it about 4x slower at the moments it fails. At 08:50:00 ten cron jobs fire in the same second (`heal_completed_packages` and `sweep_incomplete_packages` 1.7 s each, `auto-remediate-held-packages`, two review jobs, `rescue-unstarted-orders`, three stuck-package sweeps); `:00` is similar and `:13` is the full run. `pg_stat_statements` shows `heal_completed_packages()` and `sweep_incomplete_packages()` with a mean of about 240 ms but a max of about 6.3 s (they also run the leak scan per package), and PostgREST calls with a max of 7.98 s, which fits "same work, slower under concurrency". **That is a strong correlation, not a measured proof: I did not capture the failing moment itself.** The failing 08:50 call was the 5-minute held run (it fails 12 s after the cron tick, i.e. on its first detector, `template_artifact`).
- **Why the held run is the lever.** `auto-remediate-held-packages` runs every 5 minutes (288 times a day) and called six detectors (`identity_contamination`, `slip_culprit_leak`, `template_artifact`, `missing_role_branch_content`, `pointform_language_mismatch`, `narration_person_mismatch`) over the full 30-day window, only to throw away every row that is not a `needs_review` package. Measured alone on the 30-day window those six cost roughly 1.9 + 0.05 + 2.2 + 0.05 + 4.9 + 0.9 s, about 10 s of database CPU every five minutes, the largest recurring load of the detectors and the one that lines up with the other cron jobs.
- **Fix 1 (worker, `auto-remediate-packages` v27).** `runWindowDays` in `detector-guard.ts`: when `only_needs_review` is set the window is at most 7 days (`HELD_RUN_WINDOW_DAYS`); an explicit narrower `window_days` still narrows, an explicit `backfill_days` still wins, and the half-hourly full run keeps 30 days. A held package older than 7 days is therefore only picked up by the full run, not by the 5-minute one (measured on the 7-day window: meta-text-leak 2.65 s before Update 4, pointform 1.25 s; 18 packages instead of 57). The re-detect gate uses the same window as the sweep, so a fix and its check stay consistent.
- **Fix 2 (worker).** `runDetectorGuarded` retries once, and only for a message containing "statement timeout", before skipping the class and counting the failure. Other errors are not retried, and the re-detect gates are still unguarded on purpose. The retry costs up to one more detector call in the rare case; the function has 280 to 300 s.
- **Test.** `scripts/__tests__/detectorGuard.test.mjs` now 10 checks: retry then recover records nothing, two timeouts record once after exactly two attempts, a non-timeout error is not retried, and the window rules (full 30, held 7, narrower request wins, backfill wins).
- **Not done, and why.** No change to `heal_completed_packages`/`sweep_incomplete_packages` or the cron minute offsets (the other contenders; staggering is the next lever if the alert recurs, and moving the held job off `:00/:10/:50` is a one-line cron change). No SQL change in this update. If an alert arrives after v27, the next step is to capture the slow moment (`pg_stat_activity` snapshot while the full run executes) rather than guess again.
