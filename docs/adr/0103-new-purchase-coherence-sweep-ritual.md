# ADR-0103: New-Purchase Coherence Sweep — a standing practice, not a one-off audit

- **Status:** Accepted
- **Date:** 2026-08-22
- **Related:** ADR-0098 Addenda 4-8 (the audit this ritual is distilled from), ADR-0074 (blanket Sonnet 5 upgrade), ADR-0042 (the original content-quality detectors this ritual leans on and works around)

## Context

A single hands-on audit of one customer's package (Lyn DiFranco, ADR-0098 Addendum 4) turned up real, customer-facing coherence bugs — a victim-name mismatch, a self-contradicting secret, dangling references to removed characters, a garbled sentence, a leaked prompt placeholder — none of which the existing automated content-quality detectors (ADR-0042) caught. Widening the sweep found the same defect family in 14 more packages across a year of history (Addenda 5-6), and confirmed the detectors themselves had real bugs of their own (a `\b`-vs-`\M` regex mistake that silently disabled a whole marker family, and a false positive on a legitimate template token) — bugs only found by re-verifying results by hand rather than trusting a clean detector run at face value.

Jonathan now gets a paid purchase roughly every day or few days and wants to spot-check each one for coherence, the way today's audit did, without either (a) re-deriving the whole methodology from a blank prompt each time, or (b) the checklist quietly drifting/forgetting steps between sessions. He asked, in effect, for the same kind of low-friction ritual this project already has for session-closing and inbox-processing — paste a purchase notification into a fresh tab, say one word, get the same thorough check every time.

## Decision

Adopt **"sweep"** as a project shorthand command (documented in `CLAUDE.md`, which every fresh session auto-loads — no separate memory/pre-prompt setup needed). Invoking it with a pasted purchase notification (conversation ID is the only required field) runs the following checklist:

1. **Resolve the package.** From `conversation_id`: `package_id`, `created_at`, `mystery_style`, `player_count`, `has_accomplice`, `is_paid`, `purchase_date`, and the conversation's language/theme.
2. **Note the model era.** Pre- or post- 2026-08-11 (ADR-0074's blanket Sonnet 5 upgrade). Pre-upgrade packages get extra scrutiny — that's where every defect found so far has clustered — but post-upgrade is not skipped; the one post-upgrade package checked so far needed a full manual read anyway because it was non-English (see step 6).
3. **Run the two patched detectors** scoped to this package (`list_packages_with_meta_text_leak`, `list_packages_with_victim_mismatch`). Treat a clean result as a data point, not proof — both have documented blind spots (ADR-0098 Addendum 6): `victim_mismatch`'s core check still cannot catch a victim surname that's wrong but legitimately belongs to a different, living character in the same package, which was Lyn's actual bug.
4. **Manual victim-name consistency check.** Extract the victim's *exact* name string from `game_overview` and `detective_script`; cross-check against what 3-4 characters' own background/relationships sections call the victim, plus `evidence_cards`. Check for exact-string agreement, not just name *presence* — dual-gender placeholders like `"Margot/Marc Dubois"` are the intentional default convention for every named person in this generator (including the victim; the host is expected to resolve suspects manually via the `character_name` field, see Addendum 3), so `"does the character text contain the victim's name"` will pass even when one document says `"Margot"` and another still says `"Margot/Marc"` — a real, high-severity mismatch a substring-presence check cannot see. Compare the literal strings, not just whether one contains the other.
5. **Read the full detective_script** (or a large sample) end to end for leaked brackets/placeholders, garbled sentences (another character's name inserted mid-sentence), and — if `mystery_style = 'character'` (slip-style) — confirm any `[MURDERER NAME]`-style bracket is the *legitimate* host-fill-in convention (paired with an explicit stage direction telling the host to write in the name), not an accidental leak. Bracket patterns are not inherently bugs; context decides.
6. **Spot-check 2-3 characters' full content** (relationships, secrets, round scripts, accusations) for leaked authoring notes, self-directed questions, dangling references to removed characters (relevant only if this package went through Remove-a-Character), and broken/garbled sentences. **If the package is non-English, do this check in that language** — the automated detectors are English-pattern regexes and will not catch an equivalent leak in Spanish, French, etc. (confirmed clean on the one non-English package checked so far, but only because it was checked by hand, not because the detectors would have caught a problem).
7. **Full-schema field-completeness check, from the actual column list, not a remembered subset.** Pull `information_schema.columns` for `mystery_characters` directly rather than checking whichever fields seem relevant from memory — a hand-picked subset is exactly how a real gap (Grant/Gracie Whitfield's `accusations`, then `rumors`, both missed on the first two passes of this exact package — see Addendum 6) slipped through a "manual completeness check" that felt thorough at the time. Check two distinct shapes, both required:
   - **Partial nulls** (some characters in the package have the field, others don't). This shape is now caught automatically by `validate_package_characters()` for any package completing on or after 2026-08-30 (ADR-0113) — still worth a quick confirm on older packages, but no longer needs manual vigilance for new purchases.
   - **Uniform nulls** (every character in the package is missing the same field). ADR-0113's trigger cannot see this shape — its check only compares characters against each other within a package, so a field that's wrong for 100% of characters looks "consistent" to it. This is not hypothetical: checking for it directly found 12 whole packages with `secret` null on every character, invisible to the partial-null method (ADR-0113 Addendum, 2026-08-30). Run this check regardless of when the package completed.
   - **When two similarly-named columns exist for what looks like the same concept** (e.g. `secret` vs `secrets`), don't assume either is authoritative — grep the actual frontend render paths (`src/components/*.tsx`, `src/pages/*.tsx`, `src/services/*.ts`) for which one customers actually see before treating a populated "twin" field as evidence the content made it to the customer. `secrets` (plural) turned out to feed a component (`CharacterDetailView.tsx`) that isn't imported anywhere in the live app — real content sitting there was invisible to every customer despite passing an `IS NOT NULL` check.
8. **Run `package_completion_blocking_defects()`** to catch genuinely missing content — a different defect class (empty fields) from the leaked/garbled-text family everything else above targets.
9. **If something is found:** fix directly (targeted SQL edits, matching the patterns already established), re-verify with the same checks, and log a CHANGELOG entry plus an addendum to *this* ADR (not ADR-0098 — that ADR's own topic is a specific stuck-invocation incident already carrying 8 addenda on an adjacent-but-distinct investigation; this one is the dedicated home for the sweep ritual and its findings going forward).
10. **If the package is clean:** report back in chat only. No CHANGELOG entry, no ADR addendum — a "nothing found" result for a routine, expected-to-usually-be-clean check doesn't need a permanent artifact, and logging every clean sweep would bloat the trail past the point of being useful. (This is a deliberate exception to the project's general "every decision needs a durable home" rule — a sweep finding nothing isn't a decision, it's the ritual working as intended.)

## Rationale

- **CLAUDE.md over a memory-system entry**, because this is a *procedure* (repeatable steps triggered by a keyword), and the project already has this exact pattern for session-closing and inbox-processing — both live in CLAUDE.md, not in the auto-memory system, which is reserved for facts/preferences/context rather than playbooks. A fresh session auto-loads CLAUDE.md with zero setup from Jonathan; the auto-memory system is for the assistant's own accumulated understanding, not a stand-in for a checklist a human should be able to read and audit too.
- **A dedicated new ADR over folding into ADR-0098**, because ADR-0098 is already a specific incident report (a stuck batch invocation) that grew 8 addenda through an adjacent but genuinely different investigation (content-quality, not invocation reliability). A ritual that will recur every few days for the indefinite future deserves its own numbered home rather than continuing to stretch an ADR whose title no longer describes most of its content.
- **Clean sweeps get no permanent document**, a deliberate carve-out from this project's usual "capture every decision" rule — logging "checked, found nothing" every few days would make the CHANGELOG/ADR trail worse at its actual job (surfacing real decisions and defects) by drowning them in routine confirmations. The chat transcript itself is the record for a clean result; only findings get written down.
- **Detector results are a data point, not a verdict**, because this session directly proved that "the detector says zero hits" and "the package is actually clean" are different claims — twice (the `\b` bug, and the same-package-swap blind spot that's still unfixed by design). The checklist's manual steps (4, 5, 6) exist specifically to catch what the automated layer is known not to.

## Alternatives Considered

- **A slash command / skill.** Would work, but this project doesn't currently have custom skills wired up, and a CLAUDE.md section achieves the same "say one word, get the full checklist" outcome with zero additional tooling to build or maintain — consistent with this session's broader conclusion (in the model-staleness discussion) that the actual risk here doesn't warrant new infrastructure.
- **Fully automating the sweep** (a cron job that runs it on every new purchase). Rejected for now: steps 4-6 are judgment calls a human-in-the-loop read still does better than a regex, per the exact detector-blind-spot findings above. Revisit if/once the model-era risk concentration (almost everything found so far is pre-2026-08-11) is confirmed to have fully resolved and the checklist can safely shrink to steps 3+7 alone.

## Consequences

**Positive:**
- Jonathan can open a fresh tab, paste a purchase notification, say "sweep," and get the exact same thorough check every time — no re-explaining the methodology, no risk of a step being forgotten because a session started cold.
- The checklist is itself durable and auditable (this file), not locked inside one conversation's memory.

**Negative:**
- Still requires a human judgment pass (steps 4-6) — not a zero-effort automated gate. Acceptable given the "Alternatives Considered" reasoning above.
- Clean-sweep results aren't logged anywhere permanent, so there's no running count of "how many packages have been checked" without reconstructing it from chat history. Acceptable trade against not bloating the CHANGELOG/ADR trail.

## Addendum 1 (2026-08-23): step 4's "does the text mention the victim" check has the same substring-blind-spot the detectors have — found systemic, not isolated

A second sweep pass on an already-"cleared" package (Toby Wragg's *Death On The Île De Ré*, full incident in [ADR-0104 Addendum 3](0104-close-post-purchase-free-regeneration-hole.md#addendum-3-2026-08-23-victim-name-consistent-in-addendum-2-was-wrong--a-re-purchase-notification-sweep-on-the-same-package-caught-a-real-leak-addendum-2s-spot-check-missed)) found a victim-name mismatch that an earlier sweep's step-4 check had explicitly signed off as clean. The gap: checking whether a document *mentions* the victim's name (e.g. "does this character's background contain 'Margot'?") passes even when the actual rendered text differs — `"Margot/Marc Dubois"` contains `"Margot"` as a substring. Step 4 above is now reworded to require exact-string comparison, not presence-checking.

Checked whether this was specific to Toby's package (which had a rocky, manually-triggered generation history) or systemic: sampled 11 completed, live customer packages with a detectable dual-gender victim name in `master_context`. 3 of 11 (27%) had a real parent/child mismatch of this exact shape, not just Toby's — **Behind The Mask: Death At The Gilded Circle** and **Death At The Velvet Rose** were both live and delivered with the same defect, found and fixed the same session (detail in the ADR-0104 addendum linked above). Neither of the two automated detectors (`list_packages_with_meta_text_leak`, `list_packages_with_victim_mismatch`) caught any of the 3 — both have the identical substring-presence blind spot.

**Not done here:** a full audit of every completed package (only 11 with a cleanly-regex-extractable dual-name victim were sampled), and no pipeline-level fix (resolving the victim's name once upstream of both parent and child generation, or a new detector that diffs the exact victim string across documents). Both are reasonable follow-ups if this pattern shows up again on a future sweep.

## Addendum 2 (2026-08-25): `detective_script`'s REVEAL section can hardcode a fixed culprit in a `mystery_style='character'` package, and `list_packages_with_slip_culprit_leak()` doesn't check it

A sweep on Jaclyn's "Operation: Thirty & Murdery" (30 players, `has_accomplice=true`, conversation `624ad4af-3b5b-43d8-8f25-7df919ef153f`) found a real G8 violation (`docs/generation-guardrails.md`): `detective_script`'s "## THE REVEAL" section explicitly named a specific murderer and accomplice ("The killer is **Dr. Kai Okonkwo**... **Dr. Westley Kimura**, I believe that someone was you") in a `mystery_style='character'` package, where G8 requires "NO FIXED CULPRIT: the murderer is selected by slip-draw at the table... do not designate, name, or imply a pre-assigned murderer anywhere." Everything else in the package was structurally correct for the slip-draw mechanic — `game_overview` correctly says "the culprit is randomly selected at game time," every character has full innocent/guilty/accomplice round-script branches, and `character_role='suspect'` for all 30 (no DB-level fixed role) — only `detective_script`'s prose reveal broke the pattern.

`list_packages_with_slip_culprit_leak()` (migration `20260810_add_is_test_flag_and_harden_health_check_detectors.sql`) returned zero hits on this package and does not catch this shape: it only scans each character's static `secret`/`secrets` field for confession-style phrasing (`'you (poisoned|killed|murdered|...)'` + `'hide/conceal ... guilt'`), the exact shape of the original "Adelaide Crane" incident this detector was built for. It never scans `detective_script` for a named, fixed culprit. `package_completion_blocking_defects()` and `list_packages_with_meta_text_leak()` also don't catch it — this is a distinct defect class from both.

**Fixed directly** (zero-cost text edit, no Anthropic call): rewrote just the REVEAL section's culprit-naming sentences to use the same host-fill-in bracket convention already established elsewhere in the same document (e.g. `*[Read this when guests are gathered...]*`) — `**[GUILTY PLAYER'S NAME]**` / `**[ACCOMPLICE PLAYER'S NAME]**`, with explicit host stage directions to name the actual slip-drawer and connect their real motive in their own words. Verified: no hardcoded names remain (`detective_script ~* 'Dr\. Kai Okonkwo|Dr\. Westley Kimura'` → false), and the edit doesn't trip `list_packages_with_meta_text_leak()`'s bracket-pattern markers (correctly, since this is the legitimate host-fill-in convention step 5 already asks sweeps to distinguish from a leak).

Also found and fixed in the same sweep: **Cypress/Celine Beaumont was missing entirely** (no `mystery_characters` row — the health-check alert's "Missing Characters" list) despite `generation_status` already reading `'completed'`; the completion gate's `package_completion_blocking_defects()` only validates existing rows, so a wholly-missing row doesn't block completion at all, meaning a "ready" email can go out (and did, `ready_email_sent_at` predates the recovery here) while a paid-for character is completely absent. Manually re-fired the same recovery webhook the automated system uses (packages that flip to `'completed'` drop out of the `needs_review` sweep loop that would otherwise retry them) — row created, but her `round2_guilty`/`round3_guilty`/`round4_guilty`/`final_guilty` branches came back empty across two consecutive attempts (the automated 2-attempt cap is now exhausted), a persistent-looking failure possibly the same class as the Sylvie/Sylvain Dubois content-filter block noted elsewhere in this repo. Left as-is: with the REVEAL fix above, her guilty branch is never actually handed to a player in this package's as-delivered gameplay, so the practical impact is nil unless the Recast/reassignment feature is used on her later.

**Not done here:** no new detector was built for the `detective_script`-names-a-fixed-culprit shape, and no corpus-wide sweep was run to check whether other live `mystery_style='character'` + `has_accomplice=true` packages have the same reveal-hardcoding pattern (this incident is the first confirmed instance). Both are reasonable follow-ups if this shape shows up again.

## Addendum 3 (2026-08-25): root-caused and fixed Cypress's empty guilty branch — a genuine Claude output-formatting failure, not truncation, not content-filtering

Follow-up closing the "left as-is" item from Addendum 2. Root-caused via the Make API's execution log (module 513's actual output bundle for the exact failing run): Claude's response had `stop_reason: "end_turn"` and used only 2360 of the 5000 available `max_tokens` — ruling out truncation entirely — but the JSON itself was genuinely malformed: the last field's string value ended cleanly on a finished sentence ("...I collected one she never expected to pay.") with no closing `"` or `}` anywhere after it. The model simply stopped without closing the JSON structure it was still inside, despite the prompt's `critical_json_rules` block explicitly instructing it to verify the closing brace and quote are present before emitting. This is why all 5 fields from that one call (`round2Guilty`, `round3Guilty`, `round4Guilty`, `finalGuilty`, `revealConfessionGuilty`) came back empty together — `parse-claude-json`'s parse is all-or-nothing, so one malformed call zeroes out everything it was responsible for, even though 4 of the 5 fields' content was already complete and well-formed at the point the model stopped.

**Fixed**: added a new, deliberately conservative final sanitization stage to `parse-claude-json` (`attemptCleanTrailingCutoffRecovery`) that detects this exact shape — still inside an open string at end-of-input, with the trailing text ending on sentence-terminal punctuation (`.`/`!`/`?`) — and closes the string plus any still-open braces/brackets before retrying the parse. Deliberately does NOT recover a cutoff that doesn't end cleanly (mid-word, no terminal punctuation): that shape is far more likely a genuine `max_tokens` truncation, and silently "closing" it would ship a visibly cut-off sentence instead of correctly falling through to the existing empty-field handling (which the missing-content detectors and auto-recovery loop already cover safely). Verified against the actual real failing payload (extracted via the Make API, not reconstructed by hand) before deploying — recovers all 5 fields correctly; a synthetic mid-word truncation and normal valid JSON both still behave exactly as before. Deployed (`parse-claude-json` v10, `verify_jwt` preserved) and re-verified against both cases on the live endpoint post-deploy.

Not done: Cypress's own character row on the original package still has the empty guilty branch (this fix prevents the *next* occurrence, it doesn't retroactively backfill her — left alone since, per Addendum 2, her guilty branch is never actually used given the detective_script fix). Also not done: whether this exact "clean end-turn, unclosed JSON" shape has affected any *other* character/package historically, silently absorbed by the existing 2-attempt auto-recovery retry without ever surfacing — no historical sweep was run for it.

## Addendum 4 (2026-08-28): a dual-name-shorthand gap in the Recast scrub's `nameVariants()` survives even a "verified" removal — found via a package with a broken alibi, a translated-away-and-back-to-life red herring, and an unrelated full-package language bug

Sweep on rsappel17@gmail.com's "De Bittere Verjaardag: Moord In Villa Limoncello" (`eb0f3f1d-c404-49bb-8c7c-6daa135faa15`, Dutch, detective-style, 18→14 players via a paid 4-character Recast batch) found three separate, real defects layered on top of each other.

**1. Recast's `nameVariants()` (`adapt-mystery-apply/index.ts`) never generates the bare dual-first-name shorthand — e.g. "Jules/Julia" without the surname "Bergman" — that this generator's own prose uses constantly for casual references.** It only pairs each half of a dual-gender name with the surname ("Jules Bergman", "Julia Bergman"), plus the literal full string, plus a bare-surname fallback. Every one of Jules/Julia Bergman's 14 residual mentions after her "verified" removal used exactly this uncaught bare-first-name form — including **Robin Van Zuren's entire alibi for Round 3, Round 4, and the Final Statement**, built on "I was dancing with Jules/Julia the whole time," a person no longer in the game. Daan/Dana De Vries and Parker/Petra Lindholm (verified in the same batch) had smaller versions of the identical gap: 2 residual mentions each, one of them (Alex/Alexandra Dubois's Round 4 alibi, "I was with Jordan and Parker") load-bearing in the same way. `detective_script` also never got Jules/Julia's "could not attend, cleared" host note, despite the append being unconditional in code — a second, distinct gap in the same removal that a same-day sibling session's investigation (see [ADR-0088's 2026-08-28 addendum](0088-guest-dropout-multi-character-and-reassignment.md#addendum-2026-08-28-verify-step-never-got-the-sibling-batch-exclusion--false-positive-rollback-on-a-real-4-character-batch)) did not touch — that addendum fixed a different bug (the verify step's missing sibling-batch exclusion, which had caused Dr. Sasha/Sascha Kowalski's removal to roll back).

**2. That same sibling-batch-exclusion fix's "verified clean on retry" claim for Dr. Sasha/Sascha Kowalski was itself a false negative from the identical `nameVariants()` gap.** Sasha was a major red-herring thread — a patent-theft motive referenced as a comparison point in nearly every other character's reasoning about who else had a reason to want Hendrik dead. Manually re-scanning the live package after that addendum shipped found **26 residual "Sasha/Sascha" mentions across 12 of the 14 remaining characters**, including Casey Morrison's entire Round 4 alibi ("I was with Dr. Sasha/Sascha discussing root disease resistance") — the same broken-alibi shape as Robin/Jules, just larger. The verify step's blanket reference scan uses the same `variantRegex` as the scrub itself, so a name shape the scrub can't catch, the verify step can't catch either — "verified" and "verified clean on retry" are not independent confirmations of the same fact, they're the same regex asked twice.

**3. Unrelated to Recast entirely: 100% of the package's character content was in English while `game_overview`/`detective_script`/`master_context`/`evidence_cards` were correctly in Dutch**, matching the customer's actual concept-chat language. Root cause in `mystery-webhook-trigger/index.ts`: the child-generation scenario resolves its explicit language parameter from `profiles.language` (an account-level UI setting) rather than from the conversation's actual demonstrated language — this customer's profile read `"en"` despite every message in the concept chat being in Dutch. `evidence_cards` also had a mid-sentence English/Dutch template leak ("Each card pairs met een forensisch beeld").

**Fixed:** manually rewrote Robin Van Zuren's alibi to drop the dependency on Jules/Julia (falls back to the generic "dozen people"/"tennis club guests" corroboration already present in the same text, rather than inventing a new named witness), patched the Daan/Parker/Jules residual mentions, added Jules/Julia's missing detective_script note, then ran one combined Claude Sonnet 5 pass (approved cost estimate ~$0.84, actual $1.63) that translated all 14 characters' content to Dutch **and** rewrote every Sasha/Sascha reference to read coherently without her — verified afterward at 0 residual mentions of all four removed characters beyond their single legitimate host notes each. Fixed the evidence_cards template leak with a direct text edit.

**Not done here (at the time):**
- The `nameVariants()` code fix itself.
- The child-generation language-resolution root cause (ADR-0112 proposes it).
- A corpus-wide check of whether other completed Recast removals have the same undetected residual-mention shape.

All three follow-ups above were completed the same night — see Addendum 5.

## Addendum 5 (2026-08-28/29): fixed `nameVariants()` and a second, more severe bug it was masking; corpus sweep found a live customer's package with the actual murderer and accomplice still haunting every remaining character's dialogue

Following Addendum 4, Jonathan asked whether this had been addressed systemically. It hadn't — Addendum 4 fixed one package's data, not the code. Sequencing agreed: fix `nameVariants()` now (narrow, low-risk), propose the language-resolution fix as an ADR rather than code it directly (a real design decision, not a patch — see [ADR-0112](0112-child-generation-language-should-follow-the-conversation-not-the-account.md)), and run a corpus-wide sweep of every `mystery_adaptations` row with `status = 'verified'` before trusting that status again.

**Code fix 1 — `nameVariants()` bare dual-first-name shorthand.** Added the missing variant identified in Addendum 4 (`${before}/${altToken}`, e.g. "Jules/Julia"). Deployed `adapt-mystery-apply` v14, `verify_jwt: true` preserved.

**Corpus sweep found 15 total `verified` Recast rows across 3 packages.** Package `a0a985a9` (9 dual-named removals, 2026-08-20) checked clean — an initial alarm on 2 characters was a false positive in the sweep's own ad-hoc scan (the surname "Cross" coincidentally matched the common word "cross" in an unrelated sentence, a known and already-accepted risk of the bare-surname fallback, not a real leak). Our own package (`eb0f3f1d...`) was already clean from Addendum 4.

**Package `c28e31f6` ("El Último Brindis De Bellanotte," Spanish, detective-style, requested_by_email `esj@salgados.net`, 2 removals completed 2026-08-22) was badly broken, and not from the same bug.** `dropBlocksTargeting()` — the function responsible for dropping question/rumor blocks addressed to a removed character — has a name-shape regex hardcoded to English:

```
const nameShape = /^(?:\d+\.\s*)?\*\*(?:To|About)\s+([^:*]+):\*\*|^\*\*([^*]+)\*\*\s*-/;
```

It only recognizes `**To Name:**` / `**About Name:**`. Spanish uses `**A Nombre:**`. The regex never matched, so `target` was always `null`, and the code's own documented fallback for that case is "keep the block." **This means block-level removal has silently done nothing for every non-English Recast removal that uses this shape, since it shipped** — not a Spanish-specific bug, a bug for any of the 12 non-English locales this product ships in. Effect on this package: **39 undropped question/rumor blocks across all 13 remaining characters**, every one still instructing guests to interrogate two people no longer in the game.

It got worse on inspection. The two removed characters — Matilde de Monteverde and Aniceto de Monteverde, a married couple — were **the murderer and accomplice**, reassigned per ADR-0088 to Carlota de Villaclara (now murderer) and Gaspar Mondragón (now accomplice). Both reassignments had logged `"prose-smoothing pass errored (Unterminated string in JSON...) — deterministic-only output used"` — the Claude polish step failed and fell back to raw mechanical output; a spot check found the fallback content (Carlota's full murder confession) was actually complete and well-written, so this particular failure mode degraded gracefully. Separately, and worse: **Matilde and Aniceto were still referenced as live suspects in prose across 9 of the 13 remaining characters** — one character's final statement directly accused "Matilde" by name; several alibis referenced being "with Aniceto"; Aniceto never received a "could not attend" host note at all (Matilde did, so this wasn't the same missing-note gap from Addendum 4 — a third, independent gap). This package had been delivered to a real customer for 6 days.

Root cause of the composite-name gap: this product also uses a second removed-character naming convention beyond the "/" dual-gender form — "Real Name - PlayerNickname" (e.g. "Aniceto de Monteverde - Luis", noted in ADR-0088's 2026-08-22 addendum for a different reason). `nameVariants()` never generated the bare "Real Name" portion (without the nickname suffix) — the ONLY form this generator's own dialogue ever actually uses. Fixed by adding that variant (`dashMatch` in `nameVariants()`), in the same deploy as the `nameShape` fix. Deployed `adapt-mystery-apply` v15, `verify_jwt: true` preserved.

**Fixed for the live package:** re-ran the corrected `dropBlocksTargeting()` logic directly against the package (39 blocks dropped, $0 — deterministic, no LLM call), added Aniceto's missing host note (matching the existing English-language template `absentParagraph()` already uses for Matilde's note in the same package — host notes are English by design regardless of package language, an easy mismatch to introduce by hand, caught before shipping), then ran one targeted Claude Sonnet 5 pass (only the 9 affected characters × their specifically-flagged fields, not full-character resends — $0.15) to rewrite the remaining prose-level Matilde/Aniceto references coherently. Verified: 0 residual mentions of either removed character beyond one host note each; murderer/accomplice role counts both exactly 1; Carlota's own edited alibi-deflection paragraph re-read for coherence and no premature self-incrimination; Genoveva's final statement — which had wrongly accused the departed Matilde by name — now describes the qualifying evidence without naming anyone, which happens to correctly (if implicitly) point at the real murderer Carlota without spoiling the reveal, an improvement over the original.

**Not done:** proactively contacting `esj@salgados.net` about the 6 days their package was live with these defects — Jonathan's call, not made here. A corpus sweep only covers `status = 'verified'` rows; `adapt-mystery-create` (the create-time player-count adjustment path, separate from `adapt-mystery-apply`) was not checked and may have its own instance of either bug if it shares any of this code.

## Addendum 6 (2026-08-30): a character with zero accusations content, invisible to `package_completion_blocking_defects()`

Sweep on "Casa Ferrel" (`704cfef9-eb77-424c-abab-8e12652c3735`, 9-player slip-style with accomplice, English, generated same-day post-Sonnet-5-upgrade). All three scoped detectors and `package_completion_blocking_defects()` came back clean. A manual per-character completeness pass (checking every content column across all 9 `mystery_characters` rows, not just spot-checking 2-3) found Grant/Gracie Whitfield's `accusations` and `accusations_pointform` both `NULL`, while all 8 other characters had both populated — meaning that character, if drawn, would have had no deflection-tip guidance for the Accusations round.

Root cause of the detector blind spot: `package_completion_blocking_defects()` operates at the package level and was never designed to validate per-character column completeness across all 9 rows individually — the same category of gap already documented for the other three scoped detectors in the main body of this ADR, just on a different table/column shape. No corpus-wide sweep was run to check whether other packages have the same single-character gap on this or other columns; this is the first confirmed instance.

**Fixed:** backfilled both fields directly via SQL, written to match the "IF YOU DREW THE GUILTY/CULPRIT SLIP — DEFLECTION TIPS" format and voice already established by the other 8 characters, grounded in Grant/Gracie's own background/secret (political consultant, Porto photograph leverage), established allies/rivals (Otto/Odette ally; Ren/Fiona and Iris/Ivan rivals), and their existing Round 2-4 guilty-branch scripts (bar-cart proximity, unaccounted ~20 minutes after the toast). Re-verified: all 9 characters now have both fields populated. No detector or pipeline code was changed — treated as a one-off content gap in a single package rather than a systemic bug, since this is the first occurrence and the mechanism that dropped it is unknown.

**Not done:** no corpus-wide sweep for other packages with the same per-character null-content shape; no new automated detector for per-character content completeness.

**Update (same day):** both gaps closed properly. See [ADR-0113](0113-completion-gate-check-all-character-fields.md) — expanded `validate_package_characters()` to check the full field set instead of just `description`/`character_role`, closing the detector blind spot named above. Testing that fix against this already-"fixed" package found a *second* gap the manual sweep had missed: Grant/Gracie Whitfield was also missing `rumors`. Backfilled the same way; package now fully clean under the new systematic check.

## Addendum 7 (2026-08-30): ADR-0113's own field list was also hand-picked — found a genuinely new bug class (`secret` vs `secrets`), plus the sweep's comparison method has a structural blind spot of its own

Jonathan asked, reasonably, whether the Addendum 6 miss was itself systemic — it was: the "manual completeness check" that missed `rumors` was built from a remembered list of fields, not the actual `information_schema.columns` output, even though that full list had already been pulled once earlier in the same session for an unrelated lookup. Checking whether ADR-0113's own (larger, but still hand-picked) field list had the same flaw found it did: `_pointform` variants, `quick_reference`, `reveal_confession_guilty`/`reveal_confession_accomplice`, and `round{N}_questions` were never covered by the trigger's check.

Auditing those turned up a real, previously invisible bug rather than just a completeness gap. `mystery_characters` has both `secret` (singular, text) and `secrets` (plural, jsonb array) — the two live customer-facing render paths (`src/components/MysteryPackageTabView.tsx`, `src/pages/CharacterAccess.tsx`) both read `secret`; the only component reading `secrets` (`src/components/CharacterDetailView.tsx`) is never imported anywhere in the app. 39 characters corpus-wide have real secret content sitting only in the dead-code field, invisible to every customer despite passing an `IS NOT NULL` check on `secrets`.

**The more important catch:** finding this required checking for *uniform* nulls (every character in a package missing the same field), a shape distinct from the partial nulls (some characters have it, some don't) that both this ADR's manual sweep and ADR-0113's trigger check for. The "some vs. others" comparison method is structurally blind to a field that's wrong for 100% of a package's characters — it looks internally consistent. Checking directly found **12 whole packages with `secret` null on every character**, a count the partial-null method would never have produced on its own. 6 of the 12 are real paid packages (one row was internal test data): 3 (`MASKS OF DECEPTION`, `Murder at the Covid Arms Music Studio`, `MURDER ON THE WAVERLEY - 1962`) had the actual content sitting in `secrets`, recoverable with a zero-cost column copy; 2 (`The Great Candy Caper`, `Lights, Camera, Murder!`) have no secret content anywhere and would need real regeneration.

**Fixed:** backfilled `secret` from `secrets->>0` for the 3 packages with recoverable content (20 characters total, $0, no LLM call — verified via `RETURNING` on the UPDATE). Added the uniform-vs-partial-null distinction and the duplicate-column/frontend-usage-check practice directly into this ADR's checklist (steps 7-8 above) so future sweeps check both shapes and don't assume a populated "twin" column means the customer actually sees the content.

**Not done:** the 2 packages with no recoverable secret content anywhere (bundled into the broader historical-backfill discussion, age-gated per Jonathan's guidance — see the ADR-0113 follow-up); no `_pointform`-consistency investigation yet (checked once, saw a real-looking divergence — 53% populated for `introduction_pointform`/`rumors_pointform` vs. 17-23% for the guilty-branch/`accusations_pointform` fields — but didn't determine whether that reflects genuine per-field gaps or just which fields customers who requested point-form scripts actually asked for; flagged as a separate follow-up, not concluded here); no corpus-wide check for other duplicate-column pairs with the same live/dead-path split as `secret`/`secrets`.

## Addendum 8 (2026-08-31): package itself clean; found and fixed a 9-day-old systemic pointform gap on `reveal_confession_*` — closes the open thread from Addendum 7

Sweep on "The Workshop Of St. Nick" (`7ba1372d-9f16-4b21-a107-c0194370218d`, 10-player slip-style with accomplice, English, purchased same-day post-Sonnet-5-upgrade). All three scoped detectors and `package_completion_blocking_defects()` returned clean; manual victim-name cross-check, full `detective_script` read, evidence-card read, and a 2-character full-content spot-check all passed. `host_guide`/`timeline`/`preparation_instructions` null is the known 2026-04-25 static-template pattern, not a gap.

While spot-checking character content, found `reveal_confession_guilty_pointform`/`reveal_confession_accomplice_pointform` null on all 10 characters despite the source `reveal_confession_guilty`/`_accomplice` prose being fully populated and the customer having explicitly chosen `script_type='both'`. This is the exact gap Addendum 7 flagged as "checked once, saw a real-looking divergence... didn't determine whether that reflects genuine per-field gaps" — now confirmed as a genuine gap, not a customer-choice artifact. Corpus check: **13 distinct paid packages** affected, **152 of 164** characters with `reveal_confession_guilty` content missing its pointform sibling (93%), **110** missing `reveal_confession_accomplice`'s, going back to at least 2026-08-22 in the sample (the field itself shipped 2026-08-11, commit `6553b96`, ADR-0067).

**Root cause — corrected mid-investigation, worth recording since the first hypothesis was wrong and nearly became the shipped fix.** Initial read of the live Make.com blueprint (`Child (Unified)36`, fetched fresh via the Make API and confirmed byte-identical to its `temp-files/` export) found the `generate-pointform-summaries` call sitting visually before the `reveal_confession_*` upserts and concluded this was a sequencing bug. That was checking the wrong route — module 413, the one inspected, lives on route0 (`has_accomplice=false`, no `reveal_confession` fields at all). Route1 (`has_accomplice=true`, where this bug actually lives) has *two* pointform calls, both already positioned correctly, firing after the fields they'd need are written (525 after the guilty-branch upsert, 521 after the accomplice-branch upsert — the guilty upsert bundles `round2/3/4_guilty`, `final_guilty`, and `reveal_confession_guilty` together in one write, so by the time 525 fires all of them already exist). Confirmed directly: for the same character, in what has to be the same 525 call, `round2_guilty_pointform` came back populated while `reveal_confession_guilty_pointform` came back null — same batch, same call, one key silently missing from the model's JSON response. Not a timing bug; a Haiku 4.5 instruction-following gap on confession content specifically, the same failure family ADR-0074 already found and fixed (via a Sonnet 5 model swap) for a sibling call in this same pipeline. Caught and corrected before any blueprint edit was made or proposed as final; flagged the correction to Jonathan before proceeding rather than shipping the wrong fix.

**Fixed:** `supabase/functions/generate-pointform-summaries/index.ts` — split the single combined summarizer call into two: `MAIN_FIELDS` stay on Haiku 4.5 unchanged, `REVEAL_FIELDS` (`reveal_confession_guilty`, `reveal_confession_accomplice`) now get their own call on Sonnet 5, run in parallel via `Promise.all`. Two landmines guarded proactively rather than found live, both already documented in this codebase for Sonnet 5 (`regenerate-child-content/index.ts`, ADR-0074 lineage): Sonnet 5 400s on any non-default `temperature`, and needs `thinking: { type: 'disabled' }` explicitly or `content[0]` comes back as a non-text block. Also ported `regenerate-child-content`'s `escapeControlCharsInStrings()` repair pass as a fallback before the parse throws — the bullet-point output here (multiple bullets joined by literal `\n` inside one JSON string value) is exactly the shape that trips Sonnet 5's occasional raw-newline-instead-of-`\n` emission. Deployed `generate-pointform-summaries` v8, `verify_jwt: true` preserved (confirmed via the Management API, not assumed from the deploy command's own success message).

**Backfill completed later the same session.** Jonathan confirmed the packages were worth backfilling once he saw they were 0-26 days old (not the 130-333-day "party's already happened" precedent this project has declined to backfill before) — approved 145 calls, ~$1.50-2.50, after being shown the exact scope and per-call cost math. Ran as a standalone script (not the deployed edge function) calling only the Sonnet 5 `REVEAL_FIELDS` path directly, deliberately avoiding re-invoking the function's `MAIN_FIELDS` Haiku call, which would have re-spent on every already-good pointform field on every character touched — a real gap between what was quoted and what invoking the actual function would have cost, caught before running it. Required three passes (parallel-fetch/Node `undici` connection flakiness in the execution sandbox, unrelated to Anthropic — confirmed via direct `curl` succeeding when Node's `fetch` was failing at a high rate; fixed with a per-request `AbortController` timeout + retry-with-backoff, and the script re-queries "still null" fresh each run so it's naturally idempotent/resumable) — final pass cleaned up 2 characters where even Sonnet 5 dropped one of the two reveal fields from a combined response, the same failure mode the fix targets, just far rarer post-fix. **Result: all 145 characters across the 11 real packages backfilled, 0 remaining** (verified via direct query, not the script's own self-report) — the only residual nulls are in 2 unrelated internal test packages, correctly out of scope. Actual spend ≈ $1.65 across all passes (below the $1.50-2.50 estimate). Spot-checked written content for voice/coherence before declaring done.

**Not done:** no corpus-wide check of whether any *other* field in the `_pointform` family has a similar (if less severe) Haiku-drop rate — Addendum 7 flagged a 53% vs 17-23% populated-rate divergence across pointform fields generally and didn't conclude whether that's a per-field generation gap or just which customers asked for `pointForm`/`both`; today's finding confirms at least one real generation-side cause exists in that family, so the rest of that divergence should be treated as still open, not resolved by this fix.

**Follow-up the same session:** Jonathan asked why he'd received the "Generation Display Issue" alert email for this package at all, given the sweep found it fully clean. Pulled the actual `notify-generation-issue` function logs for the exact window (via `mcp__claude_ai_Supabase__query_logs`, not guessed) and found a second, independent, real bug — see the note appended to this same addendum below rather than a new one, since it's the direct consequence of investigating this same package's alert.

**Bonus finding, same session: `notify-generation-issue` false-alarmed on this exact package** — fired 3 times in under 4 minutes (08:36:29, 08:36:41, 08:40:02 UTC). The first two, with the package still 4-5 characters short, correctly self-suppressed via the existing `awaiting_empty_character_recovery` gate. The third fired a real alert to `support@mysterymaker.party` at 08:40:02 — **two minutes after `generation_completed_at` (08:38:09) and four minutes after the customer's own ready email had already gone out (08:36:26).** Root cause: that suppression gate requires `recoveryTargets.length > 0` (characters still empty *right now*) to conclude "recovery looks clean" — once generation finishes and nothing is empty anymore, that count is 0, the gate can't match, and the function falls through to its default of alerting. Finishing cleanly made it *more* likely to page a human, not less — the identical inversion ADR-0111 already fixed for `missing_round_content`, just never extended to this function's own `empty_character_content`/`missing_character_row` gate.

**Fixed:** `supabase/functions/notify-generation-issue/index.ts` — added `isFullyComplete` (package's `generation_status.status === 'completed'` AND zero empty/missing characters right now) as an alternate way to satisfy the "recovery looks clean" gate, alongside the existing `recoveryTargets.length > 0` mid-recovery case. Deliberately requires `generation_status.status === 'completed'`, not just "nothing empty this call" — a package stuck `in_progress` for an unrelated metadata reason with otherwise-healthy content should still alert; only a package the system itself considers done gets the pass. Deployed v28, `verify_jwt: true` preserved (confirmed via the Management API).

**Not done:** no backfill/retro-notification correcting the false alarm already sent (nothing to undo — it was informational, not customer-facing); no audit of how many other packages hit this same race historically (the log query only covered this one incident's window; a corpus-wide check would need querying `function_logs` for every `"Generation issue notification sent"` line and cross-referencing each package's `generation_completed_at` against its `last_notified_at`, not done here).
