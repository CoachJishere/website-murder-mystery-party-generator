# ADR-0099: delegate chain-of-thought/prose leaks to the existing auto-remediation regenerator instead of always escalating

- **Status:** Accepted
- **Date:** 2026-08-21
- **Related:** ADR-0047 (`auto-remediate-packages`, the worker this changes), ADR-0053 (the `meta_text_leak` detector, `list_packages_with_meta_text_leak`), ADR-0054 (`regenerate-child-content`, the regenerator this now delegates to for one more case), ADR-0061 (extended delegation to `identity_contamination`/`slip_culprit_leak` — this ADR follows the same reasoning one class further), ADR-0093 Addendum 6 (the incident that surfaced this gap)

## Context

Investigating why a chain-of-thought leak in Ciaran Fox's package (Psychic Sandra/Sandro's `final_innocent`, introduced by a manual re-fire during ADR-0093's remediation — see Addendum 6) sat live for ~24 hours despite `auto-remediate-packages` running every 30 minutes and detecting it within 15 minutes.

Traced the actual behavior: the worker did run, did detect it (`auto_remediation_log` shows `defect_class: template_artifact`, `action: escalate:no_mechanical_fix`, logged 2026-08-20 12:43 UTC — 15 minutes after the re-fire), and made a **documented, deliberate** choice not to attempt a fix. `stripArtifactLines()`'s own comment states it plainly: *"Chain-of-thought the meta-text detector also flags ('let me reconsider') is never touched here — it needs a rewrite, so it fails the gate and escalates, which is correct."* This is not a bug — it's ADR-0047's original scope, unchanged since.

That original scope predates ADR-0061, which built exactly the capability this gap needs: `regenerate-child-content`, a Claude-based regenerator with its own internal re-detect-and-revert safety net, already trusted to auto-fix two other judgment-heavy, no-safe-deterministic-fix defect classes (`identity_contamination`, `slip_culprit_leak`) without human review. `handleTemplateArtifacts` already delegates to it for character-scope artifacts that match a *bracketed* pattern (`[choose...]`, `[closing paragraph...]`) but can't be cleanly excised because they're embedded in real prose — the exact same "detected, judgment needed, no deterministic fix" shape as a chain-of-thought leak. The only reason chain-of-thought never reaches that same delegation path is that `ARTIFACT_TOKEN_RX`/`ARTIFACT_SPAN_RX` only recognize 3 of the 13 phrases in the SQL detector's marker regex (`\[choose`, `\[closing paragraph`, `master_context`) — the free-text phrases (`wait, i need to`, `let me reconsider`, `on second thought`, etc.) and two bracket patterns (`\[insert `, `\[if guilty`) aren't recognized as artifact candidates *at all*, so a field containing only one of them looks clean to `stripArtifactLines` and the whole package falls through to an empty plan → `escalate:no_mechanical_fix`, with no delegation attempt.

## Decision

Extend `handleTemplateArtifacts` in `supabase/functions/auto-remediate-packages/index.ts` so character-scope prose chain-of-thought leaks route through the same `delegateToRegenerator(ctx, "meta_text_leak", ...)` call already used for embedded bracket artifacts, instead of being invisible to the worker entirely:

1. Add `PROSE_LEAK_RX`, matching the SQL detector's 8 free-text alternatives (`let me reconsider|let me reread|let me recalculate|let me look at this more carefully|i need to correct this|on second thought|as an ai language model|wait, i need to`). A match on this regex has no bracket to excise, so it is *always* `safe: false` — no attempt at a span-excise, straight to the same "embedded, needs delegation" branch bare `master_context` already uses when it survives excision.
2. Add the two missing bracket patterns (`\[insert `, `\[if guilty`) to `ARTIFACT_SPAN_RX`/`ARTIFACT_TOKEN_RX`, closing the same drift for the two bracket-delimited phrases that were also silently unrecognized — these *can* attempt a clean strip first, same as `\[choose`/`\[closing paragraph`, falling back to delegation only if embedded.
3. Package-scope behavior is unchanged: `regenerate-child-content` can't write `mystery_packages` fields, so a chain-of-thought leak in `game_overview`/`host_guide`/etc. still escalates — this ADR only closes the character-scope gap, matching the existing scope boundary `handleTemplateArtifacts` already draws for bracket artifacts.
4. Updated the function's stale doc comment (which asserted the old behavior was "correct") to describe the new routing and link back to this ADR.

## Rationale

- **The safety net already generalizes.** `regenerate-child-content`'s re-detect-and-revert gate doesn't inspect *why* it was called — it re-runs the same detector after regenerating and reverts if the result still fails. It was already trusted for two defect classes at least as judgment-heavy as a chain-of-thought leak (ADR-0061's own framing: "judgment-heavy, no safe deterministic fix"). Extending it to a third, structurally identical class is not a new risk surface — it's applying an already-proven pattern to a class arbitrarily left out.
- **Same caps, same everything.** No new spend cap, attempt cap, or code path — `delegateToRegenerator` already enforces `MAX_ATTEMPTS_PER_DEFECT` (2) and the shared `$10`/day cap independent of which defect class invoked it.
- **Closes the actual gap Jonathan asked about.** The scheduled health-check bot already detects these fast and reliably (~15 min in this incident) — the missing piece was purely that detection didn't lead to action, forcing a human to notice a GitHub issue comment before anything happened. This makes the existing fast detection do something on its own.

## Alternatives Considered

- **Build a new "self-heal on health-check alert" pipeline**, reacting to the 6-hourly `list_packages_with_meta_text_leak` scan directly. Rejected: redundant with `auto-remediate-packages`, which already runs 12x more often (every 30 min vs. every 6h) and already has the detection + delegation infrastructure — the health-check's job is to catch what `auto-remediate-packages` couldn't fix and needs a human, not to duplicate its remediation logic.
- **Immediate notification on `escalate:no_mechanical_fix`** instead of extending delegation (the "something more conservative" option considered and declined). Rejected for this incident's specific defect class since delegation can just fix it outright; a per-escalation notification remains a reasonable *general* improvement for defect classes that stay genuinely human-judgment-only (structural defects, roster-count mismatches — see ADR-0064's explicit "not something to guess-fix automatically" reasoning, which this ADR does not revisit or weaken), but is out of scope here.
- **Widen `stripArtifactLines`'s span-excision to attempt rewriting chain-of-thought text directly** (e.g. regex-trim the sentence containing the phrase). Rejected: a prose leak has no clean boundary the way a bracketed authoring note does — trimming risks the exact "gutted prose the re-detect gate can't catch" failure mode the file's own header warns about. Delegating to an actual rewrite (Claude regeneration with re-detect+revert) is the correct tool, already built, already scoped for exactly this shape of problem.

## Consequences

- **Positive:** a chain-of-thought leak reintroduced by any future manual re-fire (the standard recovery tool throughout ADR-0089/0093/0095/0096/0097) now has a real chance of self-healing within 30 minutes instead of sitting live until a human notices a health-check alert.
- **Not addressed:** why the roster-count-mismatch alert (the other 2026-08-21 health-check finding, unrelated to this defect class) first appeared a day after its underlying fix (ADR-0095) landed instead of the very next cycle — flagged in ADR-0095's addendum as unexplained, not investigated further here.
- **Not addressed — deliberately, per Alternatives:** structural defects and roster-count mismatches remain escalate-only by original design (ADR-0064's "not something to guess-fix automatically" — regenerating the wrong characters, or in the wrong order, could compound the problem in a way a content rewrite cannot). This ADR does not touch that boundary.
- **Verification:** `stripArtifactLines` isolated and unit-tested against 10 cases (Sandra's actual leaked text, clean text, both existing bracket-strip/embedded behaviors unchanged, all 5 bracket patterns, all 8 prose phrases) — 10/10 pass, confirming no regression to the existing bracket-artifact path. `esbuild --bundle` confirms the deployed file compiles. Post-deploy (v10), a live `dry_run: true` call against production completed with zero errors and zero currently-flagged packages (expected — this session already remediated the only live instance). Did not build a full synthetic DB fixture exercising `delegateToRegenerator` end-to-end against a live character row — the changed surface is isolated to `stripArtifactLines`'s pure classification logic, and the downstream delegation/re-detect/revert path it now reaches is pre-existing, unmodified infrastructure already proven for `identity_contamination`/`slip_culprit_leak`. Worth a real fixture test if this pattern needs touching again.
