# ADR-0098: "Remove a Character" batch got permanently stuck; manual recovery + two real transform bugs found

- **Status:** Accepted
- **Date:** 2026-08-20
- **Related:** ADR-0091 (feature rename), ADR-0036/0082/0088 (original build, batching, murderer reassignment), ADR-0064 (roster-mismatch detector), ADR-0097 (missing-character-row auto-recovery — the second system this addendum makes aware of deliberate removal)

## Context

Lyn DiFranco (lyn.difranco@montana.edu) paid $5 to remove 9 characters from her mystery package (batch `336b5b8b-078f-4ffb-bb47-2a561d7ab675`, package `a0a985a9-2d2d-4176-a825-82ee6b2990be`) and emailed hours later — "still reads 0 of 9 updates. I need to send out my links today."

`stripe-webhook` had processed the purchase correctly (all 9 `mystery_adaptations` rows marked `paid`, confirmation email sent) and dispatched `adapt-mystery-apply` for batch_sequence 0. That single invocation claimed the row into `status: 'processing'` and then never reached a terminal state — no `completed_at`, no `error_message`, no `console.error` anywhere in `function_logs`. Chain-dispatch (the *only* mechanism that advances a batch — see ADR-0088) lives in the function's `finally` block, which a dead invocation never reaches, so the entire batch was silently orphaned: row 0 stuck in `processing`, rows 1-8 never even attempted.

## Decision

**Immediate customer fix:** bypassed the edge function entirely. Wrote a local Node script (`scripts/_incident-manual-remove-characters.mjs`, gitignored via the repo's blanket `*.mjs` rule, deleted after use) that replicates `adapt-mystery-apply`'s deterministic transform logic byte-for-byte — same field lists, same `nameVariants`/`dropBlocksTargeting`/`substituteVariants`, same snapshot-write-verify-or-revert gate, same `mystery_adaptations` schema — and ran it directly against production via the service role key, one row at a time, no chain-dispatch, no Anthropic call. All 9 characters removed and verified; 0 references to any of the 9 target characters remain anywhere in the package; all 9 `mystery_adaptations` rows are `status: 'verified'`.

**What actually blocked the first attempts wasn't one bug — it was three, stacked:**

1. **The hang itself (root cause still open).** Added `AbortSignal.timeout(45_000)` to both Anthropic `fetch` calls in `adapt-mystery-apply` (`polishWithClaude`, `reassignWithClaude`) on the theory that an un-timeout'd network call was the stall. Deployed it, retried — **the retry hung too**, sitting in `processing` for 3+ minutes, well past the 45s cap. Ruled out: a leaked/blocking Postgres session (`pg_stat_activity` showed nothing holding a lock), the package-level claim (`adaptation_claimed_at` was `null`), and a stale cached function instance (redeployed, confirmed via `get_edge_function` that the running source contains the fix). The timeout fix is deployed and is a real improvement regardless, but it did **not** explain or fix this specific hang. Cause remains unknown — see Consequences.
2. **`secrets` field shape bug (found, fixed in the manual script only).** `secrets` is a jsonb **array** wrapping one markdown string per character — confirmed via `pg_typeof` + direct value inspection — the same real shape `evidence_cards` already has its own special-cased handling for (`isSingleStringArray`). The deployed function's `PROSE_JSONB_FIELDS` handling only checks `isJsonbString` (plain string), so every array-shaped `secrets` field was silently skipped during transform, then correctly caught by the verify gate afterward — causing an otherwise-clean removal to roll back.
3. **Bare-surname substring false-positive (found, fixed in the manual script only).** `buildVariantRegex` joins name variants with no word-boundary. The bare-surname fallback (e.g. "Cross" for Dr. Finley/Fiona Cross) matches as a raw substring — confirmed live: `"across department meetings"` and `"p-hacking across multiple studies"` both matched variant `Cross`. Every surname that's also a substring of a common word (Cross→across, Price→price, likely others) triggers spurious verify failures and would corrupt PROSE-field substitutions if the same false match occurred during the transform step itself, not just verify.

Bugs 2 and 3 together explain 5 of the first 9 rows rolling back on the first real attempt; fixing both (word-boundary regex, `isSingleStringArray` treatment for `secrets`) in the manual script's copy let all 5 complete cleanly on retry. **These two fixes were not ported back to the deployed `adapt-mystery-apply/index.ts`** — only the `AbortSignal.timeout` addition was. The next real "Remove a Character" purchase will hit the same two bugs (safely — the verify-or-revert gate means a customer sees a rolled-back, not corrupted, character — but the purchase still won't complete without another manual intervention like this one).

## Rationale

- **Bypass over further live debugging** because the customer needed her links "today" and I had already burned two failed retry cycles (roughly 10 minutes of TTL waiting each) chasing a hang whose cause wasn't converging. Re-running the *exact same tested transform logic* locally, minus the one unexplained dependency (the live edge function's async/network environment), was lower-risk than a third blind retry or a deeper live debugging session with a customer waiting.
- **Reused the deployed logic instead of writing new removal logic from scratch** — copy-pasted the pure functions and field lists verbatim from `index.ts` rather than reimplementing the transform, so the manual run carries the same tested behavior and the same verify-or-revert safety property, not a parallel implementation that could diverge or be less safe.
- **Fixed bugs 2 and 3 only in the manual script, not the deployed function**, deliberately — both were discovered under real customer-data time pressure and verified against exactly one package. They're correct and narrow, but "verified once, live, under pressure" is a lower bar than this codebase normally holds for shipping an edge function change (see `feedback_adr_practice` — non-trivial changes get proposed before code). Landing them in the deployed function is a five-minute follow-up, tracked here rather than done silently in the same breath as an emergency fix.

## Alternatives Considered

- **Wait out the TTL and keep retrying the deployed function as-is.** Rejected after the second hang — no evidence the outcome would differ on a third attempt, and the customer had a same-day deadline.
- **Temporarily unset `ANTHROPIC_API_KEY` as a Supabase secret** to force the deterministic-only path through the real deployed function (chain-dispatch and all). Considered, rejected: a global secret change affects any other concurrent invocation of this function (low but non-zero risk given multiple agent sessions were active in this repo at the time — see the shared-checkout hazard already in project memory), and doesn't explain why the *first* invocation (before the timeout fix existed) also hung — the theory only ever explained a possible re-hang, not the original one. The eventual local-script approach avoids touching any shared production configuration at all.
- **Redeploy the code with bugs 2 and 3 fixed immediately, under emergency pressure.** Rejected in favor of documenting them here and shipping as a reviewed follow-up — the customer fix didn't require it (the manual script already had both fixes), so there was no urgency forcing that trade-off.

## Consequences

- **Positive:** Lyn's batch is fully complete — 9/9 `mystery_adaptations` rows `verified`, 0 references to any removed character remain anywhere in the package (checked directly, not inferred from the adaptations table).
- **Positive:** two real, previously-unknown transform bugs found and confirmed against live production data (not hypothetical) — `secrets` array-shape handling and the bare-surname word-boundary gap.
- **Not addressed — open, needs its own investigation:** why the invocation hangs at all, even with a 45s `AbortSignal.timeout` in place. This is the one item that still makes `adapt-mystery-apply` unsafe to rely on unattended for the next real purchase — a customer could hit the same "0 of 9, hours later" experience again. Candidates not yet ruled out: something in the Supabase Edge Runtime (v1.74.3, per the file's own header comment) not honoring `AbortSignal` on this particular `fetch` path; a genuinely slow/queued Anthropic response that legitimately exceeds even 45s under real load (worth instrumenting with a timestamp log at each await point rather than guessing further); or an entirely different await earlier in the function that isn't network-bound at all.
- **Not addressed — tracked, not urgent:** bugs 2 and 3 need porting from the manual script into `supabase/functions/adapt-mystery-apply/index.ts` and redeploying, with the same word-boundary and `isSingleStringArray`-for-`secrets` fixes. Low risk, well-understood, already validated against real data — but deliberately not rushed into production in the same motion as the emergency fix.
- **Neutral:** the file's own header comment still says "STAGING ONLY" despite having processed a real `cs_live_...` charge as far back as this incident's original purchase — stale, not caused by this incident, worth fixing whenever bugs 2/3 are ported.

## Addendum (2026-08-21): systemic fixes ported, root-cause research, reclaim sweep drafted

Followed up on the three open items.

**Ported all three found bugs into the deployed `adapt-mystery-apply`, redeployed:**
1. Word-boundary regex (`\b${escapeRegex(v)}\b`) in `buildVariantRegex` — the bare-surname substring false-positive from the original incident.
2. `isSingleStringArray` handling for `PROSE_JSONB_FIELDS` (`secrets`), mirroring the existing `evidence_cards` treatment — the array-shape bug.
3. **A third, more serious bug found while fixing (1) and (2):** the `variantRegex.test(JSON.stringify(current))` call in the non-string-jsonb branch of the `secrets` handling was the *only* `.test()` call anywhere in the file that didn't reset `variantRegex.lastIndex` afterward. Since `variantRegex` carries the global flag and is reused across every later scan in the same invocation (including the verify gate), a stale `lastIndex` left behind by that one call could make a *later* `.test()` on a *different* string start mid-way through it — silently missing a real match. Unlike bugs 1 and 2 (which only ever caused an unnecessary rollback), this one could in principle let a stale reference to a removed character pass verify undetected. Fixed by adding the same `variantRegex.lastIndex = 0` reset every other call site already has.
4. Also corrected the file's stale "STAGING ONLY" header comment (it has been processing real `cs_live_...` charges since at least this incident).

Verified via `esbuild --bundle` (clean, no syntax errors) before deploying. Deployed via `supabase functions deploy`.

**Root-cause research on the hang itself (still not 100% confirmed, but converged on a credible explanation):** Supabase's own troubleshooting docs and community discussion threads describe Edge Functions as capped at roughly 150s of wall-clock time per request unless the work is wrapped in `EdgeRuntime.waitUntil` — `adapt-mystery-apply`'s main body isn't (only its fire-and-forget chain-dispatch/email calls are). MDN separately notes `AbortSignal.timeout()`'s timer runs on "active," not strictly elapsed, time, and can be paused if the worker itself is suspended. Together these support a working theory: the platform's own supervisor abruptly kills the isolate around ~150s in (especially likely if the Anthropic call is slow), and that kill is external to the JS runtime — it bypasses `try`/`catch`/`finally` entirely, so nothing ever flips the row's status or fires chain-dispatch, regardless of whether `AbortSignal.timeout` would otherwise have worked. This would explain every observed symptom (no error logged, `finally` never runs, row stuck indefinitely) without requiring `AbortSignal` itself to be broken. Not proven — would need a live reproduction with full step-timestamped logging to confirm definitively, which weighs a real (if small) Anthropic spend against a fix that doesn't actually depend on knowing the exact cause (see below). Not pursued without owner sign-off on that spend.

**Drafted, then applied with sign-off, a cause-agnostic safety net:** `supabase/migrations/20260821_sweep_stuck_adaptation_batches.sql` — a `pg_cron` sweep, run every 10 minutes, that finds any `mystery_adaptations` row stuck in `processing` past the function's own 10-minute claim TTL and re-invokes `adapt-mystery-apply` for it. This doesn't require knowing *why* an invocation dies — it just guarantees a stuck batch self-heals within ~10-20 minutes instead of requiring a customer to notice and email in, the way this incident actually played out. Mirrors `sweep_stuck_needs_review_packages.sql`'s exact shape and `20260729_schedule_auto_remediate_packages.sql`'s vault-secret pattern for the service-role bearer token (confirmed the `service_role_key` vault secret already exists). Per ADR-0092's established policy (any cron touching a paid-package table needs explicit owner sign-off before running unattended — it rejected a similarly-shaped sweep on exactly that basis once before), presented this to Jonathan for sign-off before applying; approved 2026-08-21. Applied via `mcp__supabase__apply_migration` (the CLI's `supabase db push` failed on a long-standing, unrelated local/remote migration-history drift in this project — not touched, applied directly instead). **Confirmed live**: `cron.job` shows `sweep-stuck-adaptation-batches`, schedule `*/10 * * * *`, `active: true`.

**Housekeeping found along the way:** the ADR's own filename tripped this repo's `*BATCH*.md` `.gitignore` rule (meant for scratch/working docs, case-insensitive match on macOS caught the word "batch" in the title) — the file existed on disk and was fully written, just silently untracked by git. Force-added it (`git add -f`); flagged to Jonathan that the pattern is broad enough to silently swallow any future ADR whose title happens to contain "batch" (a live word in this codebase — see ADR-0088's own "batching").

## Addendum 2 (2026-08-21): the hang's actual root cause, confirmed live — superseding the wall-clock-kill theory

With owner sign-off (~$0.05–$0.25 approved Anthropic spend), built a throwaway test package (4 characters, seeded directly via SQL, `conversations.is_test = true`) and a matching `mystery_adaptations` row, added temporary step-by-step timestamped logging to `adapt-mystery-apply`, deployed it, and invoked it directly.

**Reproduced the hang on the very first attempt**, on trivial test content — this alone was informative: it isn't specific to the real customer's large/complex prose fields. The evidence, all confirmed directly:

- Exactly **one** execution ever ran for that `adaptation_id` (one `execution_id` in `function_logs`, filtered by `function_id`).
- That execution logged "invocation start," then "finally block entered" only **442ms** later, then a normal idle isolate `shutdown` ~3 minutes after that (unremarkable — just a warm isolate timing out from disuse, not evidence of anything hung).
- `pg_stat_activity` showed **zero** active backend connections touching this data at any point after that — nothing was actually computing anything server-side.
- Direct inspection of the test characters showed **no writes had happened at all** — the transform/write logic never ran.
- Yet the `mystery_adaptations` row was genuinely `status: 'processing'`, with `processing_started_at` matching that single execution's own start timestamp to the millisecond.

The only way to reconcile all five facts: the claim step's `UPDATE ... RETURNING` **committed in Postgres**, but its acknowledgement (the returned row) never made it back to the running code. The code's own view was `claimed: null` — indistinguishable, from inside the function, from "someone else already owns this row" — so it took the fast "not claimable" exit and abandoned a row it had, in fact, just written. This has nothing to do with a slow Anthropic call, a 150s platform wall-clock limit, or `AbortSignal` — that whole code path (and the `AbortSignal.timeout` fix from Addendum 1) is downstream of this and never runs. The earlier wall-clock theory was a reasonable inference from the *original* incident's timeline (hours, not milliseconds) but the live reproduction shows the actual failure is instantaneous, at the very first database call.

**Fix, deployed:** after a null claim result, do one verification `SELECT` by id. If the row is already `processing`, has no `completed_at`, and its `processing_started_at` is not older than the moment this attempt started, that can only be explained by our own just-committed, lost-acknowledgement write (a genuinely different claimant — a real second invocation, or a stale TTL-expired row — could never produce a `processing_started_at` newer than when this attempt began). Treat that case as ownership and proceed instead of abandoning the row. Even in the theoretical worst case of two execution paths both reaching this recovery branch for the same row, the pre-existing package-level claim (`claim_package_for_adaptation`, ADR-0088) is a second, independent lock — at most one of them can actually write, the other harmlessly defers back to `'paid'`. No new data-corruption risk.

**Verified the fix live**: reset the same test row past its TTL, re-invoked under the deployed fix. This time the invocation ran for **9.7 seconds** (a real Anthropic polish call, not a 442ms fast-exit) and reached genuine business logic — it hit an unrelated, expected failure (my test conversation's `player_count` was too low for `conversations_player_count_check`, a test-data gap, not a bug) — but critically, it failed **cleanly**: `status: 'failed'`, a clear `error_message`, no orphaning. That's the fix working as intended: real progress instead of silent abandonment.

**Minor incidental finding, not fixed (out of scope):** the `catch` block sets `status: 'failed'` and `error_message` but never sets `completed_at` — a small audit-trail gap, harmless (the sweep only checks `status`), noted for whoever next touches this function.

Cleaned up all test data (conversation, package, 4 characters, adaptation row) — zero remnants confirmed.

## Addendum 3 (2026-08-21): fixing Lyn's package surfaced a SECOND, live incident — the removal got silently undone by an unrelated health check

Hours after Addenda 1/2 shipped, Lyn emailed again: "today in my dashboard only the mystery with 25 guests is available" — her party is tomorrow. Investigated her account directly (not from memory of the earlier fix): her package (same `a0a985a9-2d2d-4176-a825-82ee6b2990be`) had 25 `mystery_characters` rows, and all 9 characters she'd paid to remove were present again, with fresh `created_at` timestamps from *this morning* — not the originals.

**Root cause: a completely different feature, not a regression in anything from Addenda 1/2.** This repo's roster-count-mismatch health check (`scripts/detect-roster-mismatches.mjs`, ADR-0064, runs every 6 hours via `.github/workflows/health-check.yml`) diffs each paid package's *originally approved* character count against its *current* `mystery_characters` row count, with zero awareness that "Remove a Character" (ADR-0036/0082/0088/0098) can legitimately shrink that count. It flagged Lyn's now-correct 16-character package as "16 of 25 approved characters" — a real-looking defect — and a Claude session responding to that health-check alert manually re-fired the 9 "missing" names at `CHILD_WEBHOOK`, regenerating exactly the 9 characters she'd paid to remove. Confirmed via direct inspection: `auto_remediation_log` has zero rows for this package, so the *automated* ADR-0097 recovery path did not fire — this was a human/agent acting in good faith on a detector that doesn't know `mystery_adaptations` exists.

**Immediate fix:** deleted the 9 wrongly-regenerated rows (confirmed zero `character_assignments` pointed to any of them — none of Lyn's already-claimed guest links were at risk) and confirmed `mystery_packages`/`conversations.player_count` were untouched by the regeneration (only the character rows were re-inserted), so no other repair was needed. Also inserted an `acknowledged_health_alerts` row for this package/`roster_mismatch` as an immediate belt-and-suspenders suppression ahead of the code fix below.

**Systemic fix — both places a name can look "missing" without being a bug now consult `mystery_adaptations`:**
1. `scripts/detect-roster-mismatches.mjs` — expected count is now `approved_roster_count - verified_removal_count` (a `mystery_adaptations` count where `status = 'verified'`), not the raw approved count. Verified live against production: zero false positives across every paid/completed package in the last 30 days, including Lyn's (correctly reports no mismatch at 16).
2. `supabase/functions/notify-generation-issue/index.ts` — the `missingCharacters` diff (ADR-0097's actual auto-fire trigger) now excludes any name with a `verified` `mystery_adaptations` row, exactly like an existing row. This is the more dangerous of the two paths (it fires `CHILD_WEBHOOK` with zero human review), and closing it protects against a *different* future trigger than today's actual incident (e.g. a Remove-a-Character package that later, coincidentally, enters `needs_review` for an unrelated reason). Also fixed the alert email's own "X generated / Y expected" line to subtract deliberate removals, so a human reading a *different* genuine alert on such a package is never shown a number that would tempt them into repeating today's mistake by hand.

Both changes verified via `esbuild --bundle` / `node --check` before deploying; the roster-mismatch fix additionally verified with a real run against production data (see above). Deployed `notify-generation-issue` v26, `verify_jwt: true` preserved.

**This closes the loop generally, not just for Lyn.** Both the human-facing detector that actually caused today's incident and the separate automated recovery path that could cause the same damage a different way are now both aware that "gone" can mean "customer paid for that," for any future Remove-a-Character purchase — not a one-off patch scoped to her package.

## Addendum 4 (2026-08-21): content-quality audit of Lyn's package — found and fixed real coherence bugs, unrelated to Addenda 1–3

Cleaned to `"Rowan/Rory Hartwell"`; the twin relationship is already explained in her own background/introduction text, so no narrative content was lost.

All fixes applied as targeted `UPDATE`/`replace()` statements against `mystery_packages` and `mystery_characters` (not a regeneration — every remaining character's otherwise-good content was left untouched). ## Addendum 5 (2026-08-22): is this systemic? Checked 5 weeks of packages, fixed 6 more, patched the two detectors that missed all of it

ADR-0074 itself named "victim mismatches" as one of the defect classes Haiku's weaker instruction-following was suspected to cause. Swept every paid package's delivered text (game_overview, detective_script, host-facing fields, and every character field) for the same defect family — leaked authoring instructions and unfilled template placeholders reaching player-facing content — across the last 5 weeks, then validated the pattern against full history back to 2026-04-01.

**Found and fixed the same defect family in 6 more packages, all created 2026-07-20 through 2026-08-04 (all pre-upgrade):**
- **Death By High Tea: Murder At The Velvet Shaker** — Phoenix/Phoenicia Hart's relationships had `[Note: This would be the victim, so per rules, not included in rivals list]` instead of real content; every other character in the package has a real paragraph in this slot. - **Death At The Birthday Bash: A Speakeasy Soirée Turned Deadly** — two instances: Matt LeVora's relationships had `[Note: Victim. Do not list here per rules.]` (wrote real content from his background); Lindsay Stafford's had the leak wrapped *around* real content (`[This is the victim and cannot be listed as a rival per the rules, but the tension is the core of your motive: ...]`) — stripped the wrapper, kept the motive text.
- **Death At Château Buzancy** — the detective's reveal script used raw `[Accomplice name]` / `[murderer name]` / `[accomplice name]` tokens in its final arrest lines, inconsistent with the rest of the same reveal (which never names the culprit directly, since this is a slip-style game where the culprit is drawn at the table). Rewrote those lines to not require a name, matching the established pattern.
- **The Enchanted Family Reunion Murder** — reveal script said "...placing Liene Ornicani and `[accomplice name, if applicable]` under magical custody" in a game with `has_accomplice: false`. Removed the dangling clause.
- **Death At Thornfield Manor: The Matriarch's Last Birthday** — two instances: the reveal script had a literal leaked authoring note, `[ACCOMPLICE BEAT — Note: There is no accomplice in this case. This beat is omitted.]`, in a game with no accomplice — deleted the note entirely (correctly, no beat needed). Separately, Fitzwilliam/Fiona Blackwood's relationships had `[The victim is never included in relationships per the rules. This section addresses other hostile relationships only.]` — wrote real content from their background.
- **Birthday Betrayal In Hot Springs** — Kiana's and Dylan's `accusations` fields had generic illustrative example text with bracket placeholders (`'I think [suspect name] did this because [...]'`) that the other 5 non-featured characters in the same package didn't have (they just get the clean base instruction). Lower severity than the others — read as guidance rather than a broken template — but inconsistent within the same package, so normalized both to match the clean baseline the majority already uses.

**Important finding that changes the shape of any future automation here:** `[MURDERER NAME]` / `[Suspect Name]` bracket placeholders are NOT always a bug. *Death At Hollowcrest Manor* and *Blood At Dead Man's Canyon* (older packages, outside the 5-week window, checked only to validate this) both use `[MURDERER NAME]` deliberately — in a slip-style ("character") game the culprit is drawn at the table, so the script genuinely cannot know the name at generation time, and the host is expected to write it in when running the game. This means a detector (or an auto-fix pass) that blanket-flags bracket-name patterns would false-positive on legitimate scripts. Deliberately did NOT add `[murderer`/`[suspect`/`[accomplice` as new detector markers for this reason — only the phrases with zero legitimate use anywhere in history (see below).

**Existing detectors (health-check 6–9, ADR-0042) caught none of this** — `list_packages_with_meta_text_leak` and `list_packages_with_victim_mismatch` both returned zero hits across the whole window, including on Lyn's package before it was fixed. Traced two real coverage gaps and patched both (`supabase/migrations/20260822_patch_content_quality_detectors.sql`):
1. `meta_text_leak`'s marker list didn't include the "per (the/content) rules" / "not included in" / "[VICTIM" leak family found today. Validated the new markers against every completed package back to 2026-04-01 before shipping — zero legitimate hits anywhere in history (unlike the murderer/suspect brackets above). One self-caught bug during validation: an early version of the new `accomplice beat` marker matched `"your accomplice Beatrix"` (a real character name) as a bare substring — the exact "Cross"/"across" hazard already known from earlier in this ADR. Fixed with a word-boundary (`accomplice beat\M`) before shipping.
2. `victim_mismatch`'s extraction regex required the victim's name to be the literal first "First Last" pair immediately after the "Game Overview" heading — missed every overview that opens with a narrative sentence first (the common case, including Lyn's). Added two fallback extraction patterns. **Known remaining limitation, not fixed**: the function's core check only catches a victim name that's foreign to the whole package (absent from `master_context` and every character). It does NOT catch Lyn's actual failure mode — a victim surname that's wrong but legitimately belongs to a different, living character in the same package (so it's never "absent" from `master_context`, which holds the full original roster). Closing that gap needs a different check (e.g. majority-vote of what characters' own relationships sections name as their antagonist) — flagged in the migration's own comments as an open design question, not built today.

**Also surfaced, not chased further (deliberately, to avoid unbounded scope creep):** re-running the patched detector against full history (back to 2026-04-01, beyond the 5-week window this audit was scoped to) found one more, older, unrelated leak (`Murder At The TLC Reunion`, character background literally saying "Reference the timeline from master_context" — April 2026) and confirmed a separate, pre-existing false positive already in the *original* marker set (`[choose a name or leave blank for host to personalise]` — a legitimate host-customization feature for the detective's own name, not a leak, mismatched by the existing `\[choose` marker). Neither is fixed here — flagging both for a scoping decision rather than unilaterally continuing to excavate deeper into history.

**Recommendation on where this goes next** (Jonathan's question: bake into the Make.com prompt, build new automation, or keep doing this manually): leaning toward **neither new automation nor a Make.com prompt change** — the defect class looks cleanly isolated to the pre-2026-08-11 Haiku era (zero hits in any of the 12 packages generated since the upgrade, across every check run today), and today's fixes needed real per-hit judgment (write real content vs. delete vs. rephrase; distinguishing an actual leak from an intentional host-fill-in convention) that a blind auto-fix pipeline would get wrong. The patched detectors are enough as passive, already-existing infrastructure (health-check.yml, read-only, zero new automation surface) to catch a recurrence if the upgrade doesn't fully hold.

## Addendum 6 (2026-08-22): went back further (full history, not just 5 weeks) — found and fixed a real bug in my own patch along the way

Jonathan asked whether to widen the sweep further, since Lyn's original party was booked well in advance and other customers might not have played their mystery yet either — "last 2-3 months, or even 3." Checked what that actually means in data before picking a window: **121 paid packages predate the 2026-08-11 Sonnet 5 upgrade** (not just the last 5 weeks — the earliest paid package is from 2025-07-20), and **88 of those 121 have never had guest links sent to anyone** (`character_assignments.is_sent` is false or absent for every row) — a lower-bound signal that the party hasn't happened yet, independent of how long ago the package was generated. A fixed calendar window doesn't actually match either axis that matters (when the defect can occur, or whether anyone's read the content yet), so re-ran the two patched detectors — cheap, already built, no reason to guess a cutoff — across every completed package back to 2025-01-01 instead of picking a number of months.

**Caught a real bug in the patch I shipped two hours earlier, before it caused a false negative anyone would notice.** The `per (the|content)? rules` marker never matched anything in production: PostgreSQL's regex flavor (ARE) treats `\b` as a literal BACKSPACE character, not a word boundary — `\M` is the correct end-of-word metacharacter, which I'd used correctly elsewhere in the same migration (`accomplice beat\M`) but not here. Caught it by re-testing the marker in isolation during this pass rather than trusting the "zero hits" result at face value. Also found and removed a second issue: the `\[victim` marker (added in the first patch) false-matched `[victim's name]` — a legitimate template token used in the round2/3/4 `_innocent`/`_guilty`/`_accomplice` branching-format fields, which the original validation pass hadn't checked (it only covered the unified script fields). Confirmed removing `\[victim` loses no real detection — every true positive found so far is independently caught by `per rules` or `not included in` in the same bracket — so removed it rather than trying to patch around the false positive. Both fixes applied directly (`CREATE OR REPLACE FUNCTION`, not a new migration file, since the previous one hadn't been in production long enough to matter).

**Re-running the corrected detector across full history surfaced 8 more real, confirmed hits — none newly exposed by the regex fix (the list was identical before and after, other than the `\[victim` false positive dropping out), all pre-2026-08-11, spanning 2025-10-23 through 2026-04-22:**
- Seven packages (*The Dark Side Of DevOps*, *The Last Call At The Lucky Crown*, *1950s - 17 Players*, *Blood And Bouquet: A Christmas Conspiracy In The Mountains*, *Death On The Queen Anne: A Christmas Crossing*, *Deadly Vintage: Murder In The Troodos*, *Death At The Birthday Bash*) each had exactly one character whose `accusations` field embedded a `[choose someone with strong motive...]`-style bracket in the middle of an otherwise fully-written, evidence-specific accusation paragraph — same family as Kiana/Dylan (Addendum 5), but here the surrounding paragraph was real, specific content worth keeping (references actual clues: oleander poisoning, WebAssembly deployment access, the freezer's temperature control), so fixed by rephrasing just the bracketed clause into natural prose ("whoever the evidence points to most clearly") rather than replacing the whole paragraph with the generic baseline.
- *Murder At The TLC Reunion* — the one flagged-not-fixed item from Addendum 5 — turned out to be a leaked internal instruction in `round4_innocent`, not `accusations`: `*Provide your alibi and defend yourself against accusations about opportunity. Reference the timeline from master_context.*` sitting above otherwise well-written dialogue. Deleted the leaked line; the dialogue underneath needed no other changes.
- Confirmed *Death At The Birthday Bash* (2026-01-16) already had its party — guest links sent 2026-01-31/02-01. Fixed anyway since the content is still live on the host's page, but no customer-facing action taken (party's long over, nothing to notify anyone about).
