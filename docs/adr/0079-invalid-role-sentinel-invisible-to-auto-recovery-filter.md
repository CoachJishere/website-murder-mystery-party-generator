# ADR-0079: `invalid_role` sentinel was invisible to `notify-generation-issue`'s own auto-recovery filter

- **Status:** Accepted
- **Date:** 2026-08-13
- **Related:** ADR-0052 (introduced the `'invalid_role'` sentinel coercion trigger), ADR-0076 (added attempt-cap/spend-cap safety rails to this same auto-recovery block), ADR-0061/0047 (the separate 30-min sweep worker and its own defect-class list, unaffected by this bug)

## Context

Customer `alib.botha@gmail.com` purchased "The Kommetjie Coconut Club Mystery" (8 players, conversation `e7571bc0-db6a-4067-85ad-48082f4543db`, package `3d9e0347-539e-48f0-ab51-6d055165c4e7`) at 2026-08-13 07:43:51 UTC. Generation entered `needs_review` 13 minutes later. All 8 characters had `character_role = 'invalid_role'` (the ADR-0052 sentinel).

**Correction to the initial read of this incident:** the first pass at this investigation checked `round2_script`/`round3_script`/`round4_script`/`final_statement` (the *unified* content format), found them empty, and concluded round-content generation had failed entirely alongside the role write. That was wrong. This mystery is a random-slip, no-fixed-murderer, no-accomplice character-style game (`master_context` has no designated murderer field, `has_accomplice = false`) — it uses the *branching* format (`round2_innocent`/`round2_guilty`, `round3_innocent`/`round3_guilty`, `round4_innocent`/`round4_guilty`, `final_innocent`/`final_guilty`, plus their `_pointform` variants), and the unified columns are simply never populated for this style. Once the correct columns were checked, every one of them was already fully populated, at lengths matching a same-shape completed reference package (`054a7ee7-...`, "Death Before The Wedding Vows") almost exactly. **`character_role` was the only actual defect.** Everything else — `description`/`background`/`secrets`/`introduction`/`rumors`/`accusations`/all round content/`master_context`/`game_overview`/`detective_script`/`evidence_cards` — was correct from the original generation run.

The root cause of the `character_role` write itself failing (what Make.com sent that got coerced to the sentinel, and why) was not determined — it wasn't the round-content generation halting (that content was already there), just this one field's value or mapping. Not investigated further since the fix (below) fully resolved it; flagged as an open question in Consequences.

Investigating why this hadn't already self-healed turned up two independent facts, both by design and neither a bug on their own:
1. The 30-min sweep worker (`auto-remediate-packages`) has no handler for `invalid_role` at all — confirmed intentional by its own code comment ("nothing is coming to fix those, so they alert immediately").
2. `notify-generation-issue`'s inline quick-recovery loop (re-fires the Child webhook per empty character, added specifically for this kind of gap — see ADR-0076) *should* have covered this case. It didn't, because of a third, previously-unknown bug: its filter was `chars.filter(c => !c.description || !c.character_role)`. `'invalid_role'` is a non-empty string, so `!c.character_role` evaluates `false` — the filter was built before the ADR-0052 sentinel existed, tests plain falsiness, and has no idea the sentinel means "no real role assigned." All 8 characters were silently excluded from `emptyCharacters`, so no re-fire was ever attempted and the alert email showed no "Empty Characters" / "Auto-Recovery" rows at all — just the `structuralDefects` list from `generation_status`, which comes from a different check (the completion gate) that *does* know about the sentinel.

Net effect: a real, non-transient defect that the codebase already had a working paid-recovery mechanism for went completely unactioned by that mechanism, purely because two different parts of the codebase encode "this role is broken" two different ways (NULL vs. the sentinel string) and only one of them was taught about the other.

## Decision

**Three actions — two of them (the webhook re-fires) turned out to be unnecessary spend, discovered only after the fact:**

1. **Two webhook re-fires (in hindsight, unnecessary).** Before realizing `character_role` was the *only* defect, re-fired the same production Child webhook (`hook.eu2.make.com/3l26wasbsjzh5396np25qoyv8g82u6j3`) `notify-generation-issue` uses for empty-character recovery — once manually (08:15:30 UTC, all 8 characters), then again automatically by the 10-minute sweep cron (08:20:04 UTC, 7 characters — Mark Silberbauer had already gotten a valid role from the first wave and was correctly excluded by the just-deployed filter fix, see #3 below). Both fully regenerated already-correct content a second and third time at ~$0.15/character (~$2.40 total, on the existing production key, approved in advance). Logged to `auto_remediation_log` (`defect_class: empty_character_content`) for consistent attempt-cap accounting. **Neither wave fixed `character_role`** — both wrote fresh (correct, matching) narrative content but the role write kept landing on the sentinel again.
2. **Direct SQL correction (the actual fix).** Once the branching-format columns were checked and found already fully populated and correct, ran `UPDATE mystery_characters SET character_role = 'suspect' WHERE package_id = '3d9e0347-...' AND character_role = 'invalid_role'` — matching the value every character carries in a same-shape, no-accomplice, random-slip reference package. Verified `package_completion_blocking_defects()` returned no defects, then ran `promote_complete_packages()` to flip the package from `needs_review` to `completed` immediately rather than wait for the 2-minute cron.
3. **Patched the filter** in `supabase/functions/notify-generation-issue/index.ts` to also treat the sentinel as empty: `!c.description || !c.character_role || c.character_role === "invalid_role"`. Deployed as v15 (`verify_jwt: true`, unchanged from v14). This part of the fix stands on its own merits regardless of the wasted re-fires above — the filter genuinely was blind to the sentinel, and that's still worth closing.

## Rationale

- The filter fix (item 3) is still correct and worth keeping: it makes the existing recovery mechanism see what it was already supposed to see. It just wasn't *this* incident's actual fix, because the recovery mechanism it improves (full character regeneration) was never the right tool for a single-field defect.
- The real lesson is procedural, not architectural: **check the columns the mystery's actual style/script_type combination uses before diagnosing "empty content."** This codebase has two parallel content formats on the same table (unified vs. branching, see [[reference_round_script_formats]]) and checking the wrong one silently reads as "totally empty" instead of "not applicable to this row." That mistake is what drove two unnecessary paid regenerations here.
- Not fixed here: the underlying cause of the `character_role` write itself failing (what value Make.com actually sent, why it wasn't in the enum) — not determined, see Consequences.

## Alternatives Considered

- **Rewrite the filter to check every content field** (round2–4, final_statement) instead of just description/role. Rejected: those are the *unified*-format columns, which this style of mystery never populates — a filter checking them would misfire on every normal branching-format package. (This alternative was drafted before the format mixup was caught; kept here as a record of the same mistake almost propagating into the fix itself.)
- **Add `invalid_role` to the 30-min sweep worker's defect classes.** Rejected: that worker delegates to `regenerate-child-content`, which repairs specific fields on an already-otherwise-complete character. Redundant with the filter fix, and — now confirmed — a role-only defect doesn't need content repair at all, just a value correction.

## Consequences

- **Positive:** the filter fix means a future package with a genuinely empty character (the case it was actually built for) will get an automatic re-fire instead of sitting unactioned.
- **Cost of the misdiagnosis:** ~$2.40 in unnecessary regeneration spend, and roughly 15 minutes of elapsed time chasing a "still not fixed" symptom that was actually just a stale read of the wrong columns. No customer impact from the spend itself, but worth naming as the direct cost of not checking the reference package's column-fill pattern first.
- **Not addressed:** the root cause of why `character_role` specifically failed to write a valid value on the original generation run (content generation succeeded, only this one field didn't) — not determined. Worth a follow-up if `invalid_role`-only (content otherwise complete) recurs on another package, since that would indicate a real, narrow bug in the role-assignment step rather than a one-off.
- **Not addressed:** whether other historical `needs_review` packages carry `invalid_role` with otherwise-complete content — no sweep was run for this pass; worth a follow-up query (`character_role = 'invalid_role'` across all `needs_review` packages, checking the branching columns before assuming content is missing) if this incident wasn't isolated.

## Key files

- `supabase/functions/notify-generation-issue/index.ts` — the filter fix (v14 → v15)
- `supabase/migrations/20260801_normalize_character_role_on_write.sql` — ADR-0052, the sentinel this filter now recognizes
- `supabase/migrations/20260801_prevent_structural_defects_at_completion.sql` — `package_completion_blocking_defects()`/`promote_complete_packages()`, used to verify and immediately promote the hand-repaired package instead of waiting for the 2-minute cron
- Hand-repaired: `mystery_characters.character_role` (7 rows, `'invalid_role'` → `'suspect'`) for package `3d9e0347-539e-48f0-ab51-6d055165c4e7` (conversation `e7571bc0-db6a-4067-85ad-48082f4543db`); reference package used to confirm the correct value: `054a7ee7-b8fe-4853-bdb2-3e3bb67b4f1e` ("Death Before The Wedding Vows")

## Discussion

The pattern here is the same "paired predicate drift" this codebase has been bitten by before (ADR-0055/0056/0057, and see the standing memory note on it): one concept ("this character's role is broken/unset") got two different encodings — NULL as the original convention, `'invalid_role'` as ADR-0052's deliberate addition — and a piece of code written before the second encoding existed had no way to know about it. ADR-0052 itself was careful about this on the *completion-gate* side (it explicitly designed the sentinel to still trip `package_completion_blocking_defects()`), but a sibling check three weeks and one function away wasn't updated in the same pass, because nothing forced the two to be reviewed together. No structural fix proposed here beyond the filter patch — flagging the pattern for anyone touching character-role logic next.

**Second lesson, arguably the more expensive one this time:** this table has two parallel content-storage formats (unified `roundN_script` vs. branching `roundN_innocent`/`roundN_guilty`, see [[reference_round_script_formats]]), and the investigation checked only the unified columns for a solid 15+ minutes and two paid regeneration attempts before checking the other format and finding everything already there. The existing memory note on this exact gotcha ("querying only `_script` columns falsely looks like total failure") named this precisely — it just wasn't consulted before diagnosing this incident. Re-affirming it here with a concrete cost attached (~$2.40, two rounds of "still not fixed" back-and-forth) in case a stronger nudge than a memory note is warranted — e.g., a comment on the `mystery_characters` table itself, or a small diagnostic query/view that checks both formats at once, might be worth building next time this class of "package looks stuck" investigation comes up.
