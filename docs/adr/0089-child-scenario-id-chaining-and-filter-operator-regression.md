# ADR-0089: Restore id-chaining in the Child (Unified) scenario after ADR-0087's fix broke first-time generation

- **Status:** Accepted
- **Date:** 2026-08-16
- **Related:** ADR-0087 (introduced the regression this ADR fixes, in good faith, for a different reason), ADR-0052 (`character_role` coerce-not-reject precedent), ADR-0061/0047 (auto-remediation, not applicable here — this defect class has no detector or handler)

## Context

Customer `annrelli@aol.com` purchased "The Jealous Niece" (conversation `8ea718ff-1279-4c04-82cf-aa77d59f94f5`, package `d31f69d2-aaf6-46d4-a930-c759d670e635`, 2026-08-16 17:11 UTC). Generation ran, `mystery_packages.generation_status` was written as `completed` with all sections `true`, but `mystery_characters` had **zero rows** — 0 of 6 expected characters. The customer saw "We're Finalizing" indefinitely. `notify-generation-issue` fired the generic stuck-generation alert, but its own empty-character auto-recovery loop is a no-op when zero rows exist (it only re-fires characters that have an existing-but-incomplete row) — so no automatic recovery was possible, and this surfaced only as a manual support escalation.

Root-caused live, with the customer's execution log open in Make.com, across two distinct bugs:

**Bug 1 — filter operator drift on import.** The "Identity Parsed OK" filter (added in ADR-0087 / Child28) gates the identity `upsertARecord` on `{{402/502.data.description}} <op> `. The checked-in `Child29-RelationshipSelfExclusion.blueprint.json` has this operator as `"o": "text:exist"`. Live in Make, the operator was blank/unset on both routes (detective 404, character 504) — meaning the filter could never evaluate true, so the identity write was skipped for every character regardless of whether Claude's output was good. Confirmed via a direct pull of the module's live JSON output: identical, well-formed content each time (`description` present, non-empty), yet the filter blocked it. Jonathan manually set the operator via Make's UI dropdown; the value it actually wrote was `"o": "exist"`, not `"text:exist"`. **`"text:exist"` may not be a value Make's import path honors for this filter type** — that would fully explain why it silently landed empty on import rather than erroring. Not confirmed with certainty (no way to test re-importing a `text:exist` blueprint and observing the failure directly this session), but it's the most consistent explanation and the safer value to use going forward is the UI-confirmed `"exist"`.

**Bug 2 — id-chaining regression, introduced deliberately by ADR-0087.** From Child14 through Child27, every downstream `upsertARecord` in a character's chain (408, 412 in the detective route; 508, 512, 516, 520 in the character route) mapped its `id` field to the *previous* upsert's own id (`{{404.id}}`, `{{504.id}}`) — chaining forward so every write in a character's generation lands on the same row. ADR-0087 (Child28, 2026-08-14) repointed all six of these to `{{400.id}}`/`{{500.id}}` (the one-time `searchRows` result from the top of the scenario) instead. That change was intentional and reasoned: with the new identity-guard filter able to *skip* 404/504 entirely on a parse failure, a downstream module referencing `{{404.id}}` would resolve to nothing in that run, which ADR-0087 judged riskier than referencing the always-executed search result.

That reasoning didn't hold for the common case. `{{400.id}}`/`{{500.id}}` is empty not only when 404/504 gets skipped, but on **every first-time, single-pass character generation** — the search runs before any row exists, full stop. On a brand-new character, 404/504 always succeeds (empty id → Postgres inserts fresh), but every subsequent module in the chain still reads that same permanently-empty `{{500.id}}`, tries another insert, and hits `mystery_characters_package_character_unique` (`package_id, character_name`) — a 409, which Make's default error handling drops into Incomplete Executions without surfacing anywhere. This is why prior packages "worked": most had already been through at least one earlier partial attempt, so `{{500.id}}` wasn't actually empty — it held a real id left over from a previous run. This customer's purchase was a clean, genuinely-first-ever attempt, one of the few pure enough to hit the latent bug directly. Both bugs (filter operator blank, id-chaining broken) most likely went live together, close to this customer's purchase time.

## Decision

1. **Restored the pre-ADR-0087 id-chaining pattern**: 408/412 → `{{404.id}}`, 508/512/516/520 → `{{504.id}}`, verified against Child14–Child27 (all eight identical) before applying. Built as `temp-files/MM Live - Child (Unified)30-FixIdChaining.blueprint.json`, then Jonathan applied the equivalent changes live in Make (filter operator + id fields) and re-exported, confirmed byte-for-byte consistent with the intended fix.
2. **Filter operator left at `"exist"`** (not reverted to `"text:exist"`) on both routes' "Identity Parsed OK" filters — matches what Make's own UI writes and is now confirmed working end-to-end.
3. **Manually recovered this customer's package**: re-fired all 6 characters via the child webhook directly (bypassing a full parent+child regeneration, since `master_context`/`detective_script`/`evidence_cards` were already good), verified full field completion for all 6 (identity, rumors/accusations, round 2-4 questions/innocent/guilty, final innocent/guilty), confirmed exactly 6 rows. Cost: ~10 individual character-webhook fires across iterative debugging (Molly x2, Joe Rice x2, final batch of 5), approved in advance by Jonathan with a cost estimate before the first fire.
4. **Backfilled `character_role`** from the `invalid_role` sentinel to `suspect` for all 6 (free, deterministic — separate, pre-existing, non-blocking prompt-echo issue where Claude reproduces the schema's parenthetical instruction text verbatim instead of extracting just `"suspect"`; unrelated to this incident, not fixed at the prompt level).

## Rationale

- Reverting to the known-working `{{404.id}}`/`{{504.id}}` pattern (verified across 14 prior blueprint versions) is lower-risk than engineering something new under incident pressure — it's a restore, not new logic.
- Fixing this live in Make.com first (Jonathan, hands-on with the actual scenario) and then re-exporting to `temp-files/` for the record, rather than the reverse, avoided a second round of "file vs. live" drift — a recurring failure mode this whole investigation surfaced (see Consequences).

## Alternatives Considered

- **`COALESCE({{404.id}}, {{400.id}})`** on every downstream module — would correctly handle ADR-0087's original concern (a re-fire where identity parsing fails: 404 skipped, but `{{400.id}}` still resolves to the existing row from before, so round-content writes correctly attach to it without touching the stale-but-fine identity fields) *and* the first-time-generation case (404 succeeds, `{{404.id}}` is used) *and* degrades safely on a first-time character whose identity parse fails (both empty, downstream writes correctly fail/skip rather than creating an identity-less zombie row). This is very likely the *actually correct* fix and better than a flat revert — reopening ADR-0087's original edge case for re-fires is a real, if narrow, regression. **Not implemented this session** — flagged as a follow-up below, not attempted live against a paying customer's active recovery.
- **Full regenerate via `mystery-webhook-trigger`** instead of surgical per-character re-fires. Rejected: customer had seen zero content (0 characters means the "We're Finalizing" screen, nothing else), so nothing would have been lost by a full regen, but the already-good `master_context`/`detective_script`/`evidence_cards` would have been thrown away and re-rolled for no reason, plus higher cost.

## Consequences

- **Positive:** this customer's package is fully recovered and verified complete. The id-chaining and filter-operator bugs are both fixed in the live scenario and captured in `temp-files/Child30-FixIdChaining.blueprint.json`.
- **Reopened, accepted gap:** ADR-0087's original edge case (a re-fire hitting an identity parse failure, with the guard filter correctly skipping 404/504) will once again break downstream writes for THAT specific narrow case, exactly as ADR-0087 described. The `COALESCE` alternative above closes this properly; it's a scoped, well-understood follow-up, not implemented yet.
- **Not addressed — needs a sweep:** whether OTHER customers hit the same 0-character (or partial-character) failure in the window between Child28/29 going live and this fix (2026-08-14 through 2026-08-16). This defect requires a genuinely first-time, single-pass generation to manifest, so it's plausibly rare, but no query has been run against `mystery_packages`/`mystery_characters` to confirm how many packages in that window have `generation_status.status = 'completed'` with fewer characters than `extracted_characters` implies. This is the highest-priority follow-up.
- **Not addressed:** the `"text:exist"` vs `"exist"` operator-value question is not fully confirmed as the root cause of the blank operator on import — worth testing directly next time a blueprint with a filter is imported, rather than assumed.
- **Not addressed:** `character_role` landing as `invalid_role` from the model echoing prompt-schema instructional text is a pre-existing, separate issue (not new today) — still not fixed at the prompt level, only backfilled for this one customer's 6 rows.

## Discussion

The most useful trace in this investigation was pulling the actual id-chaining values across all 16 blueprint versions (`grep` for `"id": "{{[0-9]+\.id}}"` across every `temp-files/MM Live - Child (Unified)*.blueprint.json`) rather than trusting either the most recent file or live-vs-file assumptions. That showed unambiguously: v14 through v27 all agreed on one pattern, v28 changed it everywhere at once, and v29 inherited it unchanged — turning "why is this suddenly broken" into "what changed between v27 and v28, and why," which led straight to ADR-0087's own documented (and reasoned, not careless) tradeoff. Worth remembering for future Make.com regressions in this project: the blueprint history in `temp-files/` is a real, checkable audit trail even though the files themselves are gitignored — treat it as one before assuming a live edit did something new.

The live-scenario-vs-exported-file drift (filter operator empty live but present in the file; id-chaining present in the file's v29 but reported as fully absent from Jonathan's live export before his manual fix) is a standing hazard flagged before (`feedback_makecom_blueprint_versioning`) and worth restating: **Make.com is the actual source of truth; `temp-files/` blueprints are snapshots that can silently diverge from it**, in both directions, even within the same day. Treat any exported blueprint as "what we believe was true when this was exported," not as ground truth for what's currently live.
