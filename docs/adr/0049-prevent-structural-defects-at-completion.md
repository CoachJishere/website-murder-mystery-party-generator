# ADR-0049: Prevent structural defects at completion, not just detect them after

- **Status:** Accepted
- **Date:** 2026-08-01

## Context

ADR-0048 (shipped earlier the same day) added `list_packages_with_structural_defects()` — a read-only, escalate-only detector that catches packages marked `completed` while structurally broken: an invalid `character_role`, multiple murderers, a cross-wired background, a gender-duplicated cast. It found two live incidents on first run:

- **"Death At The Velvet Viper: A New Orleans Speakeasy Tragedy"** (paid, 2026-07-30) — a raw 502 response body stored verbatim as a character's `character_role`, among other defects. Already repaired in place before the detector existed.
- **"Murder At The Coronation: A Royal Scandal"** (paid, 2026-07-31, package `96b62ce5`, conversation `f106ef2c`) — the **same failure mode recurring the very next day**, live and unfixed at detection time: a 121-character 502 HTML error body (`<html><head><title>502 Bad Gateway</title>...`) stored verbatim in `character_role`, `background`, **and** `secret` simultaneously, all three holding the identical string.

Detection is not prevention. Both packages had already shipped to paying customers marked `completed` before anything caught them. ADR-0048 explicitly scoped itself to detection and left prevention as follow-up work. This ADR is that follow-up.

### Root cause

Traced the full generation → save path: `mystery-webhook-trigger` (starts generation, no completion logic) → Make.com scenario `9106101` "MM Live - Parent v49" (builds overview/host guide/clues) → Make.com scenario `9061052` "MM Live - Child (Unified) v19" (writes each character) → `api/generation-complete.js` (Vercel edge function, the parent's completion callback) → `mystery_packages` UPDATE.

Inside the child scenario, the per-character block is:

1. `anthropic-claude:createAMessage` (module 401 and ten siblings: 405/409/501/505/509/513/517) — calls Claude, producing free-text JSON in `{{40x.textResponse}}`.
2. `http:ActionSendData` "Parse Claude JSON" (module 402 and ten siblings: 406/410/413/502/506/510/514/518/521/525) — POSTs that text to the `parse-claude-json` Supabase edge function, which repairs common JSON malformations and returns a structured object.
3. `supabase:upsertARecord` (module 404 and siblings) — maps `{{40x.data.characterRole}}`, `{{40x.data.background}}`, `{{40x.data.secret}}`, etc. directly into the `mystery_characters` row.

**Module 402 (and all ten siblings) is configured with `"handleErrors": false`.** Verified against the live blueprint (and the local backup copy in `temp-files/`): every one of the eleven `http:ActionSendData` modules has this flag, and **no error handler exists anywhere in the scenario** — every `onerror` slot is either absent or an empty array. When `parse-claude-json` itself returns a 5xx (a Supabase Edge Function gateway hiccup — cold start, deploy-in-progress, platform blip; nothing in the function's own code returns a 5xx, it only ever returns 200/400/422/500-with-JSON), Make does not treat that as a module error. The raw HTML error body flows through as if it were a successful response, and the downstream field-mapping resolves every dotted key (`.characterRole`, `.background`, `.secret`) against it — which is exactly why Coronation's three fields all held the identical error text: they are three different property accesses against the same non-object fallback value, not three independent calls each hitting a 502.

This explains why neither incident showed up as a failed Make.com run: nothing ever errored. The scenario completed "successfully" with garbage data, and downstream code correctly saw 2 characters generated (the expected count) and marked the package `completed`.

### Why this needed a DB-level fix, not just an app-layer one

There are at least four places that can set `mystery_packages.generation_status` to `completed`, discovered while tracing the path:

1. `api/generation-complete.js` — the Make.com parent's completion callback (Vercel edge function). Validates character *count* only, never content.
2. The client-side `getPackageGenerationStatus()` in `src/services/mysteryPackageService.ts` — an "auto-correction" that upgrades a package to `completed` from the browser (via the anon key) whenever title/host_guide/character-count heuristics look satisfied. No content validation either.
3. `promote_complete_packages()` (Postgres function, called every 2 minutes from `sweep_incomplete_packages()` via pg_cron) — promotes `needs_review` → `completed` once every character has non-null `description`/`character_role`.
4. `heal_completed_packages()` (Postgres function, its own pg_cron job, also every 2 minutes) — same promotion, plus a `description` length check.

A fix at any single app-layer call site leaves the other three open, and a future caller (a direct Make.com PATCH to `mystery_packages`, which is architecturally plausible given "results are saved back into Supabase" is already how `mystery_characters` is written) would bypass all of them. The one place *every* one of these paths goes through is the `mystery_packages` row itself — specifically, an **existing** Postgres trigger, `validate_package_characters()`, already fires `BEFORE UPDATE` exactly when `generation_completed_at` transitions from `NULL` to non-`NULL` (the moment of first completion), downgrading to `needs_review` and calling `notify-generation-issue` if the character count looks wrong. It just never checked `character_role` validity or field *content* — only NULL-ness and count.

Investigating the two recovery functions surfaced a second, independent gap: **both bypass `validate_package_characters()` by construction.** Neither touches `generation_completed_at` (only the initial completing UPDATE and `sweep_incomplete_packages()`'s own needs-review-setting UPDATE do), so the trigger's `OLD.generation_completed_at IS NOT NULL` early-return always short-circuits for them. Without fixing this too, a package correctly blocked by the extended trigger would have been silently re-promoted to `completed` by the very next `heal_completed_packages` tick — within 2 minutes — because that function's own check (`character_role IS NULL OR description IS NULL OR length(description) < 100`) passes trivially on a non-null, 121-character HTML error body.

## Decision

Migration `20260801_prevent_structural_defects_at_completion.sql` adds one shared function and extends three existing ones — no new trigger, no new cron job, minimal surface area:

1. **`public.package_completion_blocking_defects(_pkg mystery_packages) RETURNS text[]`** — the shared check. Returns `NULL` if clean, or an array of defect strings. Two invariants, deliberately narrow:
   - `invalid_role` — a non-`NULL` `character_role` outside `('murderer','accomplice','suspect','redHerring')`.
   - `error_body` — any package-level or character-level delivered field (dynamic scan via `to_jsonb()`, so new columns are covered automatically) matching a narrow regex: `<html`, `<!DOCTYPE html`, `bad gateway`, `gateway timeout`/`gateway-timeout`, or a `502`/`503`/`504` status code paired with its standard reason phrase. Never a bare word like "gateway" — validated against a plot mentioning "gateway to the old city" / "iron gateway" with zero false positives (see Verification).

2. **`validate_package_characters()` (extended)** — the existing pre-completion trigger now also calls the shared function and folds any hit into the same `needs_review` downgrade + `notify-generation-issue` call it already performs for empty characters. This is the primary gate. Being a DB trigger, it fires regardless of caller — `api/generation-complete.js`, the client-side auto-correction, or any future direct Make.com write all go through it for free.

3. **`heal_completed_packages()` and `promote_complete_packages()` (extended)** — both gained `AND public.package_completion_blocking_defects(mp) IS NULL` in their promotion `WHERE` clause. This is the "mirror prevention into the recovery path" fix: neither function can ever re-promote a structurally broken package to `completed`, whether the defect was introduced by the failure this ADR targets or by anything else the count/NULL-based checks miss.

**Make.com fix: identified, not applied.** The exact module (`http:ActionSendData` "Parse Claude JSON", `handleErrors: false`, no error handler, 11 occurrences across both routes of scenario 9061052) is known with high confidence — see Root Cause above. It is deliberately **not** patched in this change: adding a working retry-on-5xx error handler is a Make-UI action (right-click the module → Add error handler → configure a retry/resume directive), not a blueprint field I can safely round-trip through the API without a human confirming the result on the canvas — this project's own convention (established in prior sessions) is explicit that error handlers are added in the Make UI, not by editing blueprint JSON. Recorded as a recommendation below.

## Rationale

- **DB-level prevention closes the hole regardless of which app-layer path is used, today or in the future.** Four completion-setting call sites were found during this investigation; a trigger on the table itself is the only point common to all of them, including ones not yet written.
- **The recovery-path fix is not optional.** Without it, the primary gate is cosmetic — the healer cron undoes it within 2 minutes. This was not a hypothetical found by inspection; it was verified live (see Verification) that `heal_completed_packages()`'s pre-existing check passes trivially on the exact garbage this incident produces.
- **Scope is deliberately narrower than ADR-0048's detector.** `invalid_role` and `error_body` are simple, mechanical, zero-judgment invariants: either the value is in the enum or it isn't; either the field holds an HTTP error page or it doesn't. ADR-0048's other three sub-checks (`multiple_murderers`, `name_background_mismatch`, `duplicated_cast`) require judgment to resolve — which of two murderers is real, whether a shared surname is a family or a duplication bug — and a blocking gate that gets those wrong would create false-positive `needs_review` packages for legitimate content (family mysteries, predetermined games that legitimately reuse a role line). ADR-0048 already did this narrowing analysis for the *detection* context; the same discipline applies more strongly here because a prevention gate's false positives directly block real, paying customers rather than just adding a noisy alert row.
- **Reusing the existing trigger, not adding a new one.** `validate_package_characters()` already owns "what happens at the moment of first completion" and already has the `needs_review` + notify-generation-issue machinery. Extending it keeps the completion-time behavior in one place and avoids trigger-ordering questions with the three other triggers already on `mystery_packages` (`trg_maintain_needs_review_at`, `update_mystery_packages_updated_at`, `trigger_schedule_followup_emails`).
- **Not chasing the Make fix within this change.** The exact module is known, but "identified with confidence" and "safe to auto-apply" are different bars. The task's own guidance — and this project's established convention — is that error handlers are a Make-UI action. Forcing it through the API risks a malformed error-handler route silently not firing (worse than not having one, because it would look fixed) on a revenue-critical scenario, with no way for me to visually confirm the result the way the Make UI would.

## Alternatives Considered

1. **A new standalone `BEFORE INSERT OR UPDATE` trigger dedicated to this check**, independent of `validate_package_characters()`. Rejected: two triggers reacting to overlapping conditions on the same table is harder to reason about than one, and `validate_package_characters()` already owns exactly this moment (the completing transition) with the right side effects wired up (notify-generation-issue, `needs_review` shape the frontend already understands).
2. **Set the gated status to `failed` + `resumable: true` instead of `needs_review`.** Considered because `failed` more cleanly hides broken content from the customer (the frontend's TabView renders for both `completed` and `needs_review`, but not `failed`) and would have sidestepped the recovery-path gap entirely (neither healer touches `failed` rows). Rejected in favor of matching the *existing* convention: `validate_package_characters()` already uses `needs_review` for the empty-character case, `needs_review_at` already exists with a documented 10-minute silent-recovery UX window built around it, and `notify-generation-issue` already fires for `needs_review`. Inventing a second status semantics for what is architecturally the same "completion blocked, needs another look" event would fragment behavior the codebase has already standardized, for a customer-facing improvement (hiding partially-broken content sooner) that is really a frontend concern, not a data-integrity one. Recorded as a candidate follow-up below.
3. **Fold in ADR-0048's other three sub-checks as blocking too**, not just `invalid_role`/`error_body`. Rejected — see Rationale. `multiple_murderers`, `name_background_mismatch`, and `duplicated_cast` are judgment calls; blocking completion on them risks legitimate content (family mysteries, deliberately shared roles) never completing without human intervention, which is a worse failure mode for a paying customer than the rare structural defect this narrower gate might miss.
4. **Apply the Make.com error-handler fix via the API now.** Rejected — see Rationale and Discussion. Module identified with high confidence; change not applied.
5. **Do nothing beyond ADR-0048's detector, rely on the health-check alert + manual repair.** Rejected — that is what let Coronation recur the day after Velvet Viper. Detection without prevention means every future occurrence ships to a paying customer before anyone notices.

## Verification

Run live against the production DB (`mhfikaomkmqcndqfohbp`), using synthetic rows created and deleted within the same session — nothing left behind:

1. **Synthetic bad package blocked at completion.** A test package with two characters — one clean, one with `character_role` set to a literal 502 HTML body and the same body duplicated in `background` and `secret` (reproducing the exact Coronation multi-field-collision shape) — was driven through the completing `UPDATE ... SET generation_status = completed, generation_completed_at = now()`. Result: `generation_status.status` came back `needs_review`, listing `invalid_role.Bob Marchetti`, `error_body_in_character.Bob Marchetti.secret`, `error_body_in_character.Bob Marchetti.background`, `error_body_in_character.Bob Marchetti.character_role`. Never touched `completed`.
2. **Recovery path cannot resurrect it.** With the package still `needs_review` from step 1, `heal_completed_packages()` and `promote_complete_packages()` were both run manually. Status remained `needs_review` after both — confirming that without this migration's guard, the pre-existing checks in both functions (non-NULL `character_role`, `description` length ≥ 100) would have passed trivially on the 121-character HTML body and silently re-promoted the package to `completed` within the next real cron tick.
3. **Retry flow still works once genuinely fixed.** The bad character's three fields were updated to real content (simulating a regeneration), then `promote_complete_packages()` was re-run: status correctly flipped to `completed`. The gate blocks broken content without breaking legitimate recovery.
4. **Clean package completes normally — no false gating.** A second synthetic package, content deliberately including the phrase "an old iron gateway" and "beside an old iron gateway" in the overview (a direct test of the false-positive concern), was driven through the same completing UPDATE. Result: `completed`, `currentStep` unchanged — the gate did not fire.
5. **Regex precision spot-checked against real history.** Running `package_completion_blocking_defects()` directly against every package ADR-0048's detector has ever flagged (`_since '2000-01-01'`): both known incidents (Velvet Viper, Coronation) returned `NULL` — both were hand-repaired before this session, confirming the function doesn't flag already-fixed rows. Two legacy 2026-04-22 packages ("Death At The Velvet Rose", "Death At The Deadwood Saloon") correctly still return their `invalid_role` hits (uppercase `MURDERER`/`INNOCENT`/etc. vocabulary) — consistent with ADR-0048's own findings, and untouched by this migration since they were already `completed` long before this trigger's `generation_completed_at` NULL→NOT NULL condition could re-fire on them.

## Consequences

- Both known incidents (Velvet Viper, Coronation) are already hand-repaired; used as the shape of the synthetic test above, not live regression targets.
- Any future 5xx-body-in-character-field occurrence, from this Make.com module or any other future path, is now blocked at the DB layer before `completed` is ever visible, and cannot be silently undone by the 2-minute healer/promoter crons.
- **The Make.com root cause is not fixed** — only its DB-layer symptom is now blocked. The scenario will still burn a `needs_review` + support-notification cycle (and a wasted Claude API call) every time `parse-claude-json` 5xx's, until the Make UI change (documented below) is made. This is an accepted tradeoff of this change, not an oversight.
- **Recommended follow-up (Make UI, not applied here):** in scenario `9061052` ("MM Live - Child (Unified) v19"), for each of the eleven `http:ActionSendData` "Parse Claude JSON" modules (ids 402, 406, 410, 413, 502, 506, 510, 514, 518, 521, 525): enable "reject requests with an error status code" (flips `handleErrors` from `false`), then add an error handler (right-click → Add error handler → a **Break** directive with a short backoff and 2-3 retries is the natural fit, since Make's Break replays the run from that module). Per this project's blueprint-versioning convention: before editing, re-list `temp-files/` to confirm the current head is still "MM Live - Child (Unified)19-SlipGuilt-OutputHygiene-VictimQuestions.blueprint.json" (scenario 9061052) and "MM Live - Parent49 (Accomplice-Beat Silent-Omission).blueprint.json" (scenario 9106101, unaffected by this specific defect but worth the same audit), duplicate the current head to the next version number (Child v20 / Parent v50) as a rollback point *before* making the UI change, and make the error-handler edit directly on the canvas rather than via blueprint import.
- **Candidate follow-up — reconsider `failed`+`resumable` for the gated status**, once there's live volume to observe: if `needs_review` from this gate turns out to leave broken-looking content visible to customers in practice (see Alternatives #2), revisit.
- Vault sync completed per CLAUDE.md — this ADR plus the CHANGELOG entry are copied to the Obsidian vault. While there, also completed ADR-0048's own pending vault sync (its session's sandbox couldn't reach the vault; it was staged in `temp-files/vault-sync-pending/` with a README documenting exactly what was owed — copied over verbatim, plus a resolution note added to the Coronation incident file pointing at this ADR).

## Discussion

The sharpest judgment call was whether to spend effort on the Make.com side at all, given the instruction that prevention should be "the most robust layer." The DB trigger genuinely is more robust than any single app-layer or Make-layer fix — it's the one point every current and future completion path already goes through. But finding the exact module with this level of confidence (the `handleErrors: false` flag, the empty `onerror` arrays, the precise multi-field-collision explanation for why Coronation's role/background/secret all matched) is valuable independent of whether it gets fixed today, because it turns "somewhere in Make.com" into a five-minute UI task for a human. Writing that down precisely, rather than either silently skipping it or half-attempting an API-side blueprint edit I couldn't verify, was the better use of the confidence I'd built.

The second real decision was `needs_review` vs `failed` for the gated status. `failed`+`resumable` looked attractive at first specifically because the frontend's TabView condition (`generationStatus?.status === 'completed' || generationStatus?.status === 'needs_review'`) means a `needs_review` package is still shown to the customer — so a customer could, in principle, load their mystery page during the (target: sub-10-minute) window before this gate's `needs_review` gets noticed and see a character whose secret is a Cloudflare error page. That is a real, checkable trade-off, not a hypothetical: I read the exact frontend condition before deciding. I still chose `needs_review` because it's what `validate_package_characters()` already does for the sibling defect (empty characters) one line above the code this ADR touches, and inventing a second, parallel "blocked" status for what is conceptually the identical event (completion attempted, content not good enough, needs another pass) would be exactly the kind of drift ADR-0048's own `generation_status` double-encoding finding warns about: two things that are semantically the same event, encoded differently, silently invisible to each other's tooling. If the TabView exposure turns out to matter in practice, it is a smaller, more surgical fix to make later (add `needs_review_at`-style age-gating to the TabView condition itself, mirroring the banner it already has) than un-forking two status vocabularies would be.

Worth naming plainly: this migration does not fix the bug. It fixes the blast radius of the bug. The actual defect — a Supabase Edge Function occasionally 502'ing, and Make.com not caring — will keep happening at whatever rate transient upstream errors happen, and every occurrence will now cost a `needs_review` cycle instead of shipping broken content, which is the correct trade for a business that would rather over-flag than under-flag. But the Make-side fix is where the wasted-generation cost actually goes away, and it's recorded here precisely so it doesn't quietly become permanent scope creep on "eventually."
