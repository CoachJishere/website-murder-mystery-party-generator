# ADR-0061: Wire the child-content regenerator into the closed loop — ADR-0051 layer 3, wiring pass

- **Status:** Accepted
- **Date:** 2026-08-02
- **Builds on:** ADR-0054 (child-content regenerator, standalone primitive), ADR-0055 (widened detector RPCs so gate-held packages are visible), ADR-0047 (auto-remediation worker), ADR-0053 (completion gate)

## Context

ADR-0054 built `regenerate-child-content` — a gated, re-detecting, audit-logged primitive that repairs `identity_contamination`, `slip_culprit_leak`, and the character-sourced half of `meta_text_leak` — but deliberately shipped unwired: "document the exact call contract... wiring is the next pass." ADR-0054's own Discussion section names the contract precisely: replace the ADR-0047 worker's `handleEscalateOnly` for `identity_contamination`/`slip_culprit_leak` with a call to `regenerate-child-content`, and treat the worker's own gate as "close to a no-op confirmation rather than a second independent check" — because the regenerator already re-detects and reverts internally.

Separately, ADR-0055 (shipped earlier the same day as this ADR) fixed a real deadlock: the eight `list_packages_with_*()` detector RPCs all filtered on `generation_status = 'completed'`, so a package the gate had just set to `needs_review` became invisible to the very worker meant to heal it. That's fixed — the RPCs now see `needs_review` too. ADR-0055's own Consequences section named what's still missing: "[the hold-only classes] still require human repair or ADR-0054's child-content regenerator once it is wired into the gate." This ADR is that wiring.

Two things changed since the original task brief was written (worth naming, since it changes the shape of decision 1 below):

1. **ADR-0055 already took the "0055" slot** and already solved the "gate can't call an edge function synchronously" half of the problem — not via a trigger or `pg_net` push, but by making the *existing* worker's pull-based detector RPCs see held packages. The next available sequential ADR number is 0061 (0056–0060 shipped in between, unrelated work).
2. **The worker's `template_artifact` class is not literally the same string as the regenerator's `meta_text_leak` hint.** The worker names this class `template_artifact` (it already has a deterministic free-strip handler for it); the regenerator's `defect_class_hint` enum calls the same underlying detector `meta_text_leak`. Both point at `list_packages_with_meta_text_leak()`. This naming mismatch matters for decision 3 below.

## Decision

### 1. How a gate-held package gets repaired promptly

**Add a second, narrowly-scoped pg_cron job that re-invokes the existing `auto-remediate-packages` function every 5 minutes, restricted to `needs_review` packages and only the three newly-delegatable classes** (`identity_contamination`, `slip_culprit_leak`, `template_artifact`). The existing 4-hour full-window job (`43 */4 * * *`, all six classes, all statuses within the 30-day window) is unchanged and remains the backstop.

Rejected the trigger/`pg_net`-from-`validate_package_characters()` option: `package_completion_blocking_defects()` and the trigger that calls it are `STABLE`/synchronous SQL, deliberately kept side-effect-free per ADR-0049's "one shared chokepoint, three enforcement paths" design — bolting an async HTTP call onto the completion trigger couples the completion-time gate (a data-integrity invariant, exercised on every single completion) to the availability and latency of an LLM-calling edge function, for a benefit (a few extra minutes of latency) that a tight poll already captures at near-zero coupling cost. It would also need its own idempotency handling (the trigger firing once doesn't mean the repair only needs to be attempted once) — which the cron approach gets for free from the existing per-class attempt cap.

The worker's own code path, RPCs, and safety rails are reused as-is for the new job — no new function, no new edge function, no new secrets. The only worker change (see Decision 3) is two new optional request fields: `only_needs_review?: boolean` and `classes?: DefectClass[]`.

**Latency:** worst case ~5 minutes before a held package with a delegatable defect is first attempted, comfortably inside the ~10-minute "silent recovery window" the `needs_review` banner already assumes (ADR-0055's Consequences section flagged that this window doesn't actually work today due to a `needs_review_at` ordering bug — separate, already-tracked, not fixed here). Average case: the package is often mid-repair before a human or a customer would notice.

### 2. Delegation, not re-wrapping

The worker's `identity_contamination` and `slip_culprit_leak` classes are removed from `ESCALATE_ONLY` and get a new handler, `delegateToRegenerator`, that calls `regenerate-child-content` **directly** — it is not built as a `FixPlan` and is not passed through `runGatedAttempt`. `runGatedAttempt`'s apply→re-detect→accept/revert machinery exists because the worker's own deterministic edits (regex strips, retargets) have no re-detect gate of their own; wrapping a call to a function that *already* re-detects and reverts internally would mean two independent revert paths racing to "undo" the same writes, and a false rejection by the worker's outer gate (e.g. a stale window/`_since` mismatch) would revert content the regenerator had already committed as good. The worker's contribution here is narrower and comes before the call, not around it: the existing per-package/per-defect **attempt cap** (`attemptsUsed`, `MAX_ATTEMPTS_PER_DEFECT = 2`) is checked first — the regenerator has no attempt memory of its own, only a spend cap, so without this a permanently-unfixable package (e.g. a conflict with more claimants than `MAX_TARGET_CHARACTERS` allows) would retry forever at every cron tick — and the concurrency claim (Decision 4) is acquired and released around the call.

`meta_text_leak` is handled differently because, unlike the other two, it already has a real, safe, zero-cost deterministic repair (`handleTemplateArtifacts`'s bracketed-span strip) that should keep running exactly as today — it never reintroduces a defect and costs nothing, so there is no reason to route it through an LLM call. The change here is narrower: the strip logic already refuses (`safe: false`) when an artifact is embedded in real content rather than sitting on its own line, and previously that refusal meant an immediate, uninformative `return null` — the whole package escalated with no record of *which* field was the problem. That refusal now also records `{characterId, field}` for every character-scoped field it refuses to touch (package-scope refusals — the artifact is in `game_overview`/`host_guide`/etc. — are unchanged and still escalate as before, since `regenerate-child-content` cannot write parent-content fields). After the existing gated strip attempt runs (and, independently, whether it fixed something or not — a package can have both a strippable artifact on one character and an embedded one on another), any character-scoped fields that were refused are handed to `delegateToRegenerator` with `defect_class_hint: "meta_text_leak"` and `fields` set to exactly those refused fields. This is strictly additive to the existing free path, not a replacement of it.

**Class → repair route (no class repaired by two paths):**

| Blocking class | Route |
|---|---|
| `identity_contamination` / `identity_conflict` | `regenerate-child-content` (delegated, claim-guarded) |
| `slip_culprit_leak` | `regenerate-child-content` (delegated, claim-guarded) |
| `meta_text_leak` / `template_artifact`, character-scoped, safely strippable | worker's own deterministic strip (unchanged, free, no claim needed — single-writer already) |
| `meta_text_leak` / `template_artifact`, character-scoped, embedded (unsafe to strip) | `regenerate-child-content` (delegated, claim-guarded) — **new** |
| `meta_text_leak`, package-scoped | worker's own deterministic strip if safe, else escalate (unchanged — out of scope for the child-content regenerator, which cannot write `mystery_packages` fields) |
| `victim_mismatch` / `game_overview_victim_mismatch` | `regenerate-parent-content` via the worker's existing `handleVictimMismatch` (unchanged) |
| `missing_images` | worker's existing `generate-evidence-images` recall (unchanged) |
| `self_directed_question` | worker's existing deterministic retarget (unchanged) |

### 3. Shared-cap reconciliation

`regenerate-child-content` already reads `spentToday()` from the same `auto_remediation_log` table the worker sums, and logs its own cost there — so cross-invocation double-spending across the two *functions* was already prevented by ADR-0054's design (one shared ceiling, read fresh on every call). The gap this ADR closes is narrower and *within a single worker run*: the worker computes its own `budgetRemaining` once, at the start of the run, from `spentToday()`. If that same run also delegates one or more `identity_contamination`/`slip_culprit_leak`/`meta_text_leak` repairs earlier in its loop (each of which spends against the shared table via the regenerator's own internal check, not the worker's), the worker's locally-cached `budgetRemaining` would be stale for the paid fixes later in the *same* run (`game_overview_victim_mismatch`, `missing_images`) — silently overestimating headroom and risking a same-run overspend past the nominal $5 cap.

Fixed by having `delegateToRegenerator` read the regenerator's own response `cost_usd` field and decrement the worker's local `ctx.budgetRemaining` by that amount immediately after each delegated call returns, win or lose. No new accounting structure — same pattern `runGatedAttempt` already uses for its own paid fixes, just fed from the delegated call's actual reported cost instead of a locally-known constant.

**Attribution / no double-logging:** `regenerate-child-content` is the only writer of the `auto_remediation_log` row for a delegated attempt (it logs `fixed`/`escalated`/`failed` with `defect_class` set to whatever hint the worker passed). The worker does **not** call `logRow` again for the same attempt — doing so would double-count both the spend sum and the attempt-cap count. The worker only logs its own bookkeeping rows (`skip:attempt_cap`, and a new `escalate:delegate_call_failed` for the case where the HTTP call to the regenerator itself errors before the regenerator could log anything — see Decision 2's failure-mode note) — both are `cost_usd: 0`, so they cannot double-count spend, and both use `action` prefixes (`skip:`/`escalate:`) already excluded from `attemptsUsed()`'s count.

**Class-name consistency for attempt-cap counting:** for `identity_contamination` and `slip_culprit_leak` the worker's `DefectClass` string and the regenerator's `defect_class_hint` are byte-identical, so `attemptsUsed(packageId, defectClass)` transparently counts delegated attempts — no extra bookkeeping needed. For the `meta_text_leak` fallback, the worker's own cap check (before delegating) queries `defect_class = 'meta_text_leak'` — matching what the regenerator will actually log — deliberately *not* `'template_artifact'` (the worker's name for the free-strip lane). These are two distinct, independently-capped repair lanes for the same underlying detector: 2 free-strip attempts and, separately, 2 delegated-regeneration attempts. Documented here rather than unified because unifying them would require either renaming a class string a live system already logs under (touching history) or adding a class-name-mapping layer for one call site — more risk than the accepted outcome of "a stubborn package can be attempted up to 4 times total across two different mechanisms before a human is needed," which is still bounded and still strictly better than today's unconditional escalate.

### 4. Concurrency claim

New column `mystery_packages.remediation_claimed_at timestamptz` and two `SECURITY DEFINER` RPCs, `claim_package_for_remediation(_pkg_id uuid, _ttl_minutes int default 10)` and `release_package_remediation_claim(_pkg_id uuid)`. The claim is a single atomic `UPDATE ... WHERE id = _pkg_id AND (remediation_claimed_at IS NULL OR remediation_claimed_at < now() - ttl) RETURNING id` — row-level MVCC locking means two concurrent callers racing this statement serialize on the row; the loser's `UPDATE` commits second, re-evaluates the `WHERE` against the now-current (just-claimed) row, and affects zero rows. No advisory lock needed: `pg_advisory_lock` is session-scoped and the edge function's Postgres access is per-RPC over PostgREST (no persistent session to hold it on), so a column-based claim with a TTL is both simpler and correctly self-releasing if the function crashes or times out mid-repair — the claim just expires after `_ttl_minutes` (default 10, comfortably above the regenerator's typical single-character runtime and below the 4-hour full-sweep cadence, so a crashed claim never blocks the next legitimate attempt for more than one 5-minute tick).

Scope: only the three delegated-repair classes acquire a claim (`identity_contamination`, `slip_culprit_leak`, the `meta_text_leak` fallback) — these are the only repairs now reachable from two different schedules (the new 5-minute held-only sweep and the existing 4-hour full sweep) on the same package. The worker's other classes remain single-schedule (4-hour only, unchanged), so they carry no new concurrency risk and don't need a claim. `delegateToRegenerator` acquires the claim immediately before calling `regenerate-child-content` and releases it in a `finally`-equivalent (best-effort, logged-but-non-fatal on failure) immediately after, regardless of outcome; the TTL is the crash backstop, not the primary release mechanism.

## Rationale

- **Reuses the exact contract ADR-0054 wrote for this pass**, rather than inventing a new integration shape — the "worker delegates, regenerator owns the gate" split was already decided; this ADR executes it plus the two structural pieces (claim, cadence) ADR-0054 explicitly deferred as follow-on.
- **No new trigger, no `pg_net` on the hot completion path.** ADR-0055 already proved the pull-based (detector-RPC-sees-`needs_review`) fix works and is cheap; extending it with a tighter, narrowly-scoped poll is the smallest change consistent with that already-validated pattern, and keeps `validate_package_characters()` — a function every completion goes through — free of a dependency on edge-function availability.
- **The claim is a data-plane primitive (a column + two RPCs), not new infrastructure**, matching every other safety rail in this codebase (whitelisted accessors, shared log, shared cap) being a small SQL/edge addition layered onto existing tables rather than a new subsystem.
- **Keeping the two `meta_text_leak` repair lanes separately capped and separately named**, rather than forcing one shared bookkeeping key, avoids touching a live system's existing logged class name (`template_artifact`) purely for cosmetic unification.

## Alternatives Considered

1. **`pg_net` call from `validate_package_characters()` on entry to `needs_review`.** Rejected — see Decision 1. Couples a synchronous, every-completion data-integrity trigger to an LLM-calling edge function's latency/availability, and reintroduces exactly the kind of "second independent writer of retry state" complexity ADR-0047/ADR-0054 both avoided by keeping all mutation behind one gated path.
2. **Tighten the existing 4-hour cron itself to 5 minutes, for all six classes.** Rejected: would 48x the frequency of the paid classes (`missing_images`, `game_overview_victim_mismatch`) too, for no latency benefit on those (they aren't gate-blocking — `missing_images` is explicitly excluded from the gate per ADR-0053, and `victim_mismatch` already has no reported live backlog), just more spend-cap pressure and more log volume for classes that don't need the tighter cadence.
3. **Wrap the delegated call in `runGatedAttempt` anyway, treating the regenerator as a black-box `FixPlan.apply()`.** Rejected — see Decision 2 and the task's own explicit instruction. Two independent revert paths on the same writes is a correctness hazard, not redundancy; ADR-0054's Discussion section already flags this exact risk.
4. **`pg_advisory_lock` / `pg_try_advisory_lock` instead of a claimed column.** Rejected: session-scoped advisory locks require a held connection for their duration; PostgREST/RPC calls from the edge function don't guarantee one connection per logical operation, so a lock acquired in one RPC call is not reliably held or released across the several subsequent RPC calls (`readField`/`writeField`/Claude call/`logRow`) the repair actually makes. `pg_advisory_xact_lock` would release at the end of a *transaction*, but the repair isn't one transaction — it's many independent statements over HTTP. A column with a TTL sidesteps this entirely.
5. **Give `regenerate-child-content` its own attempt-cap column/table**, symmetric with the worker's. Rejected: the worker already owns `attemptsUsed()` against the shared log, and the regenerator is meant to be a directly-callable primitive independent of any one caller's retry policy (a human hitting it directly, or the ADR-0053 gate's future repair-in-loop, may want different retry semantics). Keeping the cap in the caller (the worker) that has retry logic to bound is the same shape ADR-0047 already established.

## Consequences

- `identity_contamination` and `slip_culprit_leak` — the ADR-0047 worker's two permanently-escalated classes since 2026-07-29 — now self-heal, capped at 2 attempts each before requiring a human, exactly like every other class the worker handles.
- Character-scoped `meta_text_leak` instances that were embedded (not cleanly strippable) now also get a real repair attempt instead of an unconditional escalate; package-scoped ones are unchanged (still escalate if unstrippable — out of scope for a child-content function).
- A held package can now be repaired within ~5 minutes instead of waiting up to 4 hours (or indefinitely, for the two previously-escalate-only classes) for the next full sweep.
- New surface: one column, two small RPCs, one new cron job, ~120 lines of worker changes. No new edge function, no new secrets, no new tables.
- **Two independently-capped repair lanes for `meta_text_leak`** (free strip vs. delegated regeneration) is a deliberate, named asymmetry — see Decision 3 — rather than a oversight.
- **Not addressed here, named as follow-up:** the `needs_review_at` trigger-ordering bug ADR-0055 recorded (timestamp is `NULL` on the gate path, so the customer-facing banner's 10-minute grace window doesn't work) is unrelated to this wiring but affects how much of this ADR's latency improvement customers actually perceive before the banner would show anyway. Still tracked separately, not fixed in this pass.
- **Not addressed here:** the ADR-0053 gate's own "repair-in-loop" integration (calling the regenerator synchronously before ever setting `needs_review`, rather than after) — ADR-0054's Discussion names this as a separate follow-on with its own call-site design. This ADR only wires the *post-hold* (worker) side.

## Discussion

The most consequential call was in Decision 1: given the task brief explicitly offered a trigger/`pg_net` option, why not take it? The honest answer is that ADR-0055 changed the problem before this ADR got written. When the task was framed, "the gate can't call an edge function synchronously" read as an open problem needing a new mechanism. It isn't open anymore — ADR-0055 solved the half of it that actually mattered (the worker couldn't *see* held packages) without touching the gate's synchronicity at all, by fixing the predicate on the read side instead of adding a push on the write side. Re-solving an already-solved problem with a heavier mechanism (a trigger calling out over the network on every single package completion, gated or not) would have been the wrong instinct here — the actual remaining gap was purely "the worker only looks every 4 hours," which is a scheduling question, not an architecture question. Recognizing that distinction — and re-reading ADR-0055 before writing anything, rather than trusting the task brief's framing of the state of the system — is most of what this ADR's Decision 1 actually is.

The second real judgment call was whether to touch `handleTemplateArtifacts`'s internals at all for the `meta_text_leak` fallback, versus scoping this ADR to only the two classes ADR-0054 named explicitly (`identity_contamination`, `slip_culprit_leak`) and leaving `meta_text_leak` fully alone. The case for leaving it alone: it already has a safe, free, working repair path for the common case, and the task's own phrasing ("meta_text if currently escalated") is conditional, not mandatory. The case for touching it, which won: ADR-0054 was built with `meta_text_leak` support in its `defect_class_hint` enum specifically because its own doc comment says the function exists to fix "the character-sourced half of meta_text_leak" — building that capability and then never calling it for the one class it names by name would leave a primitive with a real, tested capability permanently dark. The change made is deliberately the smallest one that exposes that capability: capture-don't-bail on the existing refusal path, delegate only what was refused, leave everything else about the free-strip behavior untouched.

Worth naming plainly, in the style this project's other ADRs have used: this ADR does not make the regenerator smarter, and does not change what "fixed" means for any class — `package_completion_blocking_defects()` remains the sole arbiter of promotion, exactly as the invariants below require. What changes is purely *who gets a repair attempt before a human does*.
